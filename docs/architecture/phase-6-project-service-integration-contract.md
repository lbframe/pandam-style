# Phase 6 / Project Service integration contract

## Design-system authority

The compiler creates one immutable `pandamstyle-canonical-design-system`
snapshot in `packages/compiler/src/design-system/registry/snapshot.js`. Its
identity is
`{ systemId, registryDigest, abiVersion, compilerContractVersion, manifestSchemaVersion }`;
it also owns capability flags, normalized vocabulary, compiled public refs, CSS
rule inputs, the public manifest, candidate domains and repair domains. The
snapshot is compiler-owned and is not returned to application runtime.

Project Service code may consume immutable projections and narrow queries from
that snapshot:

- design identity and capability/version fields;
- the generated JavaScript facade and adjacent declaration file;
- `manifest.json`, `artifacts.json` and identity-tagged `styles.css`;
- paginated public token candidates, optionally filtered by category;
- public repair domains for tokens, recipe axes/values, themes and conditions.

The internal primitives are `candidateDomainOf(snapshot, query)` and
`repairDomainOf(snapshot, query)`. A service wrapper owns revision checks,
pagination, role checks and result envelopes. Public/page queries must use
public domains. Private definitions stay inside the compiler and are not
returned as candidate or repair vocabulary.

## Artifact identity

The generated artifact set records one common `systemId`, `registryDigest`, ABI
version, compiler contract version and manifest schema version. It records
SHA-256 and byte length for the design module, declaration, manifest and CSS;
`artifactSetDigest` authenticates the identity plus those four content digests.
The compiler validates the set before publication. All five generated files are
staged in the same publication transaction.

These fields describe design-system semantics and generated bytes. They do not
contain `projectId`, `sessionId`, `RevisionId`, `GenerationId`,
`artifactRevision` or `associationRevision`. The Project Service remains the
only owner of those lifecycle identities and publication associations.

## Ownership boundary

Phase 7 must not own or reconstruct:

- registry building or normalization;
- a separate token catalog;
- a separate recipe catalog or variant-domain map;
- a separate theme catalog;
- public/private visibility rules for design vocabulary.

Phase 7 may own revision-bound query methods and publication lifecycle. Those
methods must read this snapshot or its immutable query projections; they must
not read generated manifest text as an alternate registry or retain mutable
registry nodes. Runtime refs continue to carry only the ABI v1 fields and do not
acquire session, revision or generation IDs.

## Stable ordering

Token paths and candidate/repair domains preserve registry declaration order,
which is deterministic and matches the established diagnostic contract. Token
category names and recipe IDs are ordered lexicographically; each recipe
preserves its declared axis order and each axis preserves its declared value
order. Condition names preserve their declaration order because condition order
participates in registry identity. The generated `base` theme comes first,
followed by theme names in lexicographic order. Type unions retain token
declaration order and recipe axis/value order. Supported-property entries
preserve the compiler policy table's declared order. These rules are independent
of filesystem enumeration.
