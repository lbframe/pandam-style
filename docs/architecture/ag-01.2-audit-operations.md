# AG-01.2 design note: audit read, compute and materialize

Status: **design, for review**. This note is PR 0 of
[#9](https://github.com/lbframe/pandam-style/issues/9) (AG-01.2, epic
[#4](https://github.com/lbframe/pandam-style/issues/4)). Rule 2 of the
[agent delivery protocol](../agent-delivery-protocol.md) applies: #9 adds the
agent layer's first write operation (`audit.materialize`, behind a mutation
grant) and results computed on invalid revisions. No code is written before this
note is reviewed.

The base is `be5a8fa`, the head of AG-01.1 PR 1
([#135](https://github.com/lbframe/pandam-style/pull/135), not merged yet). The
[AG-01.1 note](ag-01.1-operation-registry.md) is merged. It already registers
`audit.read`, `audit.compute` and `audit.materialize` as `planned` entries owned
by #9 (its §3.9). This note implements them and amends them where §3 says so.
The [accepted plan](agentic-optimizations-plan.md) (AG-01) is a plan, not a
shipped API.

"Audit" here means the **coverage audit** of a revision: the project-wide
`pandamstyle-coverage-report` that `requestFullAudit()` produces today. It is
unrelated to [docs/agent-audit.md](../agent-audit.md), the read-only consumer
assessment of whether a project could adopt PandamStyle.

Evidence labels, as in AG-01.1:

- **observed**: produced by a command run for this note (§1.1).
- **source, unverified**: read in source only, not executed.

## 1. Inventory of today's audit behaviour

### 1.1 Method

The probes are scratch scripts outside the repository, not committed. They load
`.pms-test-support/compiler-inspection.cjs`, built at `be5a8fa` with
`rollup --config ./rollup.config.mjs`. The same build gave `lib/index.mjs`
851,010 bytes (SHA-256 prefix `50b66d2aafadb071`) and `lib/cli.mjs` 854,858
bytes (`2209472f51a770d9`). The probes use copies of the test harness
(`session-helpers.js`, `pms-helpers.js`) renamed to `.cjs`. Each probe copies a
fixture into a fresh temporary directory and hashes every file under the project
before and after each call.

- `probe1.cjs` (valid fixture): `requestFullAudit` before and after publication,
  with a ticket prepared before each call. It reads the in-generation document,
  the build report's `coverageReport` and the state file. It ends with a second
  `compile()` of the same revision.
- `probe2.cjs`:
  - A: an audit requested after publication only.
  - B: a symlink planted at the next audit file path.
  - C: a second session over the same project.
  - D: the audit directory replaced by a symlink to `src/`.
  - E: the same project audited from two process working directories.
- `probe3.cjs`: `requestFullAudit` on unvalidated, invalid and stale revisions
  of `neg-forbidden-value` (page failure), `neg-unresolved-import` (closure
  failure) and a token-cycle definition (design-system failure). It also covers
  a mixed project, the valid fixture plus one failing page, through the internal
  session.
- `probe4.cjs`: the v1 `audit` block after staging, `compile()` and a second,
  post-publication request.

### 1.3 Audit artifacts: location, identity and freshness

There are two locations:

- **In the generation**, `<outDir>/coverage.json`: only when the audit was
  staged before `compile()`. The state file certifies it like every other
  generation file: `files["coverage.json"]` carries its digest and size
  (probe1).
- **In the audit directory**, `.<outDir>.pms-audit/coverage-rev-<N>.json`: when
  the audit was requested after publication.

Both hold the same `pandamstyle-coverage-report` document, schema version 1. Its
fields are `documentKind`, `schemaVersion`, `contractVersion`, `systemId`,
`registryDigest`, `revisionId`, `generationId`, `coveredRoots`, `entryCount` and
`entries`. In probe1, the entries of the standalone document equal those of the
in-generation one. The valid fixture's document is 3,886 bytes with 10 entries.

Findings (A for audit, to keep them apart from AG-01.1's F1–F8):

- **A1. Staging is not a consultation, and it changes the publication.** A
  pre-publication `requestFullAudit` changes the next generation and breaks a
  prepared ticket (§1.2). It is effect `session-state: stages-audit`, which no
  AG-01.1 grant allows (AG-01.1 §3.2.2).
- **A2. The writer follows symlinks.** It uses `mkdirSync` and `writeFileSync`
  with no link check (`session/index.js:3991`).
  - A symlink planted at `coverage-rev-2.json`, pointing at `src/page.js`: the
    call returned the link's path as the document path and **overwrote the
    covered source `src/page.js`** with the coverage JSON. The link was still in
    place afterwards. The project's next validation failed with a
    `PMS_COVERAGE_GAP` syntax error in `src/page.js` (probe2 B).
  - The audit directory replaced by a symlink to `src/`: the document was
    written into `src/` (probe2 D).
- **A3. The document names no project and no session, and its file name collides
  across sessions.** `revisionId` restarts at 1 in each session, while
  `generationId` continues across sessions through the state file. A second
  session at revision 1 found the first session's `coverage-rev-1.json` (10
  entries, generation 1) still present. Its own v1 block said
  `materialized: false`, which is true of that session. Its own audit then
  overwrote the same path with a different document (11 entries, generation 2)
  (probe2 C). A reader that resolves the document by path and `revisionId` alone
  can take another session's audit for the current one.
- **A4. Entry paths depend on the process working directory.** `relativeToCwd`
  (`session/fresh.js:295`) gives `src/barrel.js` when the process runs inside
  the project, and an absolute path otherwise. `coveredRoots` is always
  absolute. The same revision therefore produces different bytes in two
  processes with different working directories (probe2 E).
- **A5. The v1 document names the standalone document, never the in-generation
  one.** After staging and `compile()`, the block is
  `{ requested: true, materialized: true, document: null }`. A later
  post-publication request sets `document` to the standalone path (probe4). In
  probe1, a `commitPrepared` after that request reset `document` to `null`
  (source cause unverified). The in-generation document is found only by its
  fixed name.

### 1.4 Invalid revisions: what the session knows

`validate()` stops at the first failing stage (`session/index.js:2449` onwards,
source). Each stage leaves different facts behind:

| Failing stage                                                           | Example (probe3)                                                      | Coverage facts left on the revision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Scan error, or the design-system build                                  | token cycle: `coveredFileCount` 0, `designSystem` both `null`         | No closure is computed. Nothing about coverage is known. The v1 `completeness.status` is still `complete`, because it describes discovery, not coverage (observed). A reader must not take it as complete coverage.                                                                                                                                                                                                                                                                                                                                                      |
| Closure (`PMS_COVERAGE_GAP` for an unresolved import or a syntax error) | `coveredFileCount` 1, `completeness: partial`, `resyncRequired: true` | `state.covered` holds the closure, a lower bound past the unresolved edge. No file is analysed in this revision. File states keep contributions from earlier revisions, which do not describe this one (source, unverified).                                                                                                                                                                                                                                                                                                                                             |
| Page analysis (compile failures)                                        | `neg-forbidden-value`: `coveredFileCount` 2, `affected.total` 1       | The analysis loop runs over every covered file and builds a complete `analysis.coverage` array, including `failed: true` entries with `codes`. That array is **discarded** when the revision fails: `active.coverage` is only assigned on success (`session/index.js:2620`, source). In the mixed project, the passing page keeps its compiled artifact and the failing one has none (`_artifactFor`). The legacy result's affected entries carry the failed entry, and `projectEntries` is 11 (observed). An unreadable file gets no entry at all (source, unverified). |
| Consistency or target evaluation                                        | not probed                                                            | The analysis ran in full; the same discarded array exists (source, unverified).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

- **A6.** Useful coverage exists for most invalid revisions, but nothing exposes
  it. Where nothing is known, nothing says so either: the token-cycle revision
  reports `completeness: complete` with 0 covered files.

## 2. Threat model

The adversary, trust boundary and assets are those of AG-01.1 §2. The adversary
is the agent. It controls request payloads and anything it can write: sources,
the definition, files in the output and audit directories (including symlinks,
directories and FIFOs), and the process's behaviour through its edits. It can
repeat, reorder and race requests. The host that creates the session and mints
capabilities is trusted. The new assets are audit documents, the meaning of
"fresh", the audit receipt and the host's disk.

| #    | Threat                                                                                                                                                            | Required property                                                                                                                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TA1  | A read or compute mutates the revision, its verdict, tickets, outputs, publication intent or host counters, as staging does today (A1)                            | `audit.read` and `audit.compute` declare no effect beyond `consult` and assign nothing in the session. They never call `validate()`, `requestFullAudit()`, `count()` or `bump()`. Equality is tested over the complete observable state (§5.2).    |
| TA2  | A stale or foreign audit artifact is presented as current: another session's file (A3), another working directory (A4), an earlier generation, a hand-edited file | "Fresh" means byte equality with the document the current revision would produce now. Metadata inside the file is never trusted. Every other case is an explicit `stale`, `missing` or `unreadable` result.                                        |
| TA3  | Materialization without authority                                                                                                                                 | `audit.materialize` needs the `materialize-audit` grant. Capabilities are host-minted, non-serializable objects (AG-01.1 §3.4). A `consult` capability is `denied-access: missing-grant`.                                                          |
| TA4  | Materialization writes outside the declared output: a symlink or directory swap (A2), or an agent-chosen path                                                     | The path is derived from host configuration only. No input names a path, so there is nothing to traverse. The writer never follows a link and writes exactly one regular file in a real audit directory, or fails with nothing written outside it. |
| TA5  | A read follows a planted link, blocks on a FIFO or device, or reads a huge file                                                                                   | `lstat` first. Only a regular file whose size equals the expected size is opened, with `O_NOFOLLOW` and `O_NONBLOCK`, and checked again with `fstat`. Everything else is `unreadable` or `stale` without reading it.                               |
| TA6  | Unbounded results: huge projects, long relay chains or paths, invalid revisions with many files                                                                   | Entries are a paged list under AG-01.1 §3.10: totals before projection, records never cut, oversized records withheld and readable through `records.read`. Every frame field is bounded at its source.                                             |
| TA7  | A receipt is forged or replayed to claim an audit exists                                                                                                          | A receipt is evidence, never authority. No operation accepts a receipt as input. It binds revision, design system, generation, path, bytes and SHA-256, and anyone can check it with `audit.read`.                                                 |
| TA8  | Invented coverage on an invalid revision: entries from an earlier revision, counts that read like a passing build, "complete" where nothing is known (A6)         | Entries come only from the current revision's own analysis. Files the revision did not analyse are explicit `unknown` records. Completeness and limitations come from closed enums derived from the stage reached.                                 |
| TA9  | Outcome ambiguity: an audit of an invalid revision read as a failed operation, or as a passing build                                                              | `audit.compute` is not a verdict operation. It succeeds when it describes the revision, and the revision's validity is a field of the result, never the outcome.                                                                                   |
| TA10 | Disk exhaustion through repeated materialization                                                                                                                  | One fixed file name per revision, replaced in place. The number of files grows only with revisions, which consultations cannot create.                                                                                                             |
| TA11 | A partial write is taken for a complete document                                                                                                                  | Write to an exclusive temporary file, `fsync`, then `rename`. A reader sees either the old entry or the complete new file.                                                                                                                         |

Out of scope for #9: transports and their authentication (AG-02.x); concurrency
between owners (AG-10); a sandbox against code the host chooses to run (AG-01.1
§2). A host-side race in which another process swaps the audit directory between
the writer's check and its `rename` is a residual (§6).

## 3. Design

### 3.1 Layering

```
packages/compiler/src/agent/handlers/audit.js   new: the three handlers
packages/compiler/src/agent/registry.js         the three entries become implemented (§3.2)
packages/compiler/src/agent/schemas.js          audit list, address and output fragments
packages/compiler/src/api/project.js            three module-private hooks (§3.6)
packages/compiler/src/project/session/index.js  two revision fields, a pure document
                                                builder, the safe writer, two accessors
packages/compiler/src/protocol/diagnostics.js   `PMS_UNSAFE_AUDIT_PATH` in `Codes`
```

The AG-01.1 layering holds. `agent/` imports `api/project.js`, and nothing on
the session path imports `agent/`. The new handler module is under `src/agent/`,
off the published entries (AG-01.1 §3.1, I8). The session-side code is inline in
modules that `lib/index.mjs` and `lib/cli.mjs` already reach, so the
reachability allowlist (`reachability.v1.json`) does not change (§5.3).

### 3.2 Registry amendments

The AG-01.1 entries were written before this design (AG-01.1 §6, I12). #9
changes them through a reviewed registry change, as AG-01.1 requires.

| Entry               | AG-01.1                                                                                   | #9                                                                                                                                                                                                                                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `audit.compute`     | `consult`, `computes`. In `{ rev, page }`, out `{ page }`                                 | Same grant and effect. Out `{ audit, page }` at offset 0 and `{ page }` after, like `check`. Adds `invalid-input: not-validated`. Status `implemented`.                                                                                                                                                         |
| `audit.read`        | `consult`, `reads-generated`. In `{ rev, generationId? }`, out `{ present, fresh, page }` | Effects `reads-generated` and `computes`. In `{ rev }`: only the current generation exists on disk, so `generationId` selects nothing. Out `{ canonical, artifacts }` (§3.4). Adds `invalid-input: not-validated`. Status `implemented`.                                                                        |
| `audit.materialize` | `materialize-audit`, `writes-audit`. In `{ rev, expectedGenerationId ≥ 1 }`               | Effects `computes` and `writes-audit`. `expectedGenerationId` is an integer ≥ 1 **or `null`**, so an unpublished revision can be materialized. The receipt is §3.5. Adds `invalid-input: not-validated`, `constraint-violation: unsafe-audit-path`, `internal-error: audit-write-failed`. Status `implemented`. |

The list and address vocabularies gain one member each:

- `RECORD_LISTS` gains `audit-entries`.
- `RECORD_ADDRESS` gains `{ kind: 'audit-entry', index }`: the `index`-th record
  of the current revision's audit list (§3.3).

AG-01.1's rule "every list with a total has an operation that reaches every
element" (I10) then covers the new list. `audit.compute` pages it, and
`records.read` returns any withheld record.

The meaning of `writes-audit` (AG-01.1 §3.2.1) is made precise: it writes one
document in the audit directory and **records that document on the revision**,
so the v1 `audit` block stays true. It never stages, never changes the candidate
and never revokes a ticket. `session-state: stages-audit` stays forbidden to
every grant.

### 3.3 `audit.compute`: the pure in-memory path

**Session state (the only session-path change).** Each revision object gains two
fields, assigned in `validate()`:

- `coverageStage`: `'none'` initially. It becomes `'closure-partial'` or
  `'closure'` once the closure is computed (partial when it has unresolved
  edges), then `'analysed'` once `analyseCoveredFiles` returns.
- `analysisCoverage`: the `analysis.coverage` array, assigned as soon as the
  analysis returns, **before** any failure is thrown.

On a valid revision `analysisCoverage` is the same array as `active.coverage`,
so nothing more is retained. On a failed revision it keeps an array the analysis
already built until the next revision replaces the revision object. Both fields
belong to one revision object (`session/index.js:2059`), so a value can never
leak into the next revision (TA8).

**Accessor.** `_auditCoverage({ offset, limit })` reads the current revision and
assigns nothing. It returns the stage, the true total and one page of the audit
list:

| Stage             | The audit list                                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `analysed`        | The `analysisCoverage` entries, unchanged v1 coverage records with `analysed: true`. Then an `unknown` record for each covered file that has no entry (unreadable, or a consistency gap), in closure order |
| `closure`         | One `unknown` record per covered file, in the analysis order, with reason `analysis-not-run`                                                                                                               |
| `closure-partial` | The same, over the partial closure                                                                                                                                                                         |
| `none`            | Empty, `total: 0`                                                                                                                                                                                          |

An `unknown` record is `{ file, origin, analysed: false, reason }`, where reason
is `analysis-not-run` or `not-analysed`. `file` uses the same `relativeToCwd` as
the v1 entries. The schema discriminates the two record kinds by the `analysed`
constant (AG-01.1 §3.3 `oneOf`). Known records are never reshaped.

The accessor never calls `ensureFileState`, `count` or `bump`. It never reads
file states, because a file state may hold an earlier revision's contribution
(§1.4). It reads only `analysisCoverage`, `state.covered` and the generated
module's path.

**Output at offset 0.**

```js
{
  audit: {
    kind: 'pandamstyle-agent-audit', version: 1,
    validation: { ok },                     // the session's verdict, as data
    coverage: {
      stage,                                // 'none' | 'closure-partial' | 'closure' | 'analysed'
      completeness,                         // 'complete' | 'partial' | 'unknown'
      coveredFiles,                         // closure size, or null for 'none'
      knownEntries, unknownEntries,
      summary,                              // coverageSummary() over the known entries
    },
    limitations: [ /* closed, at most 8 */ ],
    canonical: { documentKind, schemaVersion, generationId, bytes, sha256 } | null,
  },
  page,                                     // the agent page of 'audit-entries' (AG-01.1 §3.10)
}
```

- `completeness` is `complete` only at `analysed` with no unknown record. It is
  `unknown` at `none`, and `partial` otherwise.
- `limitations` is a closed set:
  - `validation-failed`: the revision is invalid; these entries describe it, but
    no generation will contain them;
  - `design-system-unavailable`: no current design system (AG-01.1 §3.12);
  - `scan-failed`;
  - `closure-not-computed`;
  - `closure-incomplete`: unresolved edges, so `coveredFiles` is a lower bound;
  - `analysis-not-run`;
  - `files-not-analysed`;
  - `failed-files-without-rules`: failed entries contribute no rules, so
    `summary.ruleTotal` is a lower bound.
- `canonical` is present only on a valid revision. It describes the document
  `audit.materialize` would write now: `buildCoverageReport` over
  `analysisCoverage`, with `generationId` set to the published generation or
  `null`, serialized as `requestFullAudit` serializes it. It is built by a pure
  function split out of `materializeCoverageReport`, without its `count()` calls
  (TA1).
- The identities are in the envelope. `designSystem` is present only when it is
  current (AG-01.1 I9). Nothing in `audit` repeats or invents one.
- `references[]` carries the list continuation and any `records.read`, as in
  AG-01.1 §3.10. When `validation.ok` is `false` it adds a `check` reference for
  the diagnostics. Diagnostics are not duplicated here.

**Outcome (TA9).** `audit.compute` returns `success` whenever it describes the
current revision, whether the revision is valid or not. It is not a verdict
operation, and `classifyVerdict` is not applied to it. A request on an
unvalidated revision is `invalid-input: not-validated`, with a reference to
`check`. Compute does not validate: validating would change the revision's
validation state, and AC1 requires that state preserved. `check` already
validates without revoking tickets (AG-01.1 §3.9).

**Cost.** At offset 0 the call is O(entries) for the summary. On a valid
revision it adds one serialization of the canonical document, which is 3,886
bytes for the valid fixture; the source puts it at about 3.25 MB at c10000
(session comment at `:3250`). Later pages only slice. Nothing is retained after
the call.

### 3.4 `audit.read`: verified read of existing artifacts

Input `{ rev }`. Preconditions: the current revision, validated. Output:

```js
{
  canonical: { … } | null,          // as in audit.compute
  artifacts: [                      // always both locations, in this order
    { location: 'generation',      path, status, reason, bytes, sha256 },
    { location: 'audit-directory', path, status, reason, bytes, sha256 },
  ],
}
```

- The `generation` path is `<outDir>/coverage.json`. The `audit-directory` path
  is `<auditDir>/coverage-rev-<N>.json` for the current revision `N`. Both are
  derived from host configuration and bounded by the binding's `outDir` bound
  (`BOUNDS.auditPath`).
- `status` and `reason`:
  - `fresh`, reason `null`: the bytes equal `canonical`;
  - `stale`, reason `revision-invalid` (there is no canonical document to
    match), `size-differs` or `content-differs`;
  - `missing`, reason `null`;
  - `unreadable`, reason `not-regular-file` or `read-failed`.
- `bytes` is the size from `lstat`, or `null`. `sha256` is reported only when
  the status is `fresh`: it is then `canonical.sha256`, and no hash of an
  arbitrary file is disclosed.

**Verification (TA2, TA5).**

1. `lstat(path)`. `ENOENT` gives `missing`. Anything other than a regular file
   (symlink, directory, FIFO, socket, device) gives
   `unreadable: not-regular-file`, and the file is not opened.
2. With no canonical document (invalid revision): `stale: revision-invalid`, not
   read.
3. A size different from `canonical.bytes` gives `stale: size-differs`, not
   read. The amount read is therefore never more than the canonical size.
4. `open` with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`. `fstat` must show a regular
   file with the same device, inode and size. Exactly that many bytes are read.
5. SHA-256 over the bytes, compared with `canonical.sha256`.

The read never parses the file, never trusts its `revisionId`, `generationId` or
`systemId`, and never returns its content. A fresh document has, by definition,
the same content as `audit.compute`. The result references `audit.compute` for
it. A stale document is not current truth and is not served.

This settles A3, A4 and A5 by construction. Another session's file, a file from
another working directory and a hand-edited file all differ from the canonical
bytes. The in-generation document is checked like the standalone one, whatever
the v1 `audit.document` says.

### 3.5 `audit.materialize`: authorized write and receipt

Input `{ rev, expectedGenerationId }`, where `expectedGenerationId` is the
caller's view of `generationId`: an integer ≥ 1 when the current revision is
published, otherwise `null`. Grant `materialize-audit`. Checks, in this order
after AG-01.1's dispatcher checks (capability before input):

1. Exact current revision, else `stale-revision: revision-mismatch`. Validated,
   else `invalid-input: not-validated`.
2. Valid, else `constraint-violation: revision-invalid`.
3. The generation the document would name equals `expectedGenerationId`, else
   `stale-revision: generation-changed`.
4. Write the canonical bytes with the safe writer (below).
5. Record the document on the revision, exactly as the post-publication branch
   of `requestFullAudit` does today: `active.audit`, `auditReportReadyNs`, and
   the cached result rebuilt. `active.auditRequested` is **not** set. The
   publication candidate digest does not include `active.audit`
   (`session/index.js:4477`, source, unverified), so a prepared ticket stays
   valid. A test asserts it (§5.1).

**Safe writer (TA4, TA11).** It replaces `writeCoverageStandalone`. The SDK path
of `requestFullAudit` after publication uses it too, so A2 is closed for the
class and not only for the agent operation.

1. `dir` is `auditDir()`, derived from the host's `outDir`. Its parent is
   host-configured and trusted. Create `dir` if absent, then `lstat(dir)`. It
   must be a real directory, not a symlink. Otherwise fail with
   `PMS_UNSAFE_AUDIT_PATH`, reason `audit-directory-not-directory`, and write
   nothing.
2. Open `coverage-rev-<N>.json.<pid>.<uuid>.tmp` in `dir` with
   `O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW`, mode `0o644`. Write, `fsync`,
   close.
3. `rename(tmp, final)`. `rename` replaces a symlink or file at `final` without
   following it, so a planted link is removed and its target is untouched. If
   `final` is a directory, `rename` fails: unlink the temporary file and fail
   with `PMS_UNSAFE_AUDIT_PATH`, reason `audit-file-not-file`.
4. `lstat(final)`: a regular file of the written size. Any other I/O failure
   (`ENOSPC`, `EACCES`) unlinks the temporary file and is
   `internal-error: audit-write-failed`, with the `errno` code only.

`PMS_UNSAFE_AUDIT_PATH` is a new structured `PmsError` code. Both the SDK and
the agent path raise it. The agent maps it to
`constraint-violation: unsafe-audit-path` (the reason above in `context`). It is
documented by the registry's generated descriptions, and in
`diagnostics-protocol-v1.md` at AG-02.5 (AG-01.1 decision Q2).

**Receipt (TA7).**

```js
{
  receiptKind: 'pandamstyle-audit-receipt', receiptVersion: 1,
  operation: 'audit.materialize',
  requestId,                                   // echoed when it passed the format, else null
  revision: { projectId, sessionId, revisionId },
  designSystem: { systemId, registryDigest },  // current by precondition 2
  generationId,                                // integer or null, as written in the document
  location: 'audit-directory', path,           // absolute, ≤ BOUNDS.auditPath
  documentKind: 'pandamstyle-coverage-report', schemaVersion: 1,
  bytes, sha256, entryCount,
}
```

`sha256` equals `canonical.sha256` from `audit.compute` and `audit.read` at the
same revision and generation, and `audit.read` reports the file `fresh` right
after. The receipt confers nothing. No operation consumes receipts, so forging
or replaying one changes nothing. Its truth is checked against the file, never
against a signature. The receipt binds `sessionId`; the document does not (A3).
Retry policy: `never` (AG-01.1 §3.2.3 rule 6). Repeating the call at the same
revision and generation rewrites identical bytes. Declaring it retry-safe needs
a repeat-call test and is left to AG-10.1.

### 3.6 Hooks, queueing and cancellation

`project.js` adds three hooks under the existing module-private symbol
(`AGENT_SESSION_HOOKS`): `auditCompute`, `auditRead` and `auditMaterialize`.
Each runs as **one queued step**, so the revision check and the work see the
same state, like `check` (AG-01.1 §3.9). Cancellation is `before-start` for all
three: an abort before the step starts gives `cancelled` with no effect. Once
the materialize step starts, it completes or fails as a whole.

The raw SDK `requestFullAudit` keeps its contract and its staging branch. Its
standalone write switches to the safe writer (§3.5), the only SDK behaviour
change. That change is listed in `CHANGELOG.md`.

### 3.7 The AG-02.1 write path, reconciled

AG-01.1 §7 states, under D1: "`publish` is planned, not implemented, so no write
path exists before AG-02.1." **Decision: `audit.materialize` ships implemented
in #9, behind a host-minted `materialize-audit` capability. `publish` stays
planned (AG-07.3).**

- AC3 of #9 requires a materialization that needs mutation authority and
  produces a receipt. A `planned` entry has no handler (AG-01.1 I2), so leaving
  it planned would fail AC3.
- The concern behind the AG-01.1 sentence is a write reachable by an
  unauthenticated caller. That concern still holds. The agent layer has no
  package export and no Rollup entry until AG-02.5 (AG-01.1 §3.1). Only
  in-process code holding the host binding can mint a capability, and that code
  is the trusted host. No transport exists before AG-02.1 authenticates callers.
- The write is the narrowest possible: one compiler-derived file in a directory
  outside `outDir` and outside the generation. It touches no source, no
  generated output and no ticket.

PR 1 therefore amends the AG-01.1 sentence to: "No write path is reachable from
a package export or a transport before AG-02.1. The first implemented write,
`audit.materialize` (#9), is reachable only in process, through a host-minted
`materialize-audit` capability."

## 6. Self-attack: how this design could be wrong

- **AC1, preservation.**
  - _An undeclared effect hides in the accessors._ The perf collector is host
    state. Mitigation: `S` includes the collector's counters, and the accessors
    have no `count` calls.
  - _Rebuilding the cached result in materialize changes `check`._ That is
    materialize's declared effect (§3.2), and AC1 does not cover materialize.
    The AC3 test asserts the v1 block names the path. Nothing else in `S` may
    change, and the AC3 test asserts that too, minus the audit fields and the
    new file.
  - _The candidate digest starts including `active.audit` in a later change._
    The AC3 ticket assertion fails then.
- **AC2, invalid revisions.**
  - _A stage that leaves `analysisCoverage` from a partial loop_, for example a
    non-`PmsError` exception in the middle of the analysis. `analysisCoverage`
    is assigned only after `analyseCoveredFiles` returns, so an interrupted loop
    leaves stage `closure` and every file `unknown`. A fault-injection test
    throws inside the loop.
  - _The closure order differs from the analysis order_ for `unknown` records.
    The differential oracle compares hot and cold lists, and a cold session
    builds the same order.
  - _The hot list legitimately differs from the cold list._ The analysis loop
    and the mixed-project probe (§1.4) suggest it does not, but the claim is
    unverified, in particular for target-evaluation failures. If the oracle
    finds a real difference, the case is reported as a finding, not normalized.
  - _`relativeToCwd` paths are host-dependent (A4)._ Compute inherits them.
    Changing the coverage report's path base is a format change and out of
    scope. The limitation is stated, and freshness by bytes stays correct.
- **AC3, materialization.**
  - _TOCTOU on the audit directory_: another process swaps the directory for a
    symlink between `lstat` and `rename`. Node has no `openat`. The window is
    host-side, and the agent's edits run in its own process. The residual is
    stated, not claimed closed. The AG-10 concurrency work owns it.
  - _The parent of the audit directory is a symlink._ It is host-configured, so
    it is trusted, like `outDir` itself. An agent that can rewrite host
    configuration is outside the boundary (AG-01.1 §6, AC3).
  - _Disk growth (TA10)._ One file per revision, as today. A retention policy is
    deferred.
  - _A stale `null` generation document after publication_ reads as
    `content-differs`, not as a dedicated reason. Materializing again fixes it.
    A dedicated reason would require parsing the file, which J4 forbids.
- **AC4, freshness.**
  - _A false `fresh`_ would need a file byte-identical to the canonical
    document, which is then the current audit, whoever wrote it. That is not a
    false claim.
  - _A false `stale`_ is possible for a document that differs only in path base
    (A4) or in `generationId`. It is conservative and explained by its reason.
  - _Hashing an arbitrary planted file of the right size_ discloses nothing:
    `sha256` is reported only for `fresh`.
- **Bounds.** A new frame field could be unbounded. Mitigation: AG-01.1's
  registry-load rule requires every string in a frame position to name its
  source bound, and `frameMax` is recomputed.
- **Reconciliation (§3.7).** A future export of the agent layer would publish
  the write path. AG-02.5 owns that export and inherits AG-02.1 authentication;
  the amended AG-01.1 sentence states the condition.
