- **test**: asserted by an existing test that was run for this note.

## 1. Inventory of existing operations and effects

`packages/compiler/lib/index.mjs` built from `f4e0a10`

- Added in review round 1, together with the reviewer's `ag011-probe.cjs`:

Other findings that the design must absorb:

- F1. `validate()` revokes live publication tickets. A consultation built on it
  would let a reader cancel the host's pending publication.
- F2. Expected input errors are `TypeError`s, not structured diagnostics.
- F3. `candidateTokens` has unbounded `limit` and coerces non-string input.
- F4. `compile` is not byte-idempotent, so publication is not safely retryable.
- F5. `watch()` schedules work. No consultation may start it.
- F6. **Design-system identity and vocabulary are attributed to revisions they
  were not derived from.** The session keeps its last successful build when a
  rebuild fails (`state.designSystem` is only assigned on success,
  `src/project/session/index.js:710`). It rebuilds only when the definition
  digest changes (`:2179`). All of the following were observed (`probe4.mjs`,
  `probe5.mjs`, `probe6.mjs`):
  - Valid rev 1, then a cyclic definition: rev 2 reports `PMS_TOKEN_CYCLE`, but
    `designSystem` keeps rev 1's digest `ac409b6b43e77a38`, and
    `candidateTokens` returns rev 1 tokens labelled rev 2.
  - An invalid `targets` change behaves the same way: rev 5 has
    `PMS_INVALID_TARGET_CONFIG` and rev 4's identity and vocabulary.
  - **False acceptance.** The next revision after the failure, with no
    definition change, validates `ok: true` with no diagnostic. `compile()` then
    publishes generation 2 under rev 1's design system, although the declared
    definition is still cyclic, or the declared `targets` still invalid.
  - Recovery works. A valid definition after the failure produces a fresh
    identity (`conformance@0.2`, `12f11f03e1579ff5`) and its tokens.
  - Cold failures leave no design system. `candidateTokens` throws a plain
    `Error` before and after validation, and the v1 identity is invented (§1.5).
- F7. The affected list is cut to 64 before any paging could reach it (§1.2).
  The protocol v1 doc says the remainder is in the coverage document, which
  needs an audit write. No consultation reaches the full list today.
- F8. A single diagnostic can be unbounded. An unknown token name of 1,200,000
  characters gives one `PMS_UNKNOWN_TOKEN` of 2,401,487 bytes: `message` is
  1,200,019 bytes and `context.tokenId` 1,200,002 (observed `probe4.mjs`; the
  reviewer measured 2,401,569 with its own path names). The string is
  agent-controlled.

## 2. Threat model

**Adversary.** The agent driving the operations. It controls request payloads
(JSON data), and anything it can write: project sources, the design-system
definition, the config file, project metadata and descriptions. It can repeat,
reorder and race requests.

**Trusted.** The host or operator process that creates the `ProjectSession`,
holds the binding and mints capabilities. Code running inside the host process
is trusted. As the epic states, this boundary does not sandbox arbitrary code
that the host chooses to execute. That includes config modules the host loads on
purpose.

**Assets.** Source files, generated output and audit files, publication intent
(tickets), revision and design-system identity, the host's CPU and memory, and
the meaning of outcomes.

| #   | Threat                                                                                                                                                                                                                     | Required property                                                                                                                                                                                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1  | Forge or escalate a capability through a request field (`role`, `grants`, `capability`), project metadata or a config value                                                                                                | Authority comes only from a host-held object that JSON cannot express. Unknown request fields are rejected, never ignored.                                                                                                                   |
| T2  | Replay a capability across sessions, or after `close()`                                                                                                                                                                    | Each capability is bound to one binding (project and session), and revoked when that session closes.                                                                                                                                         |
| T3  | A consultation mutates sources, generated output or audit files, or cancels a ticket (F1)                                                                                                                                  | `consult` operations declare no write effect and no ticket revocation. This is checked when the registry loads and by an effect test over every registered `consult` operation.                                                              |
| T4  | A consultation executes config or definition code (§1.4)                                                                                                                                                                   | No PR 1 operation loads a module. Loading config is a separate planned operation behind a dedicated grant (`load-config`, AG-02.x).                                                                                                          |
| T5  | Invented identities make a stale or foreign result look bound (§1.5)                                                                                                                                                       | Identities are taken only from the session and the registry snapshot. An unknown identity is absent from the envelope and `null` in the v1 document.                                                                                         |
| T6  | Stale-revision misuse: answer for revision N presented as current, or a cursor reused after a change                                                                                                                       | Every project-dependent request carries the exact revision, and pagination is bound to it. A mismatch yields `stale-revision`, never a silently substituted revision.                                                                        |
| T7  | Oversized, deep, cyclic or getter-bearing input (resource exhaustion, TOCTOU), unbounded `limit` (F3)                                                                                                                      | Input is snapshotted into plain JSON data under byte, depth, string and array limits before validation. Validation and execution both use that snapshot.                                                                                     |
| T8  | Truncation hides an error: a compact view shows only warnings while an error lies past the cut                                                                                                                             | The outcome and `ok` come from the complete result before projection. Totals are true totals. Truncation is explicit.                                                                                                                        |
| T9  | Outcome ambiguity: "unsupported capability" vs "denied access" vs browser `PMS_TARGET_CAPABILITY_*`                                                                                                                        | Distinct outcomes with discriminators. Browser target diagnostics never set an envelope outcome other than through ordinary severity (§3.6).                                                                                                 |
| T10 | Planned operations silently execute partial behavior                                                                                                                                                                       | A `planned` entry has no handler. Dispatch returns `unsupported-capability` before reading its input.                                                                                                                                        |
| T11 | Probing other projects: paths, `projectId` and session ids of other owners                                                                                                                                                 | Responses contain only the bound session's identities. Mutation paths stay confined (existing `isWithin` checks). The absolute-path `projectId` default is kept (decision Q4, §8).                                                           |
| T12 | Error messages used as authority, such as prompt-injected text in a project file quoted back                                                                                                                               | Diagnostics stay structured: code, rule and reason. `message` is convenience (protocol v1). Description fields in the registry are compiler-authored constants, never project text.                                                          |
| T13 | An identity or vocabulary derived from an older definition is presented as the current revision's, or a failed definition is silently replaced by the last good one (F6)                                                   | A design-system identity is reported for revision R only when it was built from R's definition and configuration. Otherwise it is absent. Older vocabulary is never served as current. A failed definition stays failed until it is changed. |
| T14 | An agent-controlled value inside or outside a record (a long token name, `systemId`, category or path) makes a response larger than its ceiling, makes paging stall, or makes a projected output break its own schema (F8) | Every frame component is bounded at its source, or rejected there. A list record that is too large is withheld whole and readable in chunks. Records are never cut or reshaped, and a non-v1 page never claims v1. Every page advances.      |
| T15 | Pagination is promised over data the session already discarded (F7)                                                                                                                                                        | Every list with a total has a revision-bound operation that reaches every element. It is recomputed on demand, not retained.                                                                                                                 |

Out of scope for #8: transport authentication and descriptor theft (AG-02.1),
concurrency and crash recovery (AG-10), and fact schemas for properties,
resources and targets (CE-12.1, AG-03). Audit read, compute and materialize
operations are inventoried here and implemented by #9.

## 3. Design

### 3.1 Layering, and keeping the agent layer off the session path

```
packages/compiler/src/agent/        new: registry, schema subset, dispatcher,
                                    capabilities, handlers, codegen
packages/compiler/src/protocol/envelope.js   new: envelope builder, outcome table
packages/compiler/src/api/project.js         existing: small fixes (§7)
packages/compiler/src/project/session/index.js  existing: design-system freshness
                                    (§3.12) and on-demand affected paging (§3.10)
packages/compiler/src/design-system/registry/index.js  existing: `systemId` guard (§3.12)
```

The dependency direction is one-way: `agent/` imports `api/project.js` and
`protocol/*`. Nothing under `api/`, `project/`, `artifacts/`, `frontend/`,
`engine/`, `design-system/` or `targets/` imports `agent/` or `envelope.js`.

**Exposure without eager import.** PR 1 adds **no package export and no Rollup
entry**. `package.json` exports belong to AG-02.5. The agent layer is therefore
unreachable from `lib/index.mjs`, `lib/cli.mjs`, `lib/host.mjs` and every host
adapter. Tests reach it from source, as `accepted-snapshot-test.js` already
does, or through the private test bundle `tests/support/compiler-inspection.js`.
Both stay outside the published files.

When AG-02.5 exposes it, it must be a **separate Rollup input** with its own
`lib/agent.mjs` behind its own subpath. It must not be a lazy `import()` from
`index.js`. Every current output is a single `file:` bundle, so Rollup would
either inline a dynamic import or need a chunked output. The first defeats
laziness; the second changes the package layout.

This also matters for security. In PR 1, the published package ships no
capability-minting code. No new authority surface is published before the
transports authenticate their callers.

The hooks the agent layer needs inside the session queue are functions added to
`project.js`, keyed by a module-private symbol that is not exported from
`api/index.js`. They are the `check` step (§3.9), the affected-list page (§3.10)
and the record read (§3.10). None allocates anything per session until it is
called.

The session-path changes of §3.12 and §3.10 add two scalars to the session state
and one accessor that is not called by `validate()` or `compile()`. Their
expected memory effect is stated in §5.3.

### 3.2 Registry entry shape

There is one registry module, `src/agent/registry.js`. Every entry is a frozen
plain object:

```js
{
  name: 'check',                       // stable, kebab/dot case
  status: 'implemented',               // 'implemented' | 'planned'
  owner: 'AG-01.1',                    // planned: delivering issue, e.g. 'AG-04.1 #19'
  summary: '…',                        // compiler-authored tool description
  requires: {
    grant: 'consult',                  // closed enum, §3.4; null = no capability needed
    binding: 'session',                // 'none' | 'session'
    revision: 'current',               // 'none' | 'current'
  },
  preconditions: [                     // closed ids, each with its outcome when unmet
    { id: 'session-initialized', outcome: 'invalid-input' },
  ],
  effects: [                           // closed enum, §3.2.1
    { kind: 'computes' },
    { kind: 'session-state', detail: 'records-validation-verdict' },
  ],
  input: <schema>, output: <schema>,   // §3.3 subset
  errors: [                            // expected error contracts
    { outcome: 'stale-revision', code: 'PMS_STALE_REVISION', reasons: ['revision-mismatch'] },
  ],
  views: ['compact', 'detail'],
  pagination: { kind: 'offset', boundTo: 'revision' } | null,
  cancellation: 'before-start',        // 'none' | 'before-start'
  retry: { idempotent: true, policy: 'safe' }, // 'safe' | 'after-refresh' | 'never'
}
```

#### 3.2.1 Effect vocabulary (closed)

The effect kinds, all paths taken as resolved and canonical:

| Kind                | Meaning                                                                                                         |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| `reads-registry`    | Reads the current design-system snapshot                                                                        |
| `reads-sources`     | Reads files under `rootDir` outside `outDir`, as text: sources, manifests and config files. Never executes them |
| `reads-generated`   | Reads `outDir`, the state file or the audit directory                                                           |
| `computes`          | CPU-bound work in memory                                                                                        |
| `session-state`     | Changes in-memory session state. Closed details below                                                           |
| `session-lifecycle` | Opens, attaches to or closes a session. Closed details below                                                    |
| `schedules`         | Starts background work: watchers or timers                                                                      |
| `writes-generated`  | Writes `outDir` and the state file                                                                              |
| `writes-audit`      | Writes the audit directory                                                                                      |
| `writes-sources`    | Writes files under `rootDir` outside `outDir`, restricted to the paths of the input's `scope`                   |
| `executes-config`   | Imports or calls config or definition modules                                                                   |

`session-state` details: `records-validation-verdict`, `binds-client`,
`revokes-publication-tickets`, `advances-revision`, `stages-audit`.

`session-lifecycle` details: `opens-session`, `acquires-output-lease`,
`closes-session`, `releases-output-lease`.

#### 3.2.2 Grants and the effects they allow

Each entry has **exactly one** grant, or none. The grant fixes the set of
effects it may declare. One entry is therefore one authority and one effect
class.

| Grant                  | Effects it allows                                                                                                                            |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| none                   | `reads-registry` (registry data only, no project binding)                                                                                    |
| `consult`              | `reads-registry`, `reads-sources`, `reads-generated`, `computes`, `session-state: records-validation-verdict`, `session-state: binds-client` |
| `publish`              | the `consult` set, plus `writes-generated` and `session-state: revokes-publication-tickets`                                                  |
| `mutate-sources`       | the `consult` set, plus `writes-sources`, `session-state: advances-revision` and `revokes-publication-tickets`                               |
| `extend-design-system` | as `mutate-sources`, with `scope` restricted to the definition module                                                                        |
| `materialize-audit`    | the `consult` set, plus `writes-audit`                                                                                                       |
| `load-config`          | the `consult` set, plus `executes-config`, `session-lifecycle: opens-session` and `acquires-output-lease`                                    |
| `manage-session`       | the `consult` set, plus `schedules`, `session-lifecycle: closes-session` and `releases-output-lease`                                         |

No grant allows `session-state: stages-audit`. An entry declaring it fails to
load. The detail stays in the vocabulary so the inventory can name the effect of
`requestFullAudit` (§1.5), which no operation reproduces.

#### 3.2.3 Load-time checks (by construction)

`createRegistry()` throws, and the module fails to load, if any of these fails.
They apply to **every** entry, `planned` or `implemented`. No entry is exempt.

1. Keyword, effect, grant, outcome and precondition sets are all closed.
2. `status: 'implemented'` holds exactly when a handler exists in
   `src/agent/handlers/`.
3. The declared effects are a non-empty subset of what the entry's grant allows
   (§3.2.2).
4. `input` and `output` compile (§3.3). `input` is a closed object that declares
   every field the operation reads, and binds the revision where
   `requires.revision` is `current`.
5. `errors` holds the universal contracts, plus at least one operation-specific
   contract for every declared precondition and every `writes-*`,
   `executes-config` or `session-lifecycle` effect:
   - the universal contracts are `invalid-input`, `denied-access` when a grant
     is set, `cancelled` when cancellation is not `none`, `internal-error`, and
     `unsupported-capability` when the status is `planned`;
   - each specific contract names an outcome, a code and closed reasons.
6. `retry` agrees with the effects. Any `writes-*`, `executes-config`,
   `session-lifecycle`, `advances-revision` or `revokes-publication-tickets`
   effect forces `idempotent: false` and policy `never`. The one exception is an
   entry that names a repeat-call test in `retry.evidence`; the contract suite
   runs that test. Idempotency keys arrive with AG-10.1.
7. The effect set is fixed per entry. No input field, `oneOf` branch or flag
   selects between a consultation and a mutation. This is why `repair` and
   `extend` are split into `propose` and `apply` entries (§3.9).

Runtime validation, TypeScript declarations and tool descriptions are all
derived from these entries (§3.8). Nothing else describes an operation.

### 3.3 Schema subset (D2, kept)

This is an in-house, closed-keyword subset of JSON Schema. The allowed keywords
are `type` (`object`, `array`, `string`, `integer`, `boolean`, `null`),
`properties`, `required`, `additionalProperties: false`, `items`, `enum`,
`const`, `minimum`, `maximum`, `minLength`, `maxLength`, `maxItems`,
`description`, and `oneOf` over objects discriminated by a `const` property.

`additionalProperties` must be `false` on every object. `pattern` is excluded,
which removes any regex denial-of-service risk; identifier formats use
`enum`/`const` or a fixed character-class check implemented in code under a
named `format` from a closed list (`request-id`, `project-relative-path`).

Why not a dependency such as Ajv:

- Parity. With a closed subset, the type generator and the description generator
  are total: every legal schema has exactly one TypeScript and one description
  rendering. A full validator accepts keywords that the generators cannot
  represent, and parity would hold only by convention.
- Threat model. T1 needs unknown fields rejected everywhere. Requiring
  `additionalProperties: false` on every object is enforced at registry load.
  With a general validator it would be a per-schema convention.
- The plan forbids a parallel validator or registry. A second schema library
  would be one.

**Input pipeline (T7).** `snapshotRequest(value)` first produces plain JSON
data. It reads own enumerable data properties only, so getters are rejected, not
invoked. It rejects functions, symbols, `undefined`, non-finite numbers, cycles
and non-plain prototypes. It enforces maximum depth, string length, array length
and the total serialized byte count before any schema walk. Validation then runs
on the snapshot, and the handler receives the same frozen snapshot. There is no
TOCTOU window between validation and execution.

### 3.4 Capabilities (D5, kept with changes)

- **Minting.** A host binds a session with
  `createAgentBinding({ session, initialize })` (§3.7). Only the binding can
  mint: `binding.mintCapability({ grants })`. That function exists only on the
  host-held binding object.
- **Representation.** A capability is a frozen object with no own data. Its
  authority is a module-private `WeakMap` entry from that object to
  `{ bindingId, grants, revoked }`. A JSON value, a structured clone, a spread
  copy, `Object.create(cap)` or a `Proxy` has no entry, so it is **denied**. A
  capability from another copy of the module also fails closed.
- **Presentation.** The capability is passed out-of-band:
  `binding.dispatch(request, { capability, signal })`. It is never read from
  `request`. A request containing `capability`, `role`, `grants` or any other
  undeclared field is `invalid-input` (closed schemas), not ignored. Project
  metadata, definition fields and config values are never consulted for
  authority.
- **Grants.** The set is closed (§3.2.2). `consult` covers reads and computation
  with no write, execution or ticket effects. Every other grant is used only by
  planned operations in PR 1, so PR 1 can mint `consult` alone. A minted
  capability is immutable. Narrowing means minting a new capability; nothing can
  widen one.
- **Revocation.** All capabilities of a binding are revoked when the session
  closes or the binding is disposed.
- **Check order.** (1) Envelope shape. (2) Operation exists. (3) Operation is
  implemented. (4) Capability is valid, bound to this binding, not revoked, and
  holds the grant. (5) Input schema and limits. (6) Preconditions. (7)
  Execution.

  Checking the capability before the input means that an unauthorized caller
  learns nothing about the validity of a payload. The registry itself is public
  (§3.8), so reporting a planned operation before the capability check leaks
  nothing.

**Against the threat model.** T1 holds by construction: no code path reads
authority from data. T2 holds through binding identity and revocation.
In-process code holding the binding is the trusted host. That is the stated
boundary, not a sandbox.

Bridge authentication (AG-02.1) maps an authenticated connection to a capability
held on the host side. The wire carries no capability token in #8. Any token
format introduced later must resolve to this same object check.

### 3.5 Response envelope

```js
{
  protocol: 'pandamstyle-agent',  protocolVersion: 1,
  operation: 'check',             // echoed only if it names a registry entry
  requestId: 'r-42',              // echoed only if it passed the `request-id` format
  outcome: 'success',             // §3.6
  identities: {                   // each key ABSENT when unknown, never invented
    projectId, sessionId,
    revision: { projectId, sessionId, revisionId },
    designSystem: { systemId, registryDigest },
  },
  result: <operation output> | null,  // for `check`: { document } at offset 0,
                                       // { page } after (§3.10)
  diagnostics: [ /* protocolDiagnostic(), unchanged */ ],
  diagnosticsTotal, diagnosticsTruncated,
  failure: {                      // present iff outcome !== 'success'
    stage: 'request' | 'bootstrap' | 'execution',
    reason: '<closed id>',        // e.g. 'malformed-identity', 'output-owned'
    precondition: '<id>' | null,
    capability: '<protocol capability id>' | null, // unsupported/denied only
    retry: 'never' | 'after-refresh' | 'same-request',
  },
  references: [ { operation, input } ],  // follow-up requests, revision-bound
  view: 'compact' | 'detail',
  page: { offset, limit, returned, nextOffset, total, truncated } | null,
  withheld: [ { address, code?, severity?, bytes, sha256 } ],  // §3.10, ≤ 1 per list
  limits: { maxResponseBytes, responseBytes, floor, frameMax },
}
```

- **Diagnostics.** The envelope uses `protocolDiagnostic()` from
  `diagnostics-result-v1.js` **unchanged**. It already accepts `revision: null`
  (observed: `protocolDiagnostic(d, null)` returns `revision: null`), which is
  what bootstrap failures need.

  Envelope `diagnostics` carry request and execution failures. When an
  operation's result is itself a diagnostics document (`check`), the project's
  diagnostics stay inside that versioned document and are not duplicated.
  `failure.reason` names the case.

- **Identities.**

  - `revision` appears only when the operation is bound to an initialized
    session.
  - `designSystem` appears only when the session's design system is **current
    for that revision**: built from the revision's own definition and
    configuration (§3.12). An older successful build is never reported as
    `designSystem`.
  - When an older build exists, the envelope may add
    `identities.lastValidDesignSystem: { systemId, registryDigest, derivedFromRevision }`.
    It is labelled historical by its name and its own revision. It is
    informational only: no operation serves its vocabulary as current.
  - The v1 document, whose fields are mandatory, carries explicit `null` for
    both `systemId` and `registryDigest` in the same cases. This is the rule
    protocol v1 already states: "explicit null rather than invented precision".
    It is decided without a protocol version bump (Q3, §8).

- **Serialization.** The envelope is plain JSON. It contains no `undefined`,
  functions, `Date`, `Map` or class instances. This is checked by the round-trip
  test (§5).

Rules that hold by construction:

- `outcome` is computed by one function, `classify(result | error)`, in
  `envelope.js`. Handlers return values or throw. They never set an outcome.
- Severity, not code family, decides between `success` and
  `constraint-violation`. A browser target diagnostic therefore follows the same
  rule as every other diagnostic. `unsupported-capability` is produced only by
  the dispatcher (steps 2–3 of §3.4) and by the `snapshot-disabled` mapping. No
  `phase: 'targets'` diagnostic reaches it.
- A verdict with `ok: false` and no error diagnostic (incomplete coverage) is
  `constraint-violation` with reason `incomplete-validation`. It is never
  `success`.
- New codes are additive (protocol v1 allows this). The envelope codes are
  defined in `envelope.js`; `PMS_INVALID_DEFINITION` is added to `Codes`. In PR
  1 they are documented by the registry's generated descriptions. They are added
  to `diagnostics-protocol-v1.md` when the agent API is exposed in AG-02.5
  (decision Q2, §8).

### 3.7 Bootstrap

`createAgentBinding({ session, initialize: true })` calls `session.initialize()`
once. A failure is recorded as a structured bootstrap failure:

- the original diagnostics, or a `PMS_INTERNAL` diagnostic for a non-`PmsError`;
- `revision: null`;
- `identities: { projectId, sessionId }` only. Both exist even on failure.

Every later operation on that binding returns this failure. It does not return
the `PMS_SESSION_CLOSED` that hides the cause today (§1.2).

A host that initializes the session itself passes `initialize: false`.
Definition and `targets` failures surface through `check` as
`constraint-violation` with `stage: bootstrap` and no `designSystem` identity
(§3.6). This holds whether the failure is cold or follows a valid build, and on
every later revision until the definition or configuration changes (§3.12).

Loading a config file is not part of any PR 1 operation (T4). The CLI's
config-load failures are inventoried (§1.4). Their structured replacement is the
planned `session.open` (AG-02.1/AG-02.5) under `load-config`. Its contract in
the registry maps "file not found" to `invalid-input`, "module threw" and "not
an object" to `constraint-violation`, both with `stage: bootstrap`.

### 3.8 Negotiation and schema discovery

`protocol.operations` is implemented and needs no capability; the registry is
public, compiler-authored data. Its input is optional:

```js
{ protocolVersions?: [1], view?, names?: [...] }
```

It returns:

- the selected `protocolVersion`, or `unsupported-capability` when there is no
  overlap;
- the supported views and the limits (request bytes, depth, response bytes);
- the closed grant and effect vocabularies;
- for each entry: `name`, `status`, `owner`, `summary`, `requires`, `effects`,
  `errors`, `cancellation` and `retry`. The `detail` view adds `input` and
  `output` schemas.

When a capability is presented, the response adds `granted: [...]` and, for each
operation, `available | denied | planned`. A caller learns what it may do
without trial and error.

Generated artifacts:

- **Runtime validation** interprets the registry schemas directly. There is no
  generated code and no `new Function`.
- **Tool descriptions** are `describeOperations(registry, view)`, the function
  behind `protocol.operations`. MCP (AG-02.6) consumes the same function.
- **Types** are generated by `src/agent/codegen.js` into
  `src/agent/generated/operations.d.ts`, which is committed. The file is not in
  the package `files` until AG-02.5 exposes it.

**`check` and F1.** Today a reader that calls `validate()` revokes the host's
prepared ticket. `check` runs as one queued step through the module-private hook
in `project.js`:

- If a validation verdict exists for the exact current revision, `check` builds
  the result without re-validating, so no ticket is revoked.
- Otherwise it validates. In that case no live ticket can exist:
  `preparePublication` validates before issuing, and every revision change and
  every validation revokes.

The same-queue step removes the race between "is it validated?" and "validate".

### 3.10 Views, pagination and limits

**Views.** `compact` is the default: candidates ≤ 8 per diagnostic, diagnostics
≤ 20 per page, affected entries ≤ 16. `detail` applies the protocol v1 defaults
(32 candidates, 64 affected entries) and allows explicit `page` requests.

**Totals before projection (T8).** Projection runs after `classify()`. `ok`,
`outcome`, `diagnosticsTotal`, `candidatesTotal` and `affected.total` are true
totals of the complete result. Each projected list sets its `…Truncated` flag.

**Every truncated list has an operation that reaches every element (T15).** Each
such list adds a `references[]` entry that names an operation able to reach all
of it, bound to the same revision.

| List                         | Where it is cut today                                        | Operation that reaches all of it                                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| diagnostics                  | not cut by the session; the full list is in the result       | `check` with `page` (a page result, see below)                                                                                                                             |
| candidates of one diagnostic | cut by `candidateLimit` in the v1 builder                    | `diagnostics.candidates` over the current snapshot. It is a full domain, not the diagnostic's own list, so the `candidatesQuery` of the v1 document is honoured as written |
| affected entries             | **cut to 64 inside the session** (F7), before the v1 builder | `diagnostics.affected`, below                                                                                                                                              |
| any withheld record          | not withheld today (F8)                                      | `records.read`, below                                                                                                                                                      |

**`diagnostics.affected` recomputes, it does not retain.** PR 1 adds a private
session accessor, `_affectedCoverage({ offset, limit })`. It runs the same
computation as `affectedCoverageOf(active)` (`src/project/session/index.js`)
over the current revision's `active.invalid`, `active.newFiles`,
`active.removedFiles` and `state.fileStates`. All of that state is already kept
for the current revision. The accessor returns one sorted page and the true
count, and is reachable only through the `project.js` hook.

- It is called by no validation or compile step and stores nothing. Each call
  allocates one transient array of the touched entries, which is what
  `affectedCoverageOf` already allocates during result building.
- It is bound to the exact current revision: any other revision is
  `stale-revision`. A revision is never served from retained history.
- The count it returns must equal the v1 `affected.total` for that revision. The
  test asserts this, so the two cannot diverge.
- Entries keep `removed` and `analysed`, which the v1 projection drops. Removed
  files appear with `role: null, removed: true`, as the session builds them
  (probe: 70 removed files gave `total: 70` and `role: null` entries).
- The v1 builder (`diagnostics-result-v1.js`) is not changed. Its 64-entry
  inline list stays as it is, and the envelope's reference points past it.

**One response-size rule for every component (T14).** Every response component
is bounded in one of two ways.

1. **Bounded at its source**, for the response frame: everything except list
   records. These components and their bounds:

   - `systemId`: at most 128 UTF-8 bytes, enforced by the definition guard
     (§3.12).
   - `projectId`: at most 1,024 bytes. `outDir` and `rootDir`: at most 4,096
     bytes each. `createAgentBinding` checks these against the session and
     refuses the binding (a host-facing `TypeError`) before any request.
   - `sessionId`: a UUID. `registryDigest`: compiler-produced hex. `revisionId`
     and `generationId`: safe integers.
   - `requestId`: at most 128 characters, a closed format (§3.3).
   - `failure.*`, `outcome`, `view` and every v1 status field (`completeness`,
     `generation`, `milestones`, `audit`, `incremental`): closed enums,
     integers, booleans or the identities above.
   - `references[]`: at most one per list kind of the table above. Each one's
     input holds only the revision, integers and enums.
   - `page` and `withheld[]` entries: integers, enums, compiler codes and a
     SHA-256. `withheld[]` has at most one entry per list, because a page stops
     at its first withheld record.
   - Envelope failure diagnostics:
     - **Request failures** (schema, limits) never echo request values. They
       name the failing schema path, which is closed property names and array
       indexes.
     - **Lifecycle failures** carry only identities, bounded at the source as
       above, and request fields already bounded by the request limits.
     - **Bootstrap failures** are list records (rule 2), retained by the binding
       (§3.7).
     - As a fail-safe, `classify()` checks every other failure record against
       the record ceiling. A record over it becomes `internal-error` with reason
       `unbounded-failure-record` and a constant-size diagnostic. A test proves
       this path unreachable for every failure source listed here.

   The maximum frame size, `frameMax`, is computed from the registry's output
   schemas and these bounds. A test fills every frame component at its maximum
   and asserts `frameMax` in both views.

2. **Withheld whole if too large**, for list records. A record is a diagnostic,
   a candidate, an affected entry or a bootstrap failure diagnostic. Records are
   **never cut or reshaped**, so every record that appears is exactly what
   `protocolDiagnostic()` or the session produced. Every v1 required field is
   present, with its own totals and flags.

   A record whose canonical serialization exceeds the record ceiling (8 KiB in
   `compact`, 64 KiB in `detail`) is left out of the list. In its place, the
   response's `withheld[]` gains a constant-size entry:
   `{ address, code, severity, bytes, sha256 }`. `code` and `severity` are
   present for diagnostics only; they are compiler constants.

**Lists are always prefixes.** A page holds a contiguous run of records. It ends
before a withheld record, when the next record would pass the response ceiling,
or at `page.limit`. When the first record of a page is withheld, the page holds
no record, one `withheld` entry, and a next offset of `offset + 1`. Therefore:

- The `check` result keeps the v1 shape and meaning. Its `result.document` is
  the v1 document whose `diagnostics` array is the prefix `[0, k)`, with the
  true `diagnosticsTotal` and `diagnosticsTruncated: true` when `k` is less than
  the total. Protocol v1 allows exactly this: "Diagnostic lists may be bounded
  only with diagnosticsTotal/truncated and a revision-bound full diagnostic
  query … ok considers all diagnostics, not the displayed prefix"
  (`diagnostics-protocol-v1.md:140`). The inline `affected.entries` follows the
  same prefix rule.
- A page at `offset > 0` is not a v1 document and never claims to be one. It is
  returned as `result.page`, a distinct agent schema discriminated by
  `kind: 'pandamstyle-agent-page'`, `list`, `offset`, `records`, `total` and
  `withheld`. The record items are unchanged v1 records.

  The same page schema serves `diagnostics.candidates`, `diagnostics.affected`
  and the bootstrap failure list. The generated output types describe both
  `result.document` and `result.page`. The contract tests validate the runtime
  output against them for ordinary, truncated and withheld responses.

**`records.read` returns every withheld record in full.** It replaces the
round-1 `diagnostics.field`. Its input is `{ rev, address, page }`. Addresses
contain integers only, so they are bounded and unambiguous at one revision:

| `address.kind` | Fields                            | Record                                                                    |
| -------------- | --------------------------------- | ------------------------------------------------------------------------- |
| `diagnostic`   | `index`                           | the `index`-th diagnostic of the revision's complete ordered list         |
| `candidate`    | `index`, and a candidate `domain` | the `index`-th entry of the candidate domain selected by `domain` (below) |
| `affected`     | `index`                           | the `index`-th entry of the sorted affected list (§3.10)                  |
| `bootstrap`    | `index`                           | the `index`-th diagnostic of the binding's recorded bootstrap failure     |

**Candidate domains (BV-1).** A candidate domain is selected by one of three
forms, used identically by `diagnostics.candidates` and by the `candidate`
address of `records.read`:

- `{ kind: 'category-index', index }`: the `index`-th category of the revision's
  enumeration of public token categories, sorted by code unit. It depends on no
  other list and carries no category text, so every category is reachable
  whatever its length and whether or not a diagnostic names it.
  `categoriesTotal` in every candidates result bounds `index`.
- `{ kind: 'category', category }`: a name of at most 256 bytes, a convenience.
  A name outside the enumeration, including a prototype key such as
  `constructor`, selects an empty domain.
- `{ kind: 'from-diagnostic', index }`: the `expected.category` of the
  `index`-th diagnostic of the validated revision, so the v1 `candidatesQuery`
  is honoured as written. It needs a validated revision (`not-validated`) and a
  diagnostic with a category (`no-candidate-domain`).

Every candidates result reports `categoryIndex`, and every withheld candidate is
addressed in the `category-index` form, so no address depends on a diagnostic or
on an unbounded key. The bounded verification found that the round-2 selectors
(a category of at most 256 bytes, or a diagnostic index) left a valid category
over 256 bytes unreachable in a project with no diagnostic naming it. The class
is "a record kind whose selector depends on another list or on an unbounded
key". The other address kinds were checked against it: `diagnostic`, `affected`
and `bootstrap` index their own list, and `protocol.operations` pages a constant
list whose descriptions fit their record ceiling (checked at registry load), so
none is in the class.

The inline `affected.entries` of a `check` document at offset 0 holds v1
`{ file, role }` projections. When one is withheld, its `withheld` entry
describes the record its address reads, the agent's
`{ file, role, analysed, removed }` record of `diagnostics.affected`.

The response is a chunk of the record's canonical serialization: `JSON` with
every non-ASCII character escaped as `\uXXXX`. Byte offsets and character
offsets are then the same, and a cut can never split a character. Each chunk
carries `{ offset, bytes, sha256 }` of the whole serialization.

`records.read` recomputes from the current revision. The bootstrap failure is
the only retained case, and §3.7 already retains it. Any other revision is
`stale-revision`, and an index out of range is `invalid-input`.

**Positive progress.** The response floor is at least `frameMax` plus the record
ceiling plus one `withheld` entry. `maxResponseBytes` below the floor is
`invalid-input`, and the floor is published by `protocol.operations`. Therefore:

- every page with `offset < total` advances by at least one index;
- every `records.read` page with `offset < bytes` returns at least one byte;
- paging always terminates.

The page's `limit` is the maximum number of indexes covered. The next offset is
`offset + returned + withheld.length`, and the response states it.

**Continuations.** A `references[]` entry that continues the answered list is
the originating request with only `page.offset` advanced: the same operation,
view, limit and every selector (`names`, `protocolVersions`, `domain`,
`address`, `rev`). A reference's `input` is typed by its target operation's own
input schema, so the frame bound covers it. `records.read` returns the
continuation of its next chunk the same way.

**Every withheld record has its own reference.** Each `withheld` entry of a
response, in every list it holds (a `check` at offset 0 holds two), comes with a
`records.read` reference to exactly its address. A response therefore holds at
most five references: three continuations and two reads. The bootstrap list has
no paging operation, so a bootstrap record read in full refers to the next one.
The candidate domain of the first diagnostic with truncated candidates that a
`check` page covers, shown or withheld, is referenced from offset 0, because the
v1 record orders its candidate prefix by name and the domain by declaration. A
list is thus complete through returned references alone.

**Pagination binding.** Pagination is offset-based and carries the revision
explicitly. A page request for a non-current revision is `stale-revision`. No
cursor secret is needed: a forged offset only selects a bounded slice the caller
may already read, and a forged revision fails the exact-identity check.

**Limits.** The host binding sets ceilings. The proposed defaults are:

- request: 64 KiB serialized, depth 16, strings 4 KiB, arrays 512;
- response: 256 KiB for `compact`, 2 MiB for `detail`.

String bounds count the UTF-8 bytes of a string's JSON serialization, quotes
excluded (`stringLengthUnit: json-utf8-bytes`), so a bound on a string is a
bound on response bytes. `frameMax` and the floor are not chosen: the registry
derives them from the output schemas at load. In PR 1 they are 48,175 and 56,367
bytes in `compact`, and 105,519 and 171,055 bytes in `detail` (the round-2
proposal of a 96 KiB floor was an estimate; `detail` needs more because its
record ceiling is 64 KiB). The outcome never depends on the ceilings.

### 3.12 Design-system freshness and the `systemId` guard

This section fixes the class "identity or vocabulary attributed to a revision it
was not derived from" (F6, T13). It also fixes the session defect behind the
class's false acceptance.

**In the session (`src/project/session/index.js`).** Two scalars are added to
the session state:

- `designSystemCurrent: boolean`. It is set to `false` when a rebuild starts and
  to `true` only after it succeeds.
- `designSystemRevisionId`: the revision whose definition and configuration
  produced the current build.

The rebuild condition becomes:

```js
state.designSystem == null ||
  !state.designSystemCurrent ||
  fallbackReason != null ||
  definitionChanged;
```

A revision after a failed definition or `targets` change therefore rebuilds
again and reports the same failure. It no longer validates and publishes with
the last good design system (the probe 6 false acceptance).

`_designSystemIdentity()` returns
`{ systemId, registryDigest, derivedFromRevisionId, current }`.

**In the facade (`project.js`).**

- Every result that names a design system (v1 document, artifacts, receipts)
  uses the identity only when `current` is `true`. Otherwise it reports `null`
  for both fields. The `?? normalized.projectId` fallbacks are removed.
- `candidateTokens()`, and with it `diagnostics.candidates`, serves vocabulary
  only from a current build. When none exists, cold or after a failed change, it
  throws a structured `PmsError`: `PMS_INVALID_REVISION`, reason
  `design-system-unavailable`, the revision attached, and
  `lastValidDesignSystem` in its context when one exists. This replaces the
  plain `Error` of the cold case. Older vocabulary is not served.
- `repairDomain` is passed to the v1 builder only for a current build. Probe 4
  showed that a failed rebuild leaves only the bootstrap diagnostic (`rev2`: no
  page diagnostics), so this is a guard, not a behavior change.

**`systemId` guard (`src/design-system/registry/index.js`).** `buildRegistry`
first checks that `systemId` is a non-empty string of **at most 128 UTF-8
bytes**. Otherwise it emits the new structured diagnostic:

- code `PMS_INVALID_DEFINITION`, phase `design-system`, rule
  `definition.system-id`;
- context `{ field: 'systemId', actualType, bytes }`.

The context echoes only the value's type and byte length, never the value
itself, so the diagnostic is bounded.

Why a maximum enforced at the source, rather than truncating or hashing:

- **Exact authority.** A truncated `systemId` could collide with another
  system's identity, or be mistaken for it.
- **One identity across artifacts.** A digest form would differ from the
  `systemId` written into the generated artifacts.
- **The value is copied many times.** In probe 8, `systemId` appeared 38 times
  across 13 generated files. A 10,000-character value grew the generated output
  from 71,232 to 450,697 characters. Bounding it bounds the identity in every
  response and in the generated files.
- **Nothing in the repository is near the limit.** The longest `systemId` is 26
  characters (§6).

Today the reviewer's probe accepts a 1,200,000-character `systemId` with
`ok: true`, and its serialized identity is 1,200,051 bytes.

Today a missing, numeric or empty `systemId` becomes `PMS_SESSION_INTERNAL` with
an unrelated raw message (probe 7: "Cannot read properties of undefined", or a
`PMS_UNVERIFIED_PROPS_SOURCE` text). After the guard, it is a
`constraint-violation` with `stage: bootstrap`. That is an agent-repairable
definition error, not a compiler fault.

The guard covers `systemId` only. Property-domain validation belongs to the
parallel epic's `PMS_INVALID_PROPERTY_DOMAIN`. The two have distinct codes,
rules and fields. The only shared file is `registry/index.js`. The guard goes at
the start of `buildRegistry` (about line 103 at `f4e0a10`), away from the hunks
of CE-02.1 PR B (#132) at about lines 15, 458–473, 489 and 529.

**Units derived from the snapshot (CE-02.1, #132).** #132 adds a
`property-domains` semantic unit in `session/index.js` (about lines 609–615)
that reads `designSystem.snapshot.properties.digest`. A failed definition build
must never leave that unit, or any other unit derived from the snapshot, on the
old digest for a revision. This holds by construction:

- Semantic units are recomputed only inside a successful `rebuildDesignSystem`
  (`designSystemSemanticStateOf`, before `state.designSystem` is assigned).
- While `designSystemCurrent` is `false`, the revision ends at its bootstrap
  failure. No page analysis or publication consults any unit. Probe 4, `rev2`,
  shows this today: the cyclic-definition revision on the `neg-forbidden-value`
  fixture reports only `PMS_TOKEN_CYCLE`, with no page diagnostics.
- The rebuild is retried on every later revision, so the old digest is never
  carried into a valid revision.

The test plan adds the matching case (§5.1, AC2).

  - `PMS_SESSION_INTERNAL` keeps `internal-error`. It is triggered by a fault
    injected into the session.
  - Every later operation on a binding whose bootstrap failed returns that
    failure, not `PMS_SESSION_CLOSED`.
- **Capability denial.** Each of these gives `denied-access` with the matching
  `reason`:

  - no capability;
  - a JSON copy, a structured clone, a spread copy, `Object.create(cap)` or a
    `Proxy` of a valid capability;
  - a capability from another binding;
  - a capability after `close()`;
  - a capability without `consult`.

  A request with `role: 'host'`, `grants: [...]` or `capability: {...}` gives
  `invalid-input`. A definition or config carrying such fields grants nothing.
  Planned operations give `unsupported-capability` whatever the capability.

- **Compact and detail.** A fixture with more than 20 error diagnostics: in
  `compact`, `diagnosticsTotal` is the true count and `diagnosticsTruncated` is
  `true`, with a `references[]` entry; `detail` paging covers every diagnostic
  exactly once.

  **Exhaustive paging (I10).** For every list kind of the §3.10 table, follow
  `references[]` until done, and assert that the union equals the complete list
  exactly once, in order, with a count equal to the reported total. The
  affected-list cases are:

  - valid revision with 89 affected files;
  - 70 removed files (`removed: true`, `role: null`);
  - invalid revision with 81 affected files;
  - a definition-failure revision with 0;
  - page sizes 1, 7 and 256;
  - an offset past the end (empty page, `truncated: false`).

  A page request after a new revision is `stale-revision`, and the affected
  count equals the v1 `affected.total` at every step.

  **Oversized values (I11).** Each case runs in both views, and every response
  is checked against its ceiling.

  - **Inside records, one test per record kind.**

    - Diagnostic: an unknown token name of 1,200,000 characters, and a context
      array of 256 strings of 16 KiB (the reviewer's 12,586,234-byte record).
    - Candidate: a valid token named with 1,200,000 characters, in a project
      with zero diagnostics. It is reached through `diagnostics.candidates` by
      `category` and by `category-index`, and, in a separate fixture with a
      diagnostic, by `from-diagnostic`.
    - BV-1: a category of 257 bytes and one of 1,200,000 characters, each with a
      token of 1,200,000 characters, reached by `category-index` with zero
      diagnostics and again with unrelated diagnostics; the 257-byte name is
      refused by the `category` form without being echoed.
    - Affected entry: a deeply nested file path.
    - Bootstrap failure: a token cycle through a 1,200,000-character name.

    For each: the record is withheld, the response is under its ceiling, the
    `withheld` entry gives `bytes` and `sha256`, and `records.read` chunks of
    the maximum size reassemble to that SHA-256. The result parses back to the
    original record, deep-equal. Chunks of 1 byte and 7 bytes are run on the
    records of about 8 to 11 KiB (a withheld candidate and the nested affected
    path): one request per byte of a 1,200,000-character record is not a test
    budget, and the chunk arithmetic does not depend on the record. An affected
    path is at most 4,096 bytes on disk, at most about 25 KiB once escaped, so
    it is withheld in `compact` and never in `detail`.

  - **Outside records.**
    - A `systemId` of 129 bytes and of 1,200,000 characters gives
      `PMS_INVALID_DEFINITION` (the reviewer's probe today: `ok: true` with a
      1,200,051-byte identity). The maximum, 128 bytes, is accepted.
    - A session whose `projectId`, `rootDir` or `outDir` exceeds its bound is
      refused by `createAgentBinding`.
    - A `requestId` over 128 characters and a 4 KiB `category` that fails the
      schema are `invalid-input`, and neither is echoed.
    - A frame-maximum test fills every frame component at its bound and asserts
      `frameMax`.
    - Every non-bootstrap failure source of §3.10 is driven with maximal inputs,
      and its record stays under the record ceiling. This proves the
      `unbounded-failure-record` fail-safe unreachable.
  - **Schema.**
    - Every `check` response at offset 0 validates against the v1 document
      shape, including when the first diagnostic is withheld (`diagnostics: []`,
      true total, `diagnosticsTruncated: true`).
    - Every later page validates against the agent page schema and is not
      labelled v1.
    - Both are also validated against the generated output types, with
      `tsc --noEmit` over recorded responses.
  - **Progress.**
    - A list of many medium records: every page advances by at least one index,
      and paging terminates.
    - A list in which every record is withheld: one index per page, terminating.
    - `maxResponseBytes` below the floor is `invalid-input`.
  - Throughout, `ok` and the outcome equal those of the unprojected result.

  Class case (T8): order a fixture so that only advisory target warnings fall
  inside the compact window and the error lies past it. The outcome is still
  `constraint-violation` with `ok: false`.

- **Malformed input.** Table-driven over the closed keyword list:

  - wrong type, missing required field, unknown field, enum violation;
  - over-long string, over-long array, depth beyond the limit, serialized size
    beyond the limit;
  - a cycle, a getter (assert it is never invoked), a function, a symbol, `NaN`;
  - an invalid `requestId` (assert it is not echoed);
  - an unknown operation.

  All give `invalid-input` and no handler call; a spy handler asserts that.

- **Outcome mapping.** One test per row of §3.6, including:
  - advisory `PMS_TARGET_CAPABILITY_*` gives `success`;
  - explicit-targets `PMS_TARGET_CAPABILITY_INCOMPATIBLE` gives
    `constraint-violation`, never `unsupported-capability`;
  - `snapshot-disabled` gives `unsupported-capability` with
    `feature:accepted-snapshots`;
  - every `PMS_INVALID_REVISION` site in §1.3 carries a `reason` from the closed
    set. This is checked by iterating the reasons and triggering each one.
- **Cancellation.** Queue `check` behind a slow operation and abort the signal:
  the result is `cancelled`, the handler never runs, and nothing changes. Abort
  after the start: the result is the operation's real outcome.

### 5.3 Proof that the agent layer stays off the session path

The CE-00.3 session RSS headroom is tight: the gate failed by 0.54% on
`session.maxRssBytes`. PR 1 must show zero impact without running the perf gate.

- **(a) Structural test.** It builds each Rollup config whose input is
  `src/api/index.js`, `src/api/cli.js` or `src/api/host.js` through the Rollup
  JS API (`rollup()` and `generate()`, nothing written) and collects every
  output chunk's `modules` keys under `packages/compiler/src/`.

  The test asserts two things. No module under `src/agent/` and no
  `src/protocol/envelope.js` is present. The `src/` module set equals a
  committed **allowlist**, so any growth of the session entry's reachable graph
  needs a reviewed update.

  It is written as a **reusable test**, so the CE epic can extend it for its own
  modules:

  - a helper `reachableSourceModules(entry)`, kept next to the test in
    `packages/compiler/__tests__/pandamstyle/`;
  - a data file `reachability.v1.json`
    `{ entries: { "src/api/index.js": [...], ... }, forbidden: ["src/agent/**", "src/protocol/envelope.js"] }`.

  Adding an entry or a forbidden glob is a data change. Regeneration runs only
  under an explicit environment flag, and its diff is reviewed. The PR 1
  allowlist must equal the `f4e0a10` set exactly: every file PR 1 edits on the
  session path is already reachable, and no module is added.

  The mechanism was run for this note at `f4e0a10` (`modgraph.mjs`): `index.js`
  and `cli.js` each reach 98 `src/` modules and `host.js` reaches 1, with 0
  `agent/` and 0 `envelope.js` modules. The `protocol/` modules reached are
  `diagnostics.js`, `identities.js`, `diagnostics-result.js` and
  `diagnostics-result-v1.js`. Host adapters import only these bundles, so they
  are covered too.

- **(b) Byte delta.** Rebuild `lib/index.mjs` and `lib/cli.mjs` and report the
  size and SHA-256 against the base. The build is deterministic: two builds at
  `f4e0a10` gave identical hashes (observed). The base values are:

  | File            | Bytes   | SHA-256 prefix     |
  | --------------- | ------- | ------------------ |
  | `lib/index.mjs` | 842 703 | `8bf9ca0f105fed81` |
  | `lib/cli.mjs`   | 846 551 | `38907ea5a9e926ef` |

  The expected delta is the `project.js`, session and registry fixes (§7), about
  one to two kilobytes of source text. Any change to the module list fails (a).

- **(c) Local heap and RSS check.** Use a scratch script, not committed, in the
  same Node 22 for both builds (base `lib/` and PR `lib/`), alternating runs, 10
  runs each.

  Each run opens a session on the `valid` fixture and runs `initialize`,
  `validate`, `compile` and `close` in a fresh process with `--expose-gc`. It
  records `process.memoryUsage()` (`rss`, `heapUsed`) after `gc()`, and peak
  `rss` sampled between steps.

  Report the medians and the interquartile ranges. The expected result is no
  difference beyond run-to-run noise. A median `rss` increase larger than the
  base interquartile range, or any `heapUsed` increase above 64 KiB, counts as
  impact.

- **(d) A further run of (c) for the paging accessor.** After `compile`, call
  `diagnostics.affected` and `records.read` over every page, then `gc()`.
  Retained `heapUsed` must return to the pre-call value within the same 64 KiB
  threshold, showing that nothing is retained per call.

**Expected RSS effect of the session-path changes:**

- Two scalars per session (`designSystemCurrent`, `designSystemRevisionId`).
- No allocation in the `systemId` guard.
- No retained state for paging. The accessor allocates only when it is called,
  and neither validation nor compilation calls it.
- Lifecycle `reason` strings are allocated only on error paths.

The expected change in `session.maxRssBytes` is zero within noise. One runtime
change is visible but outside the measured path: while a definition stays

## 6. Self-attack: how this design could be wrong

- **AC1, schemas.** The closed subset may be too weak for a later operation, and
  pressure to add `pattern` or `anyOf` would reopen parity. Mitigation:
  extending the subset requires a generator update in the same change, and the
  parity tests fail otherwise.

  Effects are declared, not inferred: a handler could perform an undeclared
  effect. Mitigation: the iterated effect test observes files and tickets. It
  does not observe in-memory session state other than tickets and the verdict,
  which is a residual gap.

- **AC2, identities.** Removing the `systemId` fallback changes a public value
  from a string to `null` in failure cases. A consumer relying on a non-null
  string breaks. This is decided as a correction without a version bump, with
  the type fix and a changelog note (Q3).

  `projectId` itself defaults to an absolute path. It is kept, because the agent
  already has filesystem access (Q4).

- **I9, freshness (R1 class).** Ways the freshness design could still be wrong:

  - _A rebuild input outside the definition digest._ `engineOptions`, `roots`
    and `targets` go through `fallbackReason`, which also rebuilds. An input the
    session cannot observe is the caller's `fullFallback`. Mitigation: the
    hot-transition tests cover the definition and `targets`, and one more case
    covers `engineOptions`.
  - _A partial build that succeeds._ For example, the registry builds but code
    generation throws. `designSystemCurrent` is set only after the last
    assignment in `rebuildDesignSystem`, so any throw leaves it `false`.
    Mitigation: a fault-injection test throws at each `phase()` of the rebuild.
  - _A consumer reading the identity outside the facade._ Hosts use
    `readGeneratedArtifacts` and receipts, both of which go through the
    `current` check. The grep test also forbids direct `_designSystemIdentity()`
    use outside `project.js`.
  - _Retrying a failed rebuild on every revision costs CPU._ This is accepted as
    the price of not publishing a false acceptance, and it only applies while
    the definition is invalid.

- **I10, complete lists (R2 class).** Ways it could still be wrong:

  - _Another list cut inside the session before the v1 builder._ A grep for
    `slice(` in `session/index.js`, `protocol/*.js` and `api/project.js` found
    these cuts:

    - the affected list (session `:3780`);
    - candidate lists (`diagnostics-result.js:352`,
      `diagnostics-result-v1.js:138` and `:207`);
    - the `candidateTokens` page itself (session `:4270`).

    The other hits are path-string operations. Candidate domains are reachable
    through `diagnostics.candidates`. The grep covers `slice` only, not every
    possible truncation idiom. Mitigation: the exhaustive-paging test is driven
    by the §3.10 table, and a new list kind fails it until it gets a reaching
    operation.

  - _Recomputation that differs from what the result reported._ Mitigation: the
    count-parity assertion at every step.
  - _Paging cost on a global fallback (the whole project is affected)._ Each
    page call sorts the touched set again: O(n log n) CPU per call, and no
    memory retained. That is accepted.

- **I11, response size and retrievability (R3 and round-2 class).** Ways it
  could still be wrong:

  - _A frame component missed by the bound list_, for example a new v1 status
    field, or a host-provided string reaching the frame. Mitigation: `frameMax`
    is computed from the registry's output schemas. Every string schema in a
    frame position must name its source bound, and a schema without one fails
    registry load. A new field therefore cannot be unbounded silently.
  - _A record kind with no `records.read` address_, such as a future list.
    Mitigation: the §3.10 table and the address kinds are one closed list. The
    exhaustive-paging test iterates it, and a list kind without an address
    fails.
  - _Withholding hides the most important diagnostic._ The `withheld` entry
    keeps its `code` and `severity`, `ok` and the outcome are computed before
    projection, and the record is readable in full. A withheld record is never
    silently dropped.
  - _Addresses become ambiguous across revisions._ Every address is
    revision-bound, and the lists are deterministically ordered at one revision.
    Another revision is `stale-revision`.
  - _Escaped serialization changes the record._ Parsing it back gives the same
    value; the reassembly test asserts deep equality.
  - _The `systemId` bound rejects a project that worked before._ Every
    `systemId` string literal in the repository (97 of them, in `.js`, `.mjs`,
    `.ts` and `.md` files) has at most 26 characters (grep). The change is
    listed in the changelog.

- **I12, planned entries (R4 class).** The contracts of planned entries are
  written before their owners design them, so they may be wrong in detail. They
  are still binding on shape (closed inputs, one grant, effects within the
  grant). An owner who needs a different contract changes the registry entry,
  and the change is reviewed with its tests. A planned entry cannot stay vague,
  because the load-time rules reject vague entries.

- **AC3, capabilities.** An agent that can edit host code, such as
  `vite.config.ts`, can mint capabilities. This is outside the boundary by the
  epic's statement, and the note does not claim otherwise.

  The `WeakMap` check fails closed across duplicate module copies. That could
  surprise a host bundling two copies, but it is safe.

  The output lease mapped to `denied-access` might be confused with capability
  denial. `failure.reason` disambiguates, and tests pin it.

- **AC4, consultations.** The `check` reuse rule depends on the invariant "no
  live ticket without a current verdict". A future change to
  `preparePublication` could break it. The F1-class test (a ticket survives
  every consultation) guards it.

  `check` can still compute heavily (CPU). Resource fairness is AG-10.

  `diagnostics.candidates` reads the registry without validation, as
  `candidateTokens` does today, but only from a build that is current for the
  requested revision (§3.12). Without one it returns
  `constraint-violation: design-system-unavailable`. It never returns an older
  build's vocabulary under the new revision.

- **AC5, one meaning.** One dispatch path proves nothing about transports that
  re-serialize differently, for example MCP content blocks. That is deferred
  explicitly.

  `pms-build` keeps its own meaning until AG-02.5 and AG-13; the note does not
  claim parity for it.

- **I5, truncation.** A `references[]` entry could point to a page that no
  longer exists after a revision change. That case is defined as
  `stale-revision`, never an empty success.

- **I8, off-path.** Test (a) covers the published entries and hosts, not
  test-only bundles. (c) can miss allocation that occurs only under load; only
  the CI gate measures that, and the orchestrator decides whether to run it.
