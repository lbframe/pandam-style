# CE-01.2 design note: compiler-owned CSS transformation stage

Status: **accepted (`f768a49`) and implemented** on
`core-evolution/ce-01.2-transform`, with the orchestrator answers of
2026-10-20 (§9) and the implementation record of §10. Where §0–§8 and §10
differ, §10 describes the code. The host finding of §10.3 awaits an
orchestrator decision. Nothing here is a browser support claim.
Task: [#45](https://github.com/lbframe/pandam-style/issues/45), epic #39, base
`ed890ea` (CE-01.1, #44, PR #106). Follows the
[agent delivery protocol](../agent-delivery-protocol.md) rule 2: the note comes
before code and gets a short review.

Every claim is labelled:

- **[executed]**: observed by a command reported in §1;
- **[source]**: read in the source and not executed;
- **[unverified]**: neither; a check is planned.

## 0. Decision in brief

- **Option (a): no transformation dependency.** The data shows that the O13
  floor leaves one gap that a transformation can close without changing
  semantics: `user-select: none` on Safari and iOS Safari, where only
  `-webkit-user-select` ships. Every other gap is either already native or
  cannot be closed by a transformation that keeps computed cascade,
  inheritance and identity.
- **One rewrite class, with one entry.** A compiler-owned table of
  declaration-level *prefix aliases*. Each entry carries a committed proof. The
  stage takes no target input, so CSS bytes stay independent of targets, as in
  CE-01.1.
- **`transformed-with-proof`** is computed only for table entries.
- **Everything else** is native, or refused under enforced targets. The author
  may declare `degrade` for it, and `alternative-value` is re-deferred (Q2).
- **No layer lowering.** `@layer` is native at the O13 floor on every announced
  engine. `useCSSLayers` stays an application-owned `ProjectConfig` key.
- **Lightning CSS 1.33.0 is rejected.** It was executed on the probes (§3.2):
  - it rewrites colours that are native on modern engines;
  - it lowers `light-dark()` through the documented custom-property hack;
  - it rewrites `:dir(rtl)` to a `:lang()` list;
  - it adds a native binary per platform and a second compatibility source.

## 3. Options compared

### 3.1 (a) No dependency: native, refusal and a proven prefix table — **recommended**

Dependency cost: none. New compiler code:

- `targets/transforms.js`: one pure function over a rule text;
- `catalog/transforms.v1.json`: the table, one entry;
- an outcome rule;
- the fixtures of §6.

The table meets AC1 and AC2. It is also the mechanism that later lots use when
they admit `hyphens`, `mask-*` or `text-size-adjust`, and each of those entries
brings its own proof.

### 3.2 (b) Lightning CSS — rejected

Package facts **[executed]**:

- `lightningcss` 1.33.0 (2026-07-20), licence MPL-2.0.
- The JS package is 514 KB unpacked. It depends on `detect-libc` and selects
  one of 11 per-platform optional native packages; `linux-x64-gnu` alone is
  10.0 MB.
- The WASM alternative, `lightningcss-wasm` 1.33.0, is 16.2 MB.
- It is in `yarn.lock` today only as a dependency of `vite@8.3.1`, a host and
  dev dependency, not a compiler runtime dependency.

Effects on qualification:

- **New compiler runtime dependency.** The clean-archive installation would
  have to qualify native-binary selection (gnu vs musl, per OS and
  architecture) on the Node 22.12.0 and 24.21.0 consumer lanes.
- **Licences and donor closure.** It adds an MPL-2.0 file-level copyleft
  notice to the package closure. It is not a donor package for
  `donor-closure.js`, but it is the transformer StyleX's integration applies.
- **Second compatibility source.** It needs its own target encoding and
  feature data, which conflicts with O6 (only BCD 8.1.6).

Executed at the O13 floor (`chrome/edge/firefox 100`, `safari/ios_saf 15.4`,
`android 100`):

| Input | Output | Verdict |
| --- | --- | --- |
| `@layer p1, p2; @layer p2{…} @layer p1{…!important}` | The statement is dropped and the blocks are reordered p1, p2. No lowering | Semantics kept, bytes changed |
| `color: oklch(50% 0.1 30)` | `color:#944b40; color:lab(41.0964% 30.3829 21.1647)` | The native value becomes **lab** on every engine, and the old engines get an approximation: not equivalent |
| `--c: oklch(…)` | Hex value, plus an `@supports (color: lab(0% 0 0))` override | Gets past the custom-property limit, but the value is still approximate: a degrade |
| `light-dark(red, blue)` | `var(--lightningcss-light, red) var(--lightningcss-dark, #00f)`. `color-scheme` on the same unit gets `--lightningcss-*` and a `prefers-color-scheme` block | Without a `color-scheme` in the same unit, both fallbacks apply, and `red #00f` is invalid at computed-value time. Native `light-dark()` is replaced everywhere: **hazard confirmed** |
| `.a:dir(rtl)` | `.a:is(:lang(ae), :lang(ar), … :lang(yi))` | **Wrong semantics** (language ≠ direction) |
| `@media (width >= 600px)` / `(width > 600px)` | `(min-width:600px)` / `not (max-width:600px)` | Exact, but relies on MQ4 `not` (**[unverified]** at Chromium 100–103) |
| `@container (min-width:400px)` | `(width >= 400px)` | Rewritten toward range syntax; no help where queries are absent |
| `.a{&:hover{…}}` | Flattened | Correct, but the compiler never emits nesting |
| `user-select:none` / `mask-image` | `-webkit-` pair added | Correct, and the only useful output for our need |
| `color: oklch(from red l c h)` | `color:red; color:lab(…)` | Only a literal origin is computable; a `var()` origin is not |
| `float:inline-start` (with logical properties) | Unchanged, with declarations reordered | Its data treats Chrome 100 as supporting the value; BCD 8.1.6 says Chrome 118. The second source disagrees with the pin (O6) |
| `@property`, `:has()` | Unchanged | — |

Its one useful output for our needs, the `-webkit-user-select` pair, is the
table entry of option (a). Using it safely would mean disabling every other
feature, and each revision would still pay a full parse and print of the
stylesheet. That cost was not measured (no performance run on this host), and
the pass is not incremental.

### 3.3 (c) Other candidates — rejected

- **PostCSS 8.5.x plus Autoprefixer.** PostCSS is in the lockfile; Autoprefixer
  is not. Autoprefixer's data is caniuse-lite, a second compatibility source
  next to BCD, and it adds a full parse per revision, for one entry.
- **postcss-preset-env / csstools plugins** (`cascade-layers`, `logical`,
  `oklab-function`, `light-dark-function`, `color-mix-function`,
  `media-query-ranges`):
  - they reuse the lowerings rejected above: the specificity ladder,
    physical properties plus `[dir]`, sRGB approximations and the
    custom-property `light-dark` hack;
  - `css-has-pseudo` and `container-query-polyfill` need runtime JavaScript,
    which the runtime boundary forbids.
- **esbuild 0.27.7** (dev dependency): its CSS lowering approximates colours
  into sRGB, it has no BCD basis, and it has no proof hook.
- **`@property` default seeding** (`:root{--x:<initial>}`): changes where
  relative values compute and supplies no type validation. Rejected by
  deliverable 4.

## 4. The canonical stage

### 4.1 Placement and identity

One pure function, `applyTransforms(ruleText)`, is driven by
`transforms.v1.json`. It has no target, host, file or ordering input.

1. **Before.** Rule generation and ordering read the **untransformed** text, so
   the comparator, property priority and the specificity ladder are unchanged.
2. **Stage.**
   - `transformRuleEntry` (`engine/ordering/rules.js`) applies it to every
     entry of the complete ordered candidate.
   - The same function is applied to the unit texts that target extraction
     reads (`pageTargetSources`, the design system's injected rules,
     `intrinsicCss`).
   - The rewrite is closed over one declaration block. Applying it per rule is
     therefore equal to applying it to the complete candidate:
     `T(concat(rules)) = concat(map(T, rules))`.
   - A rewrite that needs other rules (any `light-dark` or `color-scheme`
     lowering) cannot be admitted to the table (invariant **T-local**).
3. **After.** The final `styles.css` text is built from the transformed entries.
   - `cssSourceMap` already maps the final text by its class selectors.
   - `createArtifactSet` hashes the final bytes (`artifacts.json` `sha256`,
     `artifactSetDigest`), and publication seals those digests.

The canonical identity is the compiler's `styles.css` bytes. The transform table
is compiler-bundled data, like the compat data. Its digest goes into the target
resolution `data` (`transformsDigest`), because outcomes depend on it.

### 4.2 The prefix-alias rewrite and its proof obligations

For an entry `{ property: 'user-select', variant: '-webkit-user-select' }`, a
declaration `user-select:V` becomes `-webkit-user-select:V;user-select:V`. The
pair has the same value and stays in the same block. The base comes last, so an
engine that parses both uses the standard form.

An entry is admissible only when all of the following hold:

1. On every announced engine at the O13 floor:
   - either the variant is an alias of the base property (same property,
     shared value subset), as CE-00.1 records with `vendor-legacy-variant`, not
     `divergent-legacy-variant`;
   - or it is the only form;
   - or it does not parse and is dropped at parse time.

   A renamed **value** (`-webkit-fill-available`) never qualifies.
2. The admitted values of the base are inside the shared value subset. For
   `user-select`, Alpha 1 admits only `none`.
3. A committed proof exists: a rationale, the fixture id and the executed
   evidence record ids (§6).

### 4.3 Hosts, minification and final assets (AC3)

Revised on 2026-10-20 by orchestrator decision `CE-01.2-Q6`, which replaces
the byte-identity rule of the accepted note.

- **Targets.** Targets come only from `ProjectConfig.targets`; CE-01.1 never
  reads `.browserslistrc`, `package.json#browserslist` or `BROWSERSLIST*`. The
  transform stage takes no targets, so no host option can change the canonical
  bytes: not Vite `build.cssTarget` or `css.lightningcss.targets`, not Rsbuild
  `output.overrideBrowserslist`, not Next browserslist.
- **Canonical identity.** The compiler's `styles.css` bytes are the only input
  of the canonical digests (`artifacts.json`, the artifact set and
  publication) and of the compiler's CSS source map.
- **Delivered CSS.** A host's delivered CSS must be *declaration-equivalent* to
  `styles.css`:
  - the same rules in the same order;
  - per rule, the same at-rule conditions;
  - per rule, the same selector set (the order inside one selector list may
    differ);
  - per rule, the same declarations in the same order, with the same values,
    including every vendor-prefixed pair.

  Whitespace, comments, final semicolons and selector-list order may differ,
  so minification passes. A host that drops, adds, merges, reorders or
  rewrites a declaration is redefining targets, and it fails AC3.
- **One normaliser.** `tools/pms/css-equivalence.cjs` builds the normal form
  from `@csstools/css-tokenizer` tokens. That tokenizer is a compiler runtime
  dependency, so it is present in every qualification consumer and no
  dependency is added. The block structure is read from tokens, never from a
  regex. The Vite pilot, Rsbuild and Next production qualifications record the
  result as `cssIdentity` through `tools/pms/host-css-identity.mjs`.
- **Host source maps.** A host's own source maps of its delivered CSS are the
  host's concern.
- **Vite's own minifier.** Vite 8.3.1 defaults to
  `build.cssMinify: 'lightningcss'` with `cssTarget` = `build.target` =
  `chrome111, edge111, firefox114, safari16.4, ios16.4` **[source]**. The
  adapter's raw asset bypasses it **[executed]**, see §10.3.

**Budgets (CE-00.3).**

- Timing: the stage adds one property-name check per emitted declaration in
  `transformRuleEntry` and one in the extractor, with no new parse pass. It is
  expected to stay inside noise but is **not measured**. With about 1.25
  cumulative headroom against alpha1, the CE-00.3 gate for the epoch runs on
  the dedicated measurement host, from a store copy, as for CE-01.1.
- Deterministic: `ce-corpus` mentions `userSelect` twice, so its CSS gains at
  most 2 declarations (budget 315 → limit 330) and about 50 bytes
  (14,612 → limit 15,342). This is an estimate from the workload source, to be
  measured. Option (b) would add an unmeasured full-stylesheet pass to every
  revision.

CE-01.1 deferral to CE-01.2 to be closed or re-deferred with an owning issue.
Proposed wording:

- **D-BP-07 (closed).** "Prefix emission is a compiler-owned,
  target-independent rewrite driven by
  `packages/compiler/src/targets/catalog/transforms.v1.json`. Version 1 holds
  one entry: a `user-select` declaration is preceded, in the same block, by
  `-webkit-user-select` with the same value. An entry requires that the variant
  is, on every announced engine at the O13 floor, an alias of the base, the
  only form or dropped at parse time. The admitted values must lie in the
  shared subset, and the entry needs a committed proof with executed evidence.
  Prefixed-only or renamed data without an entry stays `incompatible`. Renamed
  values such as `-webkit-fill-available` are not aliases."
- **D-BP-09 (closed).** "No third-party transformation dependency. The stage is
  one pure, declaration-local function applied to every entry of the complete
  ordered candidate and to the unit texts that target extraction reads. It runs
  after ordering and before `styles.css`, its source map and the artifact and
  publication digests. It takes no target input, so CSS bytes do not depend on
  targets. Lightning CSS 1.33.0, PostCSS plus Autoprefixer, postcss-preset-env
  and esbuild were evaluated and rejected
  (docs/architecture/ce-01.2-transformation-stage.md §3)."
- **D-BP-10 (closed).** "No layer lowering. `@layer` is native at the O13
  minimum on every announced engine. The `:not(#\#)` ladder is an intrinsic
  ordering mode, not an equivalent: unlayered CSS outside the compiler,
  `!important` reversal and `revert-layer` differ. `useCSSLayers` remains an
  application-owned `ProjectConfig` key in `SEMANTIC_CONFIG_KEYS`; hosts
  forward it unchanged and never default or rewrite it."
- **CE-01.2-T1 (impossible cases).** "No transformation is admitted for
  `light-dark()`, `@property` registration, `:has()`, container queries (size,
  style and units), relative colour, `color-mix()`, the
  `oklch`/`oklab`/`lab`/`lch`/`color()` functions, `:dir()`, cascade layers or
  logical properties. Each of these is native or refused per target, because
  no build-time rewrite keeps the computed value, inheritance and
  artifact identity on every engine served by the same bytes."
- **CE-01.2-T2 (fallback policy).** "Below support, a required feature is
  `incompatible`. It is an error under enforced targets and a warning under
  advisory. A design-system author may declare `degrade`, which is reported as
  degraded and never as equivalent. `transformed-with-proof` comes only from a
  transform-table entry. `equivalent-fallback` comes only from reviewed
  platform inapplicability, unchanged. `alternative-value` emission is
  re-deferred to CE-07.3 (#62), constrained to declaration level, never through
  a custom property, and reported as degraded."
- **CE-01.2-T3 (identity and hosts).** "The canonical identity is the
  compiler's `styles.css` bytes. A host's final asset is qualified only when it
  is byte-identical; host minification is outside the identity, and target
  facts attach only to canonical bytes."

## 10. Implementation record

### 10.1 What the code does

- **Stage.**
  - `packages/compiler/src/targets/transforms.js` holds `applyTransforms` and
    the table checks. The table is `catalog/transforms.v1.json`.
  - `transformRuleEntry` (`engine/ordering/rules.js`) applies it, and so do
    `renderCss` (`engine/lowering/styles.js`) and the texts that target
    extraction reads (`ownerGroupsOf` and the candidate check in
    `targets/evaluate.js`).
  - A rule without a table property costs one `includes` and returns the same
    string; nothing is allocated per declaration.
- **Outcome.**
  - The extractor reads `-webkit-user-select:v;user-select:v` (same value,
    same `!important`) as one construct, `property:user-select/prefix-alias`.
  - `featureOutcome` gives `transformed-with-proof` with the existing reason
    `transformation-proven` (not a new `prefix-alias` reason, as §5 proposed).
    It does so only where the base is incompatible or unknown and the
    variant's own statements are native at the floor. `proof` holds
    `{ transform, kind, variant, data }`.
  - `featureByKey` resolves the form key for package requirements.
  - Facts entries serialize `proof`, and `targets.data.transformsDigest` is
    added to the resolution record.
- **Floor tools.** `tools/targets/corpus-features.mjs` reads every input
  through the stage. `measure-floor.mjs` counts `transformed-with-proof` as
  acceptable, matching the CE-01.1 §5.1 policy.
- **Deferral.** `alternative-value` is refused with
  `context.deferredTo: "CE-07.3"`.
- **Hosts.**
  - `tools/pms/host-css-identity.mjs` records `cssIdentity` (`canonical`,
    `declaration-equivalent` or `non-equivalent`) in the Vite pilot, Rsbuild
    and Next production qualifications, through the shared normaliser.
  - Each qualification sets a host targets knob on a repeat build: Vite
    `build.cssTarget`, Rsbuild `output.overrideBrowserslist`, Next
    `package.json#browserslist`. The canonical artifacts must stay unchanged
    and, for Rsbuild and Next, the delivered CSS must stay
    declaration-equivalent. The Rsbuild and Next fixtures use
    `userSelect: 'none'`, so the pair is part of what they check.
- **Rsbuild adapter** (`packages/rsbuild/src/index.js`):
  - `excludeFromTargetLoaders` inserts a `oneOf` branch for the stylesheet just
    before Rsbuild's main `.css` branch. It is a copy of that branch without
    `builtin:lightningcss-loader` and PostCSS, and the `?url`, `?inline`,
    `?raw` and `with { type }` branches still match first.
  - `markStylesheetAssetsMinimized` (a `processAssets` hook at stage
    `optimize`) marks the CSS asset of every chunk holding the stylesheet as
    `minimized`, so Rsbuild's `LightningCssMinimizerRspackPlugin` (which
    applies the browserslist) skips it.
  - The asset stays where it was. A separate CSS chunk was tried and dropped:
    TanStack Start links CSS only through chunks that have JS files, so its SSR
    pages lost the styles.
  - Cost: other CSS in that same asset keeps its loader transforms but is not
    minified.
