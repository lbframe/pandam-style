Consequences, all **observed**:

- **Digest.** With and without every metadata key above, the registry digest is
  the same (`9943102e9adfe4a8`, P1).
- **Generated output.** Through the Project Service, the five artifacts
  (`design-module`, `declarations`, `manifest`, `css`, `artifact-metadata`) are
  byte-identical with and without metadata keys. No metadata string appears in
  any of them (P3).
- **Metadata-only edit.** On a live session, a definition edit that only adds
  metadata keys validates `ok: true`, and all five artifacts stay byte-identical
  (P3). The session detects the edit through `definitionDigest`
  (`project/session/index.js:233-245`, which hashes the whole definition), so
  the design system is rebuilt; semantic units hash registry records only
  (`index.js:536-612`), so no page is revalidated [source, unverified: rebuild
  and revalidation counts were not measured].
- **Hostile shapes.** A getter, a cycle, a symbol key and an 8 MiB string are
  all accepted and ignored by `buildDesignSystem`. Through the public session,
  the getter runs **once**, and the revision validates `ok: true`. The 8 MiB
  case completes in 48 ms (P4). **Correction (fix round 1):** round 0 attributed
  that call to `definitionDigest`. That was inferred, not observed. P6 records
  the calling frame: the call is made by `snapshotInput`
  (`api/project.js:53-81`, the read `value[key]` at l.78), synchronously when
  `createProjectSession` or `applyChanges` is called, before anything is queued.
  The getter's result becomes a plain data property in the copy, so no later
  stage can see that it was an accessor (§1.6). A cyclic definition is copied as
  a cyclic graph by `snapshotInput`'s `seen` map; `definitionDigest` then
  returns `null`, and the session falls back to object identity [fallback:
  source, unverified, `project/session/index.js:239-244`].
- **No repository definition uses `meta`.** A search of the `.js`, `.mjs`, `.ts`
  and `.tsx` files of `examples/`, `benchmarks/`, `tests/` and the package test
  directories for `meta:` finds one hit, `benchmarks/agentic/src/corpus.mjs:92`,
  which is a fixture record, not a definition. A search of the `.js` and `.mjs`
  files of `examples/` and `tests/fixtures/` for `description:` finds none
  (observed, `grep`).

The AG-03.1 deliverable "preserve metadata through normalization and flattening,
which currently discard descriptive information" therefore starts from total,
silent loss.

### 1.3 Private entities: representation and where they appear

`visibility: 'private'` exists on token leaves (`index.js:83`) and recipes
(`recipes/validate.js:181`). Themes, conditions and patterns have no visibility;
all of them are consumer-visible (P2: all appear in the manifest).

P2 searched for the private token id, the private alias id, the private recipe
id and two literal values used only by private tokens:

| Member or output                                                       | Private ids | Private literal values                                  |
| ---------------------------------------------------------------------- | ----------- | ------------------------------------------------------- |
| `snapshot.registry`                                                    | yes         | yes                                                     |
| `snapshot.vocabulary.tokens`, `snapshot.vocabulary.semanticTokens`     | yes         | `tokens` only (`resolvedValue`)                         |
| `snapshot.compiled`                                                    | token ids   | yes                                                     |
| `snapshot.tooling.manifest`, `candidateDomains`, `repairDomains`       | no          | no                                                      |
| `candidateDomainOf(snapshot, {})`, `repairDomainOf({ kind: 'token' })` | no          | no                                                      |
| `candidateDomainOf(snapshot, { allowPrivate: true })`                  | yes         | no                                                      |
| Generated design module                                                | no          | no                                                      |
| Generated declarations                                                 | no          | yes, as the value of the **public** alias `colors.text` |
| CSS                                                                    | no          | yes, as custom-property values (hashed names)           |

All rows are **observed** (P2). A consumer `create()` that names the private
token is rejected with `PMS_TOKEN_NOT_PUBLIC`, rule `visibility.consumer`, and
its candidates list only the public `colors.text` (P2).

So today "private" means **not selectable by consumers and absent from consumer
vocabulary projections**. It does not mean secret: a value that a public token
resolves to, and every value the CSS emits, is visible. The author-side members
(`snapshot.registry`, `snapshot.vocabulary.tokens`, `snapshot.compiled`) carry
private entities, and the consumer-side projections filter them. AG-03.1 keeps
that split and adds a third kind of data that must follow it.

**Where metadata could leak once it exists:**

1. Into an author-side member that a consumer projection later copies whole. For
   example, `defineRecipe` receives `...registry.recipes[recipeId]`
   (`registry/build-system.js:81-87`), so a `meta` field inside a recipe record
   would travel into the compiled recipe and the runtime projection.
2. Into compilation-identity hashes that serialize whole records: the registry
   digest payload (`index.js:456-472`, whole `tokens`, `themeOverrides`,
   `conds`, `recs`) and the `token:*` semantic unit (`session/index.js:547-550`,
   whole token record).
3. Into public metadata that names a private entity, as a structured reference,
   an example or free text.
4. Into diagnostics, which today echo author values without bound (§1.4), and
   which today name private entities to any reader (P7, observed): a cycle
   between two private tokens is `PMS_TOKEN_CYCLE` and names both, and a private
   recipe's invalid default is `PMS_INVALID_VARIANT_VALUE` and names the recipe,
   in the diagnostics returned by the public session's `validate()`. AG-01.1
   serves the same diagnostics to any `consult` caller through `check` and
   `records.read` (`address.kind: 'bootstrap'`).

### 1.4 Diagnostic echo today

Existing definition diagnostics copy author values into `context` and `message`
without bound. With a 100,000-character identifier (P5, observed):

| Case                                  | Code, rule                                       | Serialized diagnostic |
| ------------------------------------- | ------------------------------------------------ | --------------------- |
| Token `ref` to a missing token        | `PMS_UNKNOWN_TOKEN`, no rule                     | 200,279 bytes         |
| Duplicate slot names                  | `PMS_INVALID_RECIPE_SLOT`, `recipe.definition`   | 200,301 bytes         |
| Default variant value not in the axis | `PMS_INVALID_VARIANT_VALUE`, `recipe.definition` | 100,303 bytes         |

AG-01.1 handles such records by withholding them whole and serving them through
`records.read` (AG-01.1 §3.10), and CE issue #134 bounds identifier lengths.
Metadata diagnostics must not add a new instance of this class (§3.9).

## 2. Threat model

**Adversary.** The agent, and anything it can write. That includes the
design-system definition and therefore every metadata string, reference and
example in it. The author of the definition is not trusted to stay inside the
metadata contract. A consumer agent that only composes is a second party whose
view must not show private entities.

**Trusted.** The host process that loads the definition module and creates the
session. As in AG-01.1, evaluating the definition module is code execution the
host chose; this design does not sandbox it. Code that runs while the host
evaluates the module is inside that boundary, including a change the module
makes to a realm's global `Object.prototype` or `Array.prototype`. Author
behaviour that the **compiler** would trigger after the host handed it the
definition is not: an own or inherited getter, a coercion hook (`toJSON`,
`valueOf`, `toString`, `Symbol.toPrimitive`), a function value, a class instance
or other non-plain prototype. The compiler must not run author code that the
host did not already run, so ingress accepts only plain data and builds a copy
whose prototypes are this realm's intrinsics (§3.8.0). A `Proxy` is the one
residue: reading a shape runs its `getPrototypeOf`, `ownKeys` and
`getOwnPropertyDescriptor` traps during the copy, once per object or key. The
value copied is the one in the descriptor, so a trap cannot return one value to
validation and another to storage, and no trap runs after the copy.

**Assets.** Compiler authority over properties, values, visibility and
capabilities; the privacy of private entities in consumer views; the meaning of
declared metadata (no invented or altered meaning); compilation identity and
generated bytes; response sizes under the AG-01.1 bounds; host CPU and memory.

| #   | Threat                                                                                                                                                                                                                                                                                   | Required property                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | Metadata authorizes a forbidden property, value, token, recipe selection or capability: `restrictions: ['width may be 13px']`, `visibility` or `grants` inside `meta`, an example that uses a forbidden value                                                                            | No policy, engine, frontend, artifact or capability code reads metadata. ## 3. Design

### 3.1 Canonical storage: one side table, outside every compiled record

PR 1 adds one registry member, `registry.semantics`. It holds every validated
`meta` subtree of the definition, keyed by entity address (§3.4). It is the only
canonical location of metadata. Compiled records (`registry.tokens`,
`registry.recipes`, `registry.conditions`, the theme maps,
`registry.propertyDomains`) **never** contain a `meta` field.

```js
registry.semantics = {            // deep-frozen; name-keyed maps have a null prototype
  system?: SystemMeta,            // definition.meta, verbatim (may hold `patterns`)
  tokens:     { [tokenId]: Meta },
  themes:     { [themeName]: Meta },
  conditions: { [conditionName]: Meta },
  recipes:    { [recipeId]: RecipeMeta },   // verbatim (may hold `slots`, `variants`)
  propertyDomains: { [propertyKey]: Meta }, // after #132
}
SystemMeta = Meta & { patterns?: { [patternId]: Meta } }
RecipeMeta = Meta & { slots?: { [slot]: Meta },
                      variants?: { [axis]: { meta?: Meta, values?: { [value]: Meta } } } }
```

Each stored value is the author's `meta` at that position, verbatim after
validation. A key is present **iff** the author declared `meta` at that position
(`Object.hasOwn(record, 'meta')`). Child entities (slots, axes, values,
patterns) are present iff their key is present in the parent's child map; an
axis entry without its own `meta` key has no metadata of its own. The views
split a parent's own fields from its children (§3.10); storage does not.

Why a side table, checked against the threat model:

- **M9 by construction.** The registry digest payload is built from named
  members (`index.js:456-472`); `semantics` is not one of them, and no record in
  the payload gains a field. The `token:*`, `theme:*`, `recipe:*` and
  `conditions` semantic units hash records that do not change. The five
  generated artifacts read records, compiled refs and the manifest, none of
  which change. Inline `meta` would instead require every whole-record reader to
  strip it, and §1.3 lists three such readers today. Forgetting one would break
  M9, and for `defineRecipe` also M2.
- **M1 by construction.** Compilation receives `registry`, which now holds
  `semantics`, but no compile module reads that member. A structural test
  enforces this (§5.4).
- **M2.** One location means one consumer filter (§3.10).

**CE-02.1 `meta` contract.** CE-02.1 §9 reserves `meta` on each entity record,
defines its presence semantics and excludes "every `meta` subtree" from
compilation identity. This design keeps all three:

| CE-02.1 §9 commitment                                                                  | AG-03.1                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9.1 one reserved key, `meta`, per entity record; `propertyDomains` gains `meta` only   | The author key is `meta` at every supported position (§3.2). The `propertyDomains` entry schema gains exactly `meta`                                                                                                                                                                                                            |
| 9.1 `ENFORCED_FIELDS`; no policy or engine module reads `meta`                         | No effective property row ever has `meta`, so `ENFORCED_FIELDS` hashing is unaffected. The CE structural test is extended to `semantics` (§5.4)                                                                                                                                                                                 |
| 9.2 absent vs `{}`, copy rule `Object.hasOwn(entry, 'meta')`, fields inside `meta` too | Kept exactly, through normalization, `registry.semantics`, `snapshot.registry.semantics` and both views (§3.10). For a property domain, presence is observable as `Object.hasOwn(registry.semantics.propertyDomains, key)` and, when present, the stored value (`{}` or populated). The CE round-trip test lands in PR 1 (§5.1) |
| 9.2 "holds through … the effective table, `snapshot.properties`"                       | **Agreed with the CE owner (§3.1.1): presence semantics, not location.** Property-domain metadata lives in `registry.semantics.propertyDomains`, never in the normalized `propertyDomains` entries, the effective table or the `snapshot.properties` rows                                                                       |
| 9.3 `properties.digest` and `registryDigest` never include `meta`                      | Holds by construction (above)                                                                                                                                                                                                                                                                                                   |
| 9.4 excluded: every `meta` subtree                                                     | `registry.semantics` is the collection of the `meta` subtrees, so it is excluded. ### 3.2 Author syntax per entity kind

`meta` is recognized only at positions where it is not vocabulary today. Where
an author would plausibly write metadata but the position is vocabulary today,
`meta` is now an error rather than a silent reinterpretation (M10):

| Kind                  | Position                                           | Notes                                                                                                                                                                                           |
| --------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| system                | `definition.meta`                                  | Own fields, plus the `patterns` child map                                                                                                                                                       |
| token                 | the leaf object, beside `value` or `ref`           | A leaf is recognized as today (`index.js:59-65`); then `meta` is read from it. **Groups and categories take no metadata**, and a key `meta` in a group or category position is an error (below) |
| theme                 | `themes.<name>.meta`                               | Theme objects read only `extends` and `tokens` today                                                                                                                                            |
| condition             | `conditions.<name>.meta`, object form only         | The string form has no metadata (absent)                                                                                                                                                        |
| recipe                | `recipes.<id>.meta`                                | Own fields, plus `slots` and `variants` child maps                                                                                                                                              |
| slot                  | `recipes.<id>.meta.slots.<slot>`                   | Inline is impossible: `slots` is an array of names, and a `meta` key in a slot style map is a slot name                                                                                         |
| variant axis          | `recipes.<id>.meta.variants.<axis>.meta`           | Inline is impossible: `variants.<axis>.meta` is a variant **value** today (P1)                                                                                                                  |
| variant value         | `recipes.<id>.meta.variants.<axis>.values.<value>` | Inline would put `meta` in a style or slot map                                                                                                                                                  |
| pattern               | `definition.meta.patterns.<patternId>`             | Patterns are compiler-owned; the definition can describe them but not change them. Reserving a top-level `patterns` key is avoided, because CE-10 may need it                                   |
| property domain       | `propertyDomains.<key>.meta`                       | After #132 (§7)                                                                                                                                                                                 |
| application component | relation target only (§3.4)                        | Not an entity with its own metadata                                                                                                                                                             |

`metadata.unsupported-position` is raised, with a closed `reason`, for:

- `token-group`: a key `meta` in a token group, in `tokens` or in a theme's
  `tokens` overrides, whatever its value. Today
  `colors.brand.meta: { value: '#fff' }` silently becomes the token
  `colors.brand.meta` (P1), and an author who meant group metadata would get a
  token or a `PMS_FORBIDDEN_VALUE`. This was requested by the CE owner's review;
- `token-category`: a category named `meta` (`tokens.meta`), for the same
  reason, and to keep category metadata possible later;
- `theme-override-leaf`: a `meta` key on a theme override leaf
  (`themes.<name>.tokens.…`), which today would be silently dropped.

These are a breaking change for a definition that has a token path segment or a
category named `meta`. No repository definition has one (§1.2). PR 1's
`CHANGELOG.md` carries the migration note: rename the segment.

Other existing behavior is unchanged:

- style objects keep rejecting `meta` with `PMS_UNSUPPORTED_PROPERTY` (P1);
- a variant value or slot named `meta` stays vocabulary. No metadata is ever
  read at those positions (§3.2 table), so the name cannot be mistaken for
  metadata;
- unknown keys other than `meta`, such as a legacy `description`, stay silently
  ignored. That last case is CE-02.1 follow-up F4 ("reject unknown top-level
  definition keys"), not #12 scope.

Example:

```js
export default {
  systemId: 'acme-ui@1',
  meta: {
    description: 'Acme product UI vocabulary.',
    patterns: { stack: { usage: ['Vertical rhythm between sections.'] } },
  },
  tokens: {
    colors: {
      ink: { value: '#172033', visibility: 'private' },
      text: {
        primary: {
          ref: 'colors.ink',
          meta: {
            semanticRole: 'text-primary',
            description: 'Body and heading text on default surfaces.',
            terms: ['foreground', 'body-text'],
            examples: [{ property: 'color' }],
          },
        },
      },
    },
  },
  recipes: {
    button: {
      variants: { tone: { neutral: {}, danger: {} } },
      meta: {
        description: 'The only clickable action surface.',
        relations: [
          {
            relation: 'implemented-by',
            target: {
              component: { module: 'src/ui/Button.tsx', export: 'Button' },
            },
          },
        ],
        examples: [{ select: { tone: 'danger' } }],
        variants: {
          tone: {
            values: {
              danger: { usage: ['Destructive, irreversible actions.'] },
            },
          },
        },
      },
    },
  },
};
```

### 3.3 Field schema

Every `meta` object is **closed**: an unknown field is `metadata.unknown-field`.
This rejects authority-shaped fields (`visibility`, `grants`, `capability`,
`enforced`, `allow`, `role`) by the same rule as any typo (M1). Every field is
optional; nothing has a default (M4).

| Field               | Kinds                                                       | Type and bounds                                                                                                                                |
| ------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `semanticRole`      | all except system                                           | identifier: `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, 1–64 bytes. Author vocabulary; the compiler gives it no meaning                                   |
| `description`       | all                                                         | text (§3.7), 1–512 bytes                                                                                                                       |
| `usage`             | all                                                         | 1–8 texts, each 1–256 bytes; declared guidance on when to use the entity                                                                       |
| `restrictions`      | all                                                         | 1–8 texts, each 1–256 bytes; declared guidance on when not to use it. **Never enforced** (§3.10)                                               |
| `terms`             | all                                                         | 1–16 unique identifiers (same ASCII grammar as `semanticRole`, so an AG-04 lexical index needs no locale rules), each 1–48 bytes; search terms |
| `relations`         | all except system                                           | 1–16 unique `{ relation, target }` (§3.4)                                                                                                      |
| `examples`          | token, condition, recipe, pattern, property domain          | 1–4 examples (§3.6)                                                                                                                            |
| `deprecated`        | token, theme, condition, recipe, slot, axis, value, pattern | `{ reason?: text 1–256 bytes, replacement?: reference }`. Presence means deprecated. **Descriptive**: acceptance is unchanged                  |
| `patterns`          | system only                                                 | map from a `PATTERN_IDS` member to a pattern `Meta`                                                                                            |
| `slots`, `variants` | recipe only                                                 | child maps (§3.2), keys must be declared slots, axes and values                                                                                |

An empty array is rejected (`metadata.field-type`, reason `empty-array`): an
empty list and an absent field would otherwise be two encodings of "nothing
declared", and CE-02.1 §9.2 reserves only `meta: {}` for explicit emptiness.

**Child containers (fix round 1, finding R2).** The views split a parent's own
fields from its children (§3.10). A child container that holds no child would
then project exactly like an absent container: `{}` and `{ slots: {} }` give the
same recipe entry and no slot entry. The schema makes those states invalid, so
that every valid state has exactly one projection:

- `slots: {}`, `variants: {}`, `variants.<axis>.values: {}` and `patterns: {}`
  are `metadata.field-type`, reason `empty-map`;
- an axis entry with neither `meta` nor `values` (`variants.<axis>: {}`) is
  `metadata.field-type`, reason `empty-axis-entry`;
- explicit emptiness stays expressible at every level, and only one way: the
  child's own `meta: {}` for an axis, or `{}` as the child value for a slot, a
  variant value or a pattern.

Fields that are not split by the view (`deprecated`, an example's `select`,
`parameters`) keep `{}` as a value: they are projected verbatim, so `{}` is
unambiguous there (`deprecated: {}` means deprecated with no reason).

`deprecated` never adds a diagnostic to consumer code that uses the entity.
Usage warnings would change compilation results; they belong to AG-06.1 or a
follow-up, not to #12.

### 3.4 Entity addresses and references

**Address.** Every entity is addressed by a closed object whose fields are
declared names, never a delimiter-joined string. Recipe, slot, axis and value
names may contain `.` or `/` (`safeName`, `recipes/validate.js:16-19`), so a
joined string would be ambiguous.

```js
{ token: 'colors.text.primary' }
{ theme: 'dark' }                 { condition: 'wide' }
{ recipe: 'button' }              { recipe: 'card', slot: 'root' }
{ recipe: 'button', variant: 'tone' }
{ recipe: 'button', variant: 'tone', value: 'danger' }
{ pattern: 'stack' }              { property: 'width' }      // property domain
{ component: { module: 'src/ui/Button.tsx', export: 'Button' } } // relation target only
```

The same shape is used as a reference inside metadata (`relations[].target`,
`deprecated.replacement`) and as `context.entity` in diagnostics. The planned
AG-01.1 `describe` input (`{ kind, id }`, AG-01.1 §3.9) cannot address slots,
axes, values or property domains unambiguously. AG-03.2 adopts this address
shape through a reviewed registry change.

**Resolution rules** (each failure is one diagnostic, §3.9):

1. The target exists: a declared token, theme, condition, recipe, slot, axis or
   value, a `PATTERN_IDS` member, or a property with a `propertyDomains` entry.
   Otherwise `metadata.unknown-reference`.
2. **Visibility.** If the source entity is consumer-visible, the target is too.
   Otherwise `metadata.private-reference` (M2). A private source may reference
   anything.
3. No reference to the source entity itself (`metadata.self-reference`).
4. `relation` is one of `related`, `pairs-with`, `alternative` or
   `implemented-by`. `implemented-by` takes exactly a component target;
   component targets take only `implemented-by` (`metadata.reference-kind`).
5. **Component targets.** `module` is a project-relative POSIX path of 1–256
   bytes, with no leading `/`, no `\`, no `.` or `..` segment, no URL scheme,
   and text rules (§3.7). `export` is an ECMAScript `IdentifierName` or
   `default`, 1–128 bytes. **Existence is not checked** in AG-03.1: the registry
   build reads no project file, and adding a file read would make a definition's
   validity depend on the source tree. Views label component targets as declared
   and unverified (§3.10). This was decided by the orchestrator (Q1, §8).

`relations` may form cycles: `a pairs-with b` and `b pairs-with a` is
meaningful. Replacements may not (§3.5).

### 3.5 Deprecation and replacement

`deprecated.replacement` follows the rules of §3.4, plus:

- **Same kind.** A token is replaced by a token **of the same category**, a
  recipe by a recipe, a slot by a slot of the same recipe, an axis by an axis of
  the same recipe, a value by a value of the same axis, and likewise for themes,
  conditions and patterns (`metadata.replacement-kind`, with `expectedKind`,
  `actualKind` and, for tokens, `reason: 'category'`). A replacement in another
  category would point at something that the same property rejects.
- **Acyclic.** Each entity has at most one replacement, so the replacement graph
  is a functional graph. An iterative walk with three colors finds every cycle
  in O(entities) without recursion (no stack overflow on a 10,000-entity chain).
  Each cycle is reported once, on its smallest address in canonical
  serialization order, as `metadata.replacement-cycle` with `cycleLength` and
  the first 16 addresses of the cycle, walked from that smallest address. A
  self-replacement is a cycle of length 1.
- A chain that ends at a deprecated entity is allowed: `a → b`, `b` deprecated
  with no replacement. Views report only declared edges; the compiler never
  computes a "final" replacement, because that would be invented meaning (M4).

### 3.6 Examples, verified by compilation

Examples are **structured JSON data**, never source text. Nothing is parsed or
executed. A token reference inside an example is the object
`{ token: '<path>' }`. The validator turns it into a compiler-kind reference
(`mintTokenRef`, `design-system/tokens/ref.js`) before compilation.

| Kind            | Example shape                                               | Compiled as                                                                                           |
| --------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| token           | `{ property, condition? }`                                  | `{ [property]: ref(this token) }`, or under the named condition in the consumer style form            |
| condition       | `{ property, value }`, `value` a JSON scalar or `{ token }` | the value under this condition                                                                        |
| property domain | `{ value }`                                                 | `{ [this property]: value }`                                                                          |
| pattern         | `{ parameters }`, values JSON scalars or `{ token }`        | `createPatternIR(patternId, parameters, { refKind: 'compiler' })`, then its declarations              |
| recipe          | `{ select?: { [axis]: value }, slot? }`                     | the runtime selection rules of `@pandamstyle/core` over the compiled recipe spec, plus `slot ∈ slots` |

**Role and visibility.** A consumer-visible entity's example compiles with
`role: 'consumer'` and `allowPrivateTokens: false`, exactly like page code. A
private token or private recipe's example compiles with `role: 'system'`, as the
design system's own styles do (`build-system.js:64-76`). So a public example
that uses a private token fails with the unchanged `PMS_TOKEN_NOT_PUBLIC` (M2),
and a forbidden property or value fails with the unchanged policy diagnostic
(M1).

**No feedback.** Examples run through `compileStyles` directly, never through
`create()`, which would merge rules into the generation
(`build-system.js:93-105`). The compiled result is discarded after its
diagnostics are read. An accepted example adds no rule, no token, no domain
member and no candidate (M1, M9).

**Where it runs.** `buildDesignSystem`, after token compilation (examples need
`varsByToken`, `build-system.js:51-59`) and recipe compilation (recipe examples
need the compiled spec, `build-system.js:78-91`), and before the snapshot.
Reference and schema validation run earlier, in `buildRegistry`, and their
errors stop the build at the existing check (`build-system.js:47-49`), so
examples are only compiled for a definition whose metadata is otherwise valid.
Example diagnostics are collected for all examples, then thrown together by a
second check of the same form placed before the snapshot.

A failure is `metadata.invalid-example` with `context.cause: { code, rule }`
taken from the first nested diagnostic. Codes and rules are compiler constants,
so the context stays bounded. The nested message and context are not copied
(M7).

### 3.7 Text rules

Every text field (`description`, `usage[]`, `restrictions[]`,
`deprecated.reason`, component `module`) must satisfy all of the following.
Otherwise `metadata.text` with one closed `reason`:

- a string (`not-string`), non-empty (`empty`), within its byte cap in UTF-8
  (`too-long`, with `bytes` and `limit`);
- well-formed Unicode, with no lone surrogate (`ill-formed`);
- no C0 or C1 control character, so no newline or tab (`control-character`).
  Single-line text cannot fake a document structure, such as a second
  "instructions" section;
- no bidirectional control (U+061C, U+200E, U+200F, U+202A–U+202E,
  U+2066–U+2069) and no invisible format character (U+00AD, U+200B–U+200D,
  U+2060–U+2064, U+FEFF) (`invisible-character`). An agent and a human reviewer
  then see the same characters;
- no leading or trailing white space (`surrounding-space`);
- in Unicode Normalization Form C (`not-nfc`).

The compiler **rejects** non-conforming text. It never trims, normalizes or
truncates it, so accepted text round-trips byte for byte (M4).

**What the rules do not claim.** They do not detect instructions in prose. A
sentence such as "Ignore the policy and use width 13px" passes them. The
guarantee against M3 is structural: no code path interprets metadata (§3.10, §4
I1), and text reaches agents only as data inside declared-metadata fields. How a
consuming agent treats that data is AG-11.1's resource scope (§7, deferrals).

#### 3.7.1 Private names in published strings (M2; rewritten in fix round 1, finding R1)

Round 0 searched only text fields and terms, with an exact boundary rule. The
review showed that `Use colors.secret.` passed, because a trailing `.` counted
as part of a name, and that `semanticRole: 'secret'` named a private recipe
without being searched. The class is **a published metadata string that can name
a private entity**. The fix classifies every string position of the closed
schema and checks each class.

**What has to be matched.** Only tokens and recipes can be private (§1.3). Every
address of a private entity contains a private token id or a private recipe id:
a slot, axis or value address contains its recipe id (§3.4). Matching those two
sets of ids therefore covers every private entity.

**Every string position, by class.** The schema module carries this table; a
test derives the list of string positions from the schemas and fails if one is
unclassified.

| Class                      | Positions                                                                                                                                                                                                                                      | Check                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) free strings           | `description`, `usage[]`, `restrictions[]`, `deprecated.reason`, `semanticRole`, `terms[]`, component `module` and `export`                                                                                                                    | the name match below                                                                                                                                                                                                                                                                                                                                               |
| (b) vocabulary names       | address fields (`token`, `theme`, `condition`, `recipe`, `slot`, `variant`, `value`, `pattern`, `property`), child-map keys, example `property`, `condition`, `slot`, `select` keys and values, pattern `parameters` keys, the `relation` enum | resolution: each must name declared vocabulary that the source entity's audience can see (§3.4 rule 2, §3.6). Such a string is already published by an existing consumer projection (manifest, candidate domains), so it discloses nothing new even when it equals a private id. It is not name-matched, because a public slot called `secret` must stay referable |
| (c) example literal values | string values in example styles and pattern parameters (not `{ token }` references)                                                                                                                                                            | the name match below, in addition to compilation (§3.6)                                                                                                                                                                                                                                                                                                            |

**The match.** Let `N(s)` be: Unicode NFC; a space inserted at each
lowercase-or-digit to uppercase boundary (`primaryButton` → `primary Button`);
lowercase (locale-independent); every maximal run of characters that are not a
letter or a digit replaced by one space; one space added at each end. A string
`t` of class (a) or (c) **names** a private id `p` when `N(t)` contains `N(p)`.
So `colors.secret`, `colors.secret.`, `Colors/Secret!`, `COLORS_SECRET`,
`colors . secret` and `primary button` (for `primaryButton`) all match.
`colors.secretive` and `primary-buttons` do not: a letter or digit extending the
last word makes a different word. All of these cases were executed on a model of
the rule (P8).

A match is `metadata.private-identifier`, with `context.privateKind` (`token` or
`recipe`) and the field path (§3.9), but **not** the private id. The diagnostic
must not repeat what it protects.

**What is guaranteed, precisely.** For every consumer-visible entity, no class
(a) or (c) string of its stored metadata contains, under `N`, the full id of a
private token or private recipe as a whole-word sequence. Class (b) strings name
only consumer-visible vocabulary. The structured guarantees (references,
examples, view filter: I4) do not depend on this check.

**What is not guaranteed** (the residual):

- paraphrase ("the hidden ink colour");
- a partial path, such as the last segment `secret` of `colors.secret`. Matching
  segments would reject most prose, because segments like `md` and `text` are
  common words;
- inflection by letters (`primary-buttons`);
- confusable characters (Cyrillic `е` for Latin `e`), which NFC does not fold;
- a name split across two strings, or encoded (base64, spelling out).

Each of these is a deliberate disclosure by an author who controls the
definition and could equally make the entity public. The check catches
references written as names, including with different punctuation and case.

**False rejections.** A private recipe whose id is a common word (`secret`)
makes that word unusable in public free text. The repair is explicit in the
diagnostic: rephrase, or rename the recipe. This is preferred to a false
acceptance, because AC3 is a privacy criterion.

**Cost.** `N(p)` of every private id is a sequence of at most `w` words. Each
normalized string is scanned once, looking up every window of 1 to `w` words in
a hash set. That is O(words × w), not O(bytes × ids). PR 1 measures it on the
synthetic maximal fixture (§5.5).

Private literal values are not matched. §1.3 shows that values are not secret:
CSS and public tokens expose them, and a value such as `8px` appears in ordinary
prose.

### 3.8 Input snapshot

#### 3.8.0 Definition ingress: accepted shapes, fixed prototypes (fix rounds 1 and 2, findings R3 and R2-1)

§1.6 shows that every public path copies the definition with `snapshotInput`,
which reads `value[key]` and so runs each getter once, at call time, and stores
its result as plain data. A check placed after that copy cannot see the
accessor. Round 1 fixed own accessors only. Review round 2 (R2-1) showed that a
descriptor copy that **keeps the source prototype** still lets inherited
behaviour run after ingress: an inherited token `value` getter ran 3 times, and
an inherited `toJSON` getter on metadata ran once, through the public session's
`initialize`/`validate`, and neither was rejected (reviewer's model
`/tmp/ag031-r2-ingress-model.cjs`). The class is **author-supplied executable
behaviour reachable after ingress**: own or inherited getters, `toJSON`,
`valueOf`, `toString`, `Symbol.toPrimitive`, Proxy traps and non-plain
prototypes. It is fixed by accepting a closed set of shapes and building a copy
whose prototypes are fixed by construction.

**Accepted shapes.** `snapshotDefinition` (in
`design-system/registry/ingress.js`) accepts exactly:

- primitives: string, number, boolean, `null`, `undefined`;
- **plain objects**: prototype `null`, or the `Object.prototype` intrinsic of a
  realm. All own keys are strings, and each is an enumerable data property;
- **arrays**: `Array.isArray`, prototype the `Array.prototype` intrinsic of a
  realm. The own keys are `length` and integer indexes below it, each a data
  property. Holes are kept as holes: they hold no behaviour;
- **`token()` marks**: an object whose only own key is
  `Symbol.for('pandamstyle.tokenRef')`, holding a string data value.

"Intrinsic of a realm" is checked from descriptors only: the prototype's own
`constructor` is a data property holding the native `Object` (or `Array`)
function, whose own `prototype` data property is that same prototype, and an
`Object.prototype` has a `null` prototype. A look-alike such as
`Object.create({ constructor: Object })` fails. This accepts plain objects from
another realm (a `vm` context, Jest's `structuredClone`), which are idiomatic,
and the repository evidence below needed it.

**Everything else is rejected**, on its first occurrence, with a `PmsError`
carrying one diagnostic: `PMS_INVALID_DEFINITION` (#135), phase `design-system`,
rule `definition.shape`, `context: { field, reason }`. Reasons are closed:

| `reason`                 | Shape                                                                                                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accessor`               | an own getter or setter, including on `meta` itself                                                                                                                         |
| `prototype`              | any other prototype: a class instance, an object with an inherited getter, `toJSON` or `Symbol.toPrimitive`, `Date`, `Map`, `Set`, `RegExp`, boxed primitives, typed arrays |
| `function`               | a function value, which covers own `toJSON`, `valueOf` and `toString` methods                                                                                               |
| `symbol-key`             | a symbol-keyed property other than a `token()` mark, which covers own `Symbol.toPrimitive`                                                                                  |
| `symbol-value`, `bigint` | a symbol or bigint value                                                                                                                                                    |
| `non-enumerable`         | a non-enumerable own string key, which destructuring would read but `Object.keys` would not                                                                                 |
| `array-shape`            | an array with an own key other than `length` and its indexes                                                                                                                |
| `token-mark`             | a `token()` mark whose value is not a string data property                                                                                                                  |
| `unreadable`             | a `Proxy` trap throws while the shape is read                                                                                                                               |

`field` is the path from the definition root. Schema keys (`tokens`, `meta`,
`value`, `visibility` …) appear by name; author-named segments appear as
`{ index: n }`, their position among the parent's own keys. No author name is
echoed, because at ingress the compiler does not yet know which names are
private (§3.9.1).

**The copy.** Every object is copied into a fresh `{}` and every array into a
fresh `[]` of this realm, with `Object.defineProperty` (so an own key named
`__proto__` stays an own key and never sets a prototype). Every value comes from
an own data descriptor, so the copy **never performs `[[Get]]`** on the source
and never reads the source prototype beyond the identity check above. A
`token()` mark is copied as a fresh frozen mark. Cycles and shared references
are kept, as `snapshotInput` kept them. Once copied, the definition contains
only plain data with this realm's intrinsic prototypes and `token()` marks, so
nothing the author wrote can run when a later stage reads, hashes
(`definitionDigest`) or serializes it.

**Proxy.** A Proxy cannot be detected, and its descriptor-level traps
(`getPrototypeOf`, `ownKeys`, `getOwnPropertyDescriptor`) run **during the
copy**, once per object or per key. The copied value is the one in the
descriptor that the engine completed from the trap's result, so a trap that lies
on a second read is never consulted twice. The copy is Proxy-free, so no trap
runs after ingress. This is the residue stated in §2.

**Where it applies.** It replaces `snapshotInput` at the three definition copy
sites: `resolveConfig` (`api/project.js:105`), `resolveConfigChanges` (l.180),
and in `snapshotMutation` (l.220-221) both `transaction.definition` and the
`definition` member of `transaction.config`. The rest of `config`, as well as
`engineOptions`, `targets` and operation options, keeps `snapshotInput`
(follow-up, §7).

**Effect on the paths of §1.6.** `createProjectSession` and `applyChanges` fail
**during the call**, before anything is queued, exactly where today's
`snapshotInput` runs. No session is created by a failing `createProjectSession`,
and no revision by a failing `applyChanges`. This is the failure point of the
existing synchronous input checks (the `TypeError`s of `resolveConfig` and
`applyChanges`), with a structured diagnostic instead. A rejected shape is a
definition error the author can repair, so it is a `PmsError`, not a
`TypeError`.

**Why reject, rather than copy a value.** A getter or coercion hook can return
different values to two readers, and whether it runs at all is the property the
compiler owes the host (§2, Trusted). Copying own data while silently dropping
inherited members would change the definition's meaning without notice.
Replacing a hook with a marker reported later was rejected: the marker would
have to change the session's `definitionDigest`, or a later edit could be taken
for no change. Rejection keeps the session untouched.

**Internal callers** (§1.6, last row) receive copies made by the public facade,
or come from the private test bundle. `snapshotMetadata` below keeps its own
descriptor-first reading as defense in depth for them.

#### 3.8.1 Metadata snapshot

Metadata is read once, by a single function, `snapshotMetadata(value, caps)`,
into frozen plain data. Validation and storage use that copy (M8):

- Accepted values: plain objects (prototype `Object.prototype` or `null`), dense
  arrays (prototype `Array.prototype`, no extra own keys), strings, finite
  numbers other than `-0`, and booleans.
- Each own key is inspected with `Object.getOwnPropertyDescriptor` **before**
  reading it. An accessor property is rejected without being invoked
  (`metadata.malformed`, reason `accessor`). On the public paths, §3.8.0 has
  already rejected every accessor, so this branch is reachable only from
  internal callers.
- Rejected (`metadata.malformed`): symbol keys (this covers `token()` objects;
  the message names the `{ token: '<path>' }` form), non-enumerable own keys,
  functions, `undefined`, `bigint`, holes, depth above 12, and any object seen
  twice on the current path (cycle). The deepest valid path is 11 levels: a
  recipe value's component target
  (`meta.variants.<axis>.values.<value>.relations[i].target.component.module`)
  or a pattern example's conditional parameter.
- Byte budgets (§3.8.2) are counted while copying. Copying stops at the first
  cap overrun, so a hostile 8 MiB string is measured, not copied.

#### 3.8.2 Size bounds (M6)

Sizes are measured in the AG-01.1 canonical serialization: JSON with sorted keys
and every non-ASCII character escaped as `\uXXXX` (AG-01.1 §3.10).

| Bound                                       | Default     | Diagnostic                                     |
| ------------------------------------------- | ----------- | ---------------------------------------------- |
| One entity's own `meta` (children excluded) | 4,096 bytes | `metadata.too-large`, `{ bytes, limit }`       |
| All metadata of one definition              | 1 MiB       | `metadata.total-too-large`, `{ bytes, limit }` |

The per-field caps of §3.3 apply first. Rationale:

- **Response bounds.** The AG-01.1 record ceiling is 8 KiB in `compact` and 64
  KiB in `detail` (AG-01.1 §3.10). 4 KiB of metadata leaves at least half a
  compact record for the entity address and the enforced facts AG-03.2 adds. A
  record that is still too large is withheld whole and readable through
  `records.read`, as AG-01.1 already guarantees. The cap prevents metadata from
  being the reason a record is withheld; it is not needed for correctness.
- **Memory.** The total cap bounds what metadata adds to each retained design
  system. That matters for the CE-00.3 peak-RSS budgets (#122).
- **Headroom.** No repository definition has metadata today (§1.2), so there is
  no corpus to size from. PR 1 measures a maximal synthetic definition and
  confirms or lowers the defaults before freezing them, as AG-01.1 did for its
  ceilings.

Identifier lengths in addresses are bounded by CE #134, not here (§7).

### 3.9 Diagnostics

One new code, `PMS_INVALID_METADATA`, with `phase: 'registry'`,
`severity: 'error'` and one rule per class:

| Rule                                             | Raised when                                                                                                                      |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `metadata.malformed`                             | §3.8 shape violations, with closed `reason`                                                                                      |
| `metadata.unsupported-position`                  | `meta` where §3.2 does not support it                                                                                            |
| `metadata.unknown-field`                         | a field outside the closed schema of that kind                                                                                   |
| `metadata.field-type`                            | wrong type, out-of-range count, duplicate, bad identifier grammar, empty array, empty child container or empty axis entry (§3.3) |
| `metadata.text`                                  | §3.7, with closed `reason`                                                                                                       |
| `metadata.too-large`, `metadata.total-too-large` | §3.8.2                                                                                                                           |
| `metadata.unknown-child`                         | `slots`, `variants`, `values` or `patterns` key not declared                                                                     |
| `metadata.unknown-reference`                     | §3.4 rule 1                                                                                                                      |
| `metadata.private-reference`                     | §3.4 rule 2                                                                                                                      |
| `metadata.self-reference`                        | §3.4 rule 3                                                                                                                      |
| `metadata.reference-kind`                        | §3.4 rule 4, and component path or export grammar                                                                                |
| `metadata.replacement-kind`                      | §3.5                                                                                                                             |
| `metadata.replacement-cycle`                     | §3.5                                                                                                                             |
| `metadata.invalid-example`                       | §3.6                                                                                                                             |
| `metadata.private-identifier`                    | §3.7.1                                                                                                                           |

The definition-level ingress error of §3.8.0 uses `PMS_INVALID_DEFINITION`, rule
`definition.shape`, because it concerns the whole definition, not metadata. It
follows the same context and audience rules.

**Context, bounded by construction (M7).** `context` holds only:

- `entity`: the entity whose `meta` is at fault, in the audience-safe form of
  §3.9.1. Errors are attributed to the most specific entity: a slot's error
  names the slot, not its recipe;
- `field`: the path inside that entity's own `meta`, made of closed field names
  and array indexes, for example `['relations', 2, 'target']`. A map key the
  author chose (an undeclared child key, for `metadata.unknown-child`) appears
  as `{ index: n }`, its position among the map's own keys. **No author string
  appears in `field`** (changed in fix round 1: round 0 put child names in it);
- rule-specific closed enums and integers: `reason`, `bytes`, `limit`,
  `expectedKind`, `actualKind`, `privateKind`, `cycleLength`, `cause`, and for
  `metadata.replacement-cycle` the list `cycle` of at most 16 entities, each in
  the audience-safe form.

It never holds a metadata value: no text, no term, no reference target, no
example value. `message` is a compiler template that interpolates only the names
that §3.9.1 allows. `source` is the constant `design-system` for every metadata
diagnostic. It never carries an entity path such as
`design-system:recipes.<id>`, which the existing recipe diagnostics use
(`recipes/validate.js:29`). The author can read the offending value at the
`field` path of their own definition.

Names of consumer-visible entities are author identifiers. CE #134 records the
identifier limits (about 128 to 256 bytes per kind) in one place; metadata
diagnostics, and the metadata caps of §3.8.2, reference those limits rather than
restate them. Until #134 lands, an oversized diagnostic is withheld and served
by AG-01.1 `records.read`. That is the existing class (§1.4), which #134 also
takes over for the existing diagnostics that echo values.

#### 3.9.1 Audience-safe diagnostics (fix round 1, finding R5)

Round 0 put a private entity's address in `context.entity`. Bootstrap
diagnostics reach any `consult` caller through AG-01.1 `check` (the listing) and
`records.read` with `address.kind: 'bootstrap'` (the full record). The class is
**diagnostics as a private-entity leak channel**. The fix is at the source: a
diagnostic introduced by PR 1 is built in its safe form, so every path that
carries it carries only that form. This covers the raw SDK `validate()`,
`check`, `records.read`, the formatted CLI output and host overlays. No path
needs a redaction step it could forget.

**The safe default** (the only form produced in PR 1):

- An entity is shown by its address only if it is **consumer-visible**: a public
  token; a public recipe and its slots, axes and values; a theme; a condition; a
  pattern; a property domain; the system.
- A private token, a private recipe, or a slot, axis or value of a private
  recipe, is shown as `{ kind, visibility: 'private', ordinal }`. `ordinal` is
  the entity's 0-based rank among the private entities of the same `kind` that
  have an own `meta` key, ordered by the canonical serialization of their
  addresses. It is a pure function of the definition, so it is deterministic
  across sessions and needs no stored state.
- `message` names no private entity. `field` holds no author string (above).
  `metadata.private-reference`, `metadata.private-identifier` and
  `metadata.unknown-reference` never carry the target (§3.4, §3.7.1).
- `definition.shape` (§3.8.0) is raised before visibility is known, so its
  `field` shows every author-named segment as `{ index: n }`, whoever owns it.

**What the safe form still discloses:** that private entities of a kind exist,
how many of them have metadata, and the faulty entity's rank among them. It
discloses no name, no value and no metadata.

**Detailed identities, for authors.** An author agent holds the definition
source. It can map `{ kind, ordinal }` back by the documented order. PR 1 adds
an in-process function, `resolvePrivateEntity(definition, safeEntity)`,
returning the address. It is not exported from any package entry and is
reachable from no operation. Serving detailed diagnostics to a caller belongs to
AG-03.2, behind the author capability it defines with AG-01.1 (§3.10). The safe
form is the default for every caller without that capability, and it stays the
default if AG-03.2 serves nothing more.

**Scope of the fix.** It covers every diagnostic that PR 1 introduces:
`PMS_INVALID_METADATA` and `definition.shape`. Existing definition diagnostics
also name private entities (P7: `PMS_TOKEN_CYCLE`, `PMS_INVALID_VARIANT_VALUE`,
observed). They are not introduced by #12, and changing them changes codes owned
elsewhere. They are filed as a follow-up (§7), with the instances found.

**Every error is reported.** Metadata validation does not stop at the first
error, unlike the throwing token and theme checks (`index.js:132-166`). An agent
can then repair all metadata in one pass. To avoid cascades, an entity whose
`meta` fails the snapshot or schema stage gets no reference, text or example
check, and a reference to it is still resolved against the declared vocabulary,
not against its metadata. Each diagnostic is bounded, and AG-01.1 pages the
list.

**Outcome.** A metadata error is a definition error. The revision has no current
design system and reports `constraint-violation` with `stage: bootstrap`
(AG-01.1 §3.6, §3.12). Each diagnostic carries
`repair: { kind: 'edit-design-system-definition', applicable: false, … }`,
following the CE-02.1 `domainError` convention (#132 `policy/domains.js`),
because no page-role repair edits the definition.

**Why errors and not warnings.** A warning that dropped invalid metadata would
serve a definition whose declared meaning differs from its source, and an agent
could not tell dropped metadata from metadata that was never declared (M4, M5).
An error keeps one definition, one verdict, as for `propertyDomains` and
`enhancements`. The cost is that a metadata mistake blocks the build until it is
fixed. §6 records this.

### 3.10 Views and round-trip

PR 1 adds one projection module, `design-system/semantics/views.js`, with
`semanticsViewOf(snapshot, { audience })`. AG-03.2 builds its projections on it,
and AG-03.2's `describe` serves it. PR 1 serves it through no operation.

```js
{
  kind: 'pandamstyle-semantics-view', schemaVersion: 1,
  audience: 'consumer' | 'author',
  designSystem: { systemId, registryDigest },
  componentTargets: 'declared-unverified',   // constant, §3.4 rule 5
  entities: [                                 // canonical address order
    { entity: <address>, visibility: 'public' | 'private',
      origin: { entity: 'definition' | 'compiler', meta: 'definition' },
      meta?: <validated meta, verbatim> },    // key absent iff undeclared
  ],
}
```

- **Consumer audience.** Lists only consumer-visible entities: public tokens,
  public recipes with their slots, axes and values, every theme, condition and
  pattern, every property domain, and the system. Metadata validation already
  guarantees that no listed `meta` references, exemplifies or names a private
  token or recipe (§3.4, §3.6, §3.7.1). The filter is the only step; nothing is
  redacted. As defense in depth, the view re-checks every reference against
  visibility. A failure is an internal error, never a silent drop, and a test
  proves the path unreachable (§5.3).
- **Author audience.** Lists every entity, private ones included. It is not
  reachable from any consumer-facing output in PR 1. Which host grant selects it
  belongs to AG-03.2 with AG-01.1 capabilities. The recommendation is: the
  audience comes only from the capability, never from request data, and a
  request may narrow author to consumer but never widen.
- **Enforced vs declared.** In the view, `meta` holds declared metadata and
  nothing else. Enforced facts (visibility, category, axes, admitted values)
  come from compiler records. AG-03.2 adds them beside `meta`, never inside it,
  so `restrictions` can never be mistaken for policy.
- **Parents and children.** A recipe entry's `meta` holds the recipe's own
  fields, without `slots` and `variants`; each slot, axis and value is its own
  entry. Likewise the system entry omits `patterns`, and each pattern is its own
  entry.
- **The projection is injective on valid states (fix round 1, finding R2).**
  Round 0 projected `{}` and `{ slots: {} }` identically, and likewise for
  `patterns`, `variants` and an axis's `values`. The class is **a projection
  that is not injective on declared states**. With the schema rule of §3.3 (no
  empty child container, no empty axis entry), the stored value is rebuilt from
  the entries:

  - `slots`, `patterns` or an axis's `values` is present iff at least one of its
    children has a `meta` key in the view;
  - `variants.<axis>` is present iff the axis entry has `meta` or one of its
    values does;
  - the parent's own fields are its entry's `meta`.

  Every valid state therefore has exactly one projection, and every state that
  would collide is rejected by the schema. On a model of the schema and the
  split (P9, observed), the 88 distinct recipe `meta` states with containers
  absent, empty or populated at each level give 52 rejected and 36 valid. The 36
  valid states round-trip exactly with no two projections equal. Without the
  schema rule, 46 states collide.

- **Entities without metadata** are listed with no `meta` key in the consumer
  view, so that "nothing declared" is explicit for every vocabulary entity. The
  view never synthesizes a description, role, term or relation (M4).

**Round-trip guarantee (AC1).** For every supported position:

- if the definition has no own `meta`, `registry.semantics` has no key for it
  and the view entry has no `meta` key;
- if the definition has `meta: {}`, both hold a frozen empty object;
- otherwise the stored value's canonical serialization (§3.8.2) equals that of
  the author's `meta`, and the view entries rebuild it exactly (above). Arrays
  keep author order. Strings and numbers are unchanged. No field is added,
  removed or reordered within arrays.

A definition with any metadata error has no snapshot, so it cannot round-trip a
partial or altered value.

### 3.11 Serving through the AG-01.1 registry and envelope

PR 1 adds no operation and changes no operation contract. The interactions with
AG-01.1 are:

- **Bootstrap.** `PMS_INVALID_METADATA` diagnostics are bootstrap failure
  records. They are listed by `check` and readable by `records.read` with
  `address.kind: 'bootstrap'`, unchanged. Both carry the safe form of §3.9.1,
  because the record is built safe at its source; neither operation needs a
  redaction step. Their context is bounded (§3.9). With #134's identifier limits
  in place, none should be withheld in `compact`; PR 1 asserts the bound against
  those limits.
- **Identity.** A metadata-only edit leaves `registryDigest` unchanged (M9). The
  revision identity still changes, and AG-01.1 binds every project-dependent
  response to the exact revision, so a metadata answer is never stale under an
  unchanged digest. AG-03.2 adds the discovery digest that CE-02.1 §9.3 makes
  room for.
- **Descriptions.** AG-01.1 T12 says descriptions in the operation registry are
  compiler-authored constants. That stays true: metadata text never enters an
  operation's `summary`, an envelope `failure`, or a diagnostic `message` or
  `context`.
- **`describe` (AG-03.2).** It serves `semanticsViewOf` entries as list records
  under the AG-01.1 size rules, with the address shape of §3.4.

### 3.12 Interaction with CE descriptors and session units

- **Property descriptors** (#126 `policy/descriptors.js`) are compiler data.
  AG-03.1 adds no compiler-authored metadata to them (M4). A future
  compiler-authored description would carry `origin.meta: 'compiler'` and is out
  of scope.
- **`propertyDomains`** (#132). `normalizePropertyDomains` accepts `meta` as an
  additional member. An entry still needs at least one domain member: an entry
  holding only `meta` fails CE's existing rule for an entry without members. The
  function hands the raw value to the metadata snapshot and keeps it out of the
  normalized entry. The normalized entry is in the registry digest payload (#132
  `index.js` ~l.489) and must stay `meta`-free.
- **Session.** The design system is rebuilt on a metadata-only edit (§1.2). No
  semantic unit reads `semantics`, so no page is revalidated, and no artifact
  byte changes. PR 1 tests both with the parse counter of `session-helpers.js`.
  Skipping the rebuild itself is AG-03.2 ("skip CSS recompilation for
  metadata-only changes only where independence is established").

### 5.4 Structural test

The test extends CE-02.1's "no policy or engine module reads `meta`" test. No
module under `engine/`, `policy/`, `frontend/`, `artifacts/`, `targets/`,
`agent/`, `project/` or `packages/core/` reads a `semantics` member or a `meta`
property (`import.meta` is a different syntax node and is ignored). The only
modules that may read either are `design-system/semantics/**` and the extraction
sites: `registry/index.js`, `recipes/validate.js`, `registry/build-system.js`

imports with the Babel parser the compiler already uses; it does not rely on a
text search. `policy/domains.js` is allowed only for its
`normalizePropertyDomains` hand-off, so the test checks the function, not just
the file.

## 6. Self-attack: how this design could be wrong

1. **The side table could diverge from the CE-02.1 text.** Resolved in fix round
   1: the CE owner agreed in writing, and #138 amends the CE note (§3.1.1). The
   remaining risk is that #138 does not merge as written. The PR 1 tests of §5.1
   assert the agreed behavior, so a divergence shows up as a failing test, not
   as silent drift.
2. **Prose can still carry a private name the match does not cover.** The
   residual is stated in §3.7.1: paraphrase, partial paths, inflections,
   confusables, split or encoded names. Only an author who controls the
   definition can produce them, and that author could make the entity public.
   The privacy guarantee for structured data rests on I4's resolution rules. The
   reverse error, false rejection, occurs when a private id is a common word.
   The repair is explicit.
3. **Errors could be too strict.** A typo in a description blocks every build of
   the project until it is fixed. The alternative, dropping with a warning,
   violates M4 and M5 (§3.9). If agents find this costly in AG-00 measurements,
   a later issue can add a reviewed "metadata degraded" state. #12 does not.
4. **Existing definition diagnostics still name private entities.** The
   diagnostics PR 1 introduces are safe at the source (§3.9.1). Existing codes
   (P7: `PMS_TOKEN_CYCLE`, `PMS_INVALID_VARIANT_VALUE`) are not. Until the
   follow-up lands, a private name can still reach a consumer through those
   codes. That channel exists today, and #12 does not widen it.
5. **Component references are unchecked.** A wrong module path is accepted. The
   view labels it `declared-unverified`, so no agent is told it exists. This was
   decided by the orchestrator (Q1, §8).
6. **Example semantics could drift from page semantics.** The token example's
   condition form and the recipe example's selection must use exactly the
   consumer paths. PR 1 must call the same functions (`compileStyles` with
   `role: 'consumer'`, `createPatternIR`, the core selection rules), not
   re-implement them. A test compiles each accepted example as page code through
   `compileFile` and expects the same verdict.
7. **The caps are unmeasured.** The defaults in §3.3 and §3.8.2 come from the
   AG-01.1 record ceiling, not from real metadata. §5.5 measures them before
   they are frozen.
8. **The round-0 inventory was wrong about who runs the getter.** It named
   `definitionDigest`, by inference. P6 shows `snapshotInput` runs it, on every
   public path, during the call (§1.6). The fix is at that site (§3.8.0).
   `definitionDigest` would still run a getter for an internal caller that skips
   the facade. No published entry does that (§1.6), and for those callers
   `snapshotMetadata` still rejects accessors inside metadata.

9. **The ordinal discloses counts.** The safe form tells a consumer how many
   private entities of a kind carry metadata, and the rank of the faulty one. A
   salted handle would hide the count, but it would not be reproducible across
   sessions. Deterministic diagnostics were preferred, and the disclosure is
   stated (§3.9.1).
10. **The shape rule is broader than metadata, and could reject an idiomatic
    definition.** A definition with a getter, a function, a class instance, a
    `Date` or any other non-plain object anywhere now fails, not only in `meta`;
    `snapshotInput` used to copy `Date`, `RegExp`, `Map` and `Set`. Copying
    values while dropping inherited behaviour would change meaning silently, and
    a marker reported later would need a session change (§3.8.0). The risk of
    false rejection was measured, not assumed: 0 of 26 standalone definitions
    and 0 of 790 definition passages in the compiler suite are rejected (P10,
    P11). The first model's same-realm check did reject cross-realm plain
    objects, which is why the rule accepts the intrinsics of any realm. Host
    suites were not instrumented (§3.8.0). The changelog states the change.
