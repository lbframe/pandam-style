# CE-01.1 design note: browser targets and capability outcomes

Status: **design proposal for review, not implemented.** Nothing in this note
is a shipped API or a support claim. Names, paths and fields below are
proposals that become binding only once this note is accepted and implemented.
Task: [#44](https://github.com/lbframe/pandam-style/issues/44), epic #39, base
`e2a864b`. Follows the [agent delivery protocol](../agent-delivery-protocol.md)
rule 2.

## 1. Source facts this design starts from

Each fact below was inspected in the source at `e2a864b`; none was executed.

- The compiler has no browser-target concept. `@mdn/browser-compat-data`
  appears nowhere. `browserslist` 4.28.0, `caniuse-lite` and
  `baseline-browser-mapping` appear in `yarn.lock` only transitively, through
  Babel. The root `package.json` already overrides `baseline-browser-mapping`
  with `resolutions`, which shows that a consumer can swap data under a
  dependency.
- The project configuration is `ProjectConfig` (`types/index.d.ts:12-24`),
  normalized in `project/session/index.js` `normalizeConfig`. Unknown keys are
  dropped silently. Vite and the Next coordinator forward an explicit
  allowlist. Rsbuild spreads its input through.
- `SEMANTIC_CONFIG_KEYS` (`designSystemFile`, `engineOptions`, `useCSSLayers`)
  trigger a counted full fallback (`compiler-configuration`). The per-file
  validity key and `fresh.js` take `engineOptions` and `useCSSLayers`.
- The compiler itself emits target-sensitive CSS whatever the source:
  - `@layer` blocks when `useCSSLayers` is set;
  - otherwise a `:not(#\#)` specificity ladder (`engine/ordering/rules.js:673`);
  - custom properties for tokens;
  - `@property` for typed tokens.

  Condition definitions are raw strings (`registry/index.js:413-441`). They
  can carry `:has()`, `@container`, `@supports` and media features verbatim.
- The canonical snapshot (`registry/snapshot.js`) has `identity`,
  `capabilities`, `registry`, `vocabulary`, `compiled` and `tooling.manifest`.
  The constants are ABI 1, `pms-0.1` and manifest schema 1. `artifacts.json`
  and core's `GeneratedIdentity` hard-check these identity fields.
- Registry 1,108 entries carry BCD 8.1.6 data at **property level only**.
  - 35 entries reference D-BP-06, 10 reference D-BP-07 and 3 reference
    D-BP-03.
  - The 101 `obsolete-engine-prefix` entries belong to CE-01.
- The CE-00.2 corpus (840 declarations) exercises these contexts:
  - selectors `:focus-visible`, `:dir()`, `::file-selector-button`;
  - media features `prefers-reduced-motion`, `forced-colors`,
    `prefers-contrast`, `pointer` and `hover`.

  It does not exercise `:has()`, containers, layers, `@property`, anchors,
  scopes or view transitions.

## 2. Target configuration contract

### 2.1 Where it lives

| Concern                                             | Owner                                                         | Surface                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Which engines an application announces              | Application (project)                                         | `ProjectConfig.targets`; host plugin options forward the same plain object  |
| Which features are optional enhancements, with what fallback | Design-system author                                  | New definition field `enhancements` (§5.2)                                  |
| What a reusable package requires                    | Compiler (computed)                                           | Manifest `targetRequirements` (§6, D-BP-13); a package never declares targets |

Targets are a property of the application, not of the design system. One
design system may serve applications with different targets. Consumer (page)
source can never change targets or policies.

### 2.2 Shape (proposed)

```ts
interface TargetConfig {
  // Named profiles the application announces. All must pass.
  profiles: readonly ProfileRef[];          // e.g. ['pandamstyle:default@1']
  // Project-defined profiles, referenced as 'project:<name>'.
  define?: Readonly<Record<string, ProfileDefinition>>;
}
type ProfileRef = `pandamstyle:${string}@${number}` | `project:${string}`;
interface ProfileDefinition {
  // Exactly one of the following three:
  extends?: ProfileRef;                     // built-in base, narrowed only upward
  engines?: Readonly<Partial<Record<EngineId, string>>>; // exact floors, e.g. { safari_ios: '17.4' }
  browserslist?: string;                    // restricted subset, §2.3
  electron?: string;                        // exact Electron version, e.g. '44.7.2'
}
type EngineId = 'chrome' | 'chrome_android' | 'edge' | 'firefox'
  | 'safari' | 'safari_ios' | 'webview_android';
```

Built-in, versioned profiles:

| Profile                        | Contents                                                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `pandamstyle:default@1`        | Modern evergreen web, desktop and mobile, frozen from the corpus as described in §3; includes `safari_ios`     |
| `pandamstyle:ios-safari@1`     | `safari_ios` only, at the default floor; for iOS-only applications                                             |
| `pandamstyle:electron@1`       | Electron, with the floor taken from the announced desktop consumer (D-BP-03)                                     |
| `pandamstyle:android-webview@1` | Opt-in only, not part of the default (Q4)                                                                      |

A profile id is immutable. Changing floors means `@2`; `@1` never changes
meaning. When `targets` is absent, the project gets `pandamstyle:default@1`,
and provenance records `origin: "default"` (Q9).

### 2.3 Deterministic resolution

Resolution is a pure function of three inputs:

- the `targets` value, canonicalized with the existing `stableJson`;
- the compiler-bundled compat data module (§2.4);
- the built-in profile records.

It never reads any of the following:

- environment variables (`BROWSERSLIST`, `BROWSERSLIST_ENV`, ...);
- `.browserslistrc` or `package.json#browserslist`;
- the clock;
- the network;
- a consumer-installed `browserslist` or `caniuse-lite`.

**Recommended (Q1): no Browserslist at compile time.** The compiler parses only a
restricted, finite query subset itself:

- `<browser> >= <version>`;
- `<browser> <version>`;
- comma-joined combinations of those two forms.

Browser names follow Browserslist spelling (`ios_saf`, `and_chr`,
`android`, `electron`). Each is mapped to a BCD browser id by a committed table.

Every other term is rejected with `PMS_INVALID_TARGET_CONFIG` and
`rule: targets.query.nondeterministic`. Rejected terms include:

- usage-based terms (`> 1%`, `cover`);
- relative terms (`last N versions`, `last N years`, `since`);
- data-dependent terms (`dead`, `defaults`, `unreleased`, `supports`);
- indirection (`extends`, `browserslist config`).

Accepting old target syntax promises nothing (deliverable 1). An `ie 11` term
parses, then resolves to the incompatibility disposition in §2.5.

Output: one **target resolution record** (`kind:
"pandamstyle-target-resolution"`, `schemaVersion: 1`):

```json
{
  "kind": "pandamstyle-target-resolution",
  "schemaVersion": 1,
  "digest": "sha256:…",
  "provenance": {
    "origin": "project-config",
    "inputDigest": "sha256:…",
    "ambientSourcesConsulted": []
  },
  "data": {
    "bcd": { "version": "…", "commit": "…", "digest": "sha256:…" },
    "browserslist": { "version": "…" },
    "caniuseLite": { "version": "…" },
    "electronToChromium": { "version": "…" },
    "generator": { "path": "tools/targets/build-compat-data.mjs", "digest": "sha256:…" }
  },
  "profiles": [
    {
      "ref": "pandamstyle:default@1",
      "origin": "builtin",
      "definitionDigest": "sha256:…",
      "engines": [
        { "engine": "safari_ios", "floor": "…", "basis": "declared" },
        {
          "engine": "chrome",
          "floor": "…",
          "basis": "derived-from-electron",
          "electron": "44.7.2"
        }
      ]
    }
  ]
}
```

- `origin` is one of `project-config` or `default`.
- `ambientSourcesConsulted` is always empty, and a test asserts it.
- In the `browserslist` and `caniuseLite` data entries, the version is the one
  the generator used for release lists and the Electron mapping.
- An engine's `basis` is one of `declared`, `derived-from-electron` or
  `profile-floor`.

Engines are sorted, floors are exact strings, and no field depends on time or
host. Every `…` is filled from executed resolution, never written by hand.

### 2.4 Pinned compat data

`tools/targets/build-compat-data.mjs` generates a committed module,
`packages/compiler/src/targets/data/compat-data.v1.json`, which is
compiler-owned and never edited. It runs from exact devDependency pins:

- `@mdn/browser-compat-data`;
- `browserslist` and `caniuse-lite`, used only for release lists;
- `electron-to-chromium`.

It also uses the BCD source checkout at the pinned commit. The published BCD
package resolves `"mirror"` statements, so only the source shows which
`safari_ios`, `edge`, `chrome_android` and `webview_android` statements are
mirrored.

The data is restricted to the BCD paths that the feature catalog (§4.1)
references. It contains each statement's raw fields:

- `version_added` and `version_removed`;
- `partial_implementation`, `prefix`, `alternative_name` and `flags`;
- a digest of `notes`;
- `mirrored`.

A CI check regenerates the module and requires byte identity. Because the data
is bundled into compiler `lib/`, consumer `resolutions` cannot substitute it.
A data refresh is an explicit compiler change. It moves every target digest
and is reviewed as a new epoch.

The pinned BCD version is the comparator (8.1.6) unless refreshing is decided
at implementation. The refresh is recorded either way (issue: "refresh exact
upstream identities").

### 2.5 IE and obsolete engines (D-BP-05)

These engines resolve to `PMS_INCOMPATIBLE_TARGET_ENGINE` (error, `rule:
targets.engine.obsolete`), and the project fails to configure:

- Internet Explorer (`ie`, `ie_mob`);
- legacy EdgeHTML (`edge` < 79);
- Presto Opera (`opera` ≤ 12.1, `op_mini`, `op_mob` ≤ 12.1);
- KHTML.

An engine that has no data entry, or a floor below the compiler's intrinsic
floor (§3), fails with `rule: targets.engine.unsupported-floor`.

The 101 `-ms-`, `-o-` and `-khtml-` registry entries get catalog records with
`recognition: not-admitted`. Their outcome is `incompatible`, with reason
`obsolete-engine` (LIM-05), on every profile. Nothing is silently dropped from a
profile.

## 3. Freezing the default profile from the corpus

The numbers come from the corpus and the data, never from upstream headlines.
Panda's FAQ floor and StyleX's Lightning CSS defaults are neither inputs nor
expected values.

1. **Feature set F.** Run the catalog extractor (§4.3) over two inputs:
   - every CE-00.2 corpus declaration in the profiles `web`, `content`,
     `forms` and `data`, using `accounting.v1.json` declarations, their
     contexts and the fixture stylesheets;
   - the compiler's **intrinsic emission features** under default
     configuration: custom properties, the `:not(#\#)` ladder,
     `@layer` (statement and block, only as a separate `useCSSLayers` variant)
     and the condition/at-rule wrappers that the engine emits.
2. **Per-engine minimum.** For each feature f and announced engine e, take the
   earliest version with full support: unprefixed, unflagged, not partial and
   without an unreviewed caveat (§4.2). The data in §2.4 is the only input.
3. **Floor.** `floor(e)` is the maximum over F of that minimum. The tool
   records the binding features that set each engine's floor.
4. **Floor exceptions.** A feature with no full-support version for some e
   cannot set a floor. It is listed as an exception and needs a reviewed
   decision before the freeze. The options are:
   - an optional enhancement with an author fallback;
   - an approved equivalent with proof;
   - an engine limitation recorded in the profile.

   Examples to expect include `forced-color-adjust` in Safari and `ruby-*` in
   some engines.
5. **Freeze.** `tools/targets/measure-floor.mjs` writes
   `packages/compiler/src/targets/profiles/default.v1.json`. It contains:
   - the floors, binding features and exceptions with their decisions;
   - the corpus manifest digest;
   - the data digest.

   A check rederives the file and requires identity, so the floor cannot
   drift from its inputs. **The measured table goes to the orchestrator for
   decision before the freeze commit.** Floor-binding versus enhancement
   choices are product decisions.

Features outside F, such as `:has()`, containers, anchors, view transitions,
`@scope`, typed `@property` or `text-wrap: pretty`, never raise the default
floor. Each is evaluated against the frozen floor and is either
`native`, or must be an author-declared enhancement, or fails the profile.

## 4. Capability record schema

### 4.1 Feature catalog (`pandamstyle-feature-catalog`, v1)

The catalog is a finite set of feature keys, compiler-owned and authored as
reviewed data under `packages/compiler/src/targets/catalog/`. Each key has its
own BCD path or paths. A key never borrows its parent's data.

| Kind              | Key form                                     | Examples (non-exhaustive; the list closes D-BP-08)                                                                                                                                                         |
| ----------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `property`        | `property:<name>`                            | `property:text-wrap`, `property:mask-image`, `property:anchor-name`, `property:view-transition-name`, `property:view-transition-class`, `property:container-type`                                       |
| `value`           | `value:<property>/<keyword>`                 | `value:text-wrap/balance`, `value:text-wrap/pretty`, `value:text-wrap/stable`, `value:display/<multi-keyword>`, `value:width/min-content`, `value:width/fit-content`, `value:width/stretch`, `value:container-type/scroll-state` |
| `function`        | `function:<name>[/<context>]`                | `function:color-mix`, `function:light-dark`, `function:fit-content/width`, `function:anchor`, `function:anchor-size`, relative color syntax                                                               |
| `color-space`     | `color-space:<name>`                         | `oklch`, `oklab`, `lab`, `lch`, `color()` spaces, with color-mix interpolation spaces as separate keys                                                                                                       |
| `unit`            | `unit:<unit>`                                | `cqw`/`cqh`/`cqi`/`cqb`/`cqmin`/`cqmax`, `dvh`/`svh`/`lvh` families, `lh`/`rlh`                                                                                                                         |
| `selector`        | `selector:<pseudo>`                          | `selector:has`, `selector:focus-visible`, `selector:dir`, `selector:is`, `selector:where`, `selector:not-complex`, `selector:file-selector-button`, `selector:view-transition-*` pseudo-elements      |
| `at-rule`         | `at-rule:<name>[/<kind>]`                    | `at-rule:layer/statement`, `at-rule:layer/block`, `at-rule:container/size`, `at-rule:container/inline-size`, `at-rule:container/style`, `at-rule:container/scroll-state`, `at-rule:property`, `at-rule:scope`, `at-rule:starting-style`, `at-rule:position-try`, `at-rule:view-transition`, `at-rule:supports/selector` |
| `media-feature`   | `media:<feature>[/<value>]`                  | `media:prefers-reduced-motion`, `media:forced-colors`, `media:prefers-contrast`, `media:pointer`, `media:hover`, `media:any-pointer`, `media:prefers-color-scheme` (D-BP-11)                              |
| `descriptor`      | `descriptor:<at-rule>/<name>`                | `descriptor:property/syntax`, `descriptor:property/inherits`, `descriptor:property/initial-value`                                                                                                        |
| `api`             | `api:<name>`                                 | `api:same-document-view-transition`, `api:cross-document-view-transition`. These are native API dependencies (LIM-04), recorded but never implemented by CSS                                            |
| `platform`        | `platform:<engine>/<name>`                   | `platform:electron/-webkit-app-region`, `platform:electron/-webkit-user-drag`, `platform:electron/-webkit-font-smoothing` (D-BP-03, LIM-07)                                                              |
| `combination`     | `combination:<key>+<key>[+…]`                | Only catalogued interaction hazards, for example `function:light-dark` without `color-scheme`, `at-rule:layer/block` with `!important`, `unit:cq*` outside a container context, `value:transition-behavior/allow-discrete` with `at-rule:starting-style` |

### 4.2 Record and outcome

A **catalog record** keeps the compiler side and the browser side apart:

```json
{
  "feature": "value:text-wrap/pretty",
  "kind": "value",
  "parent": "property:text-wrap",
  "bcd": ["<exact BCD path, validated to exist in pinned data>"],
  "recognition": {
    "status": "not-admitted",
    "contexts": [],
    "ownerLot": "CE-06"
  },
  "transformations": [],
  "equivalents": [],
  "caveats": [
    {
      "engine": "safari",
      "noteDigest": "sha256:…",
      "disposition": "unreviewed",
      "review": null
    }
  ],
  "evidence": []
}
```

- `recognition.status` is one of `admitted`, `recognized` or `not-admitted`.
  `ownerLot` names the lot that admits the feature.
- `transformations` and `equivalents` stay empty until a proof exists. Each
  entry will be `{ id, engines, proofFixtureId }`. Transformed outputs come
  from CE-01.2.
- `caveats[].disposition` is one of `unreviewed`, `irrelevant`, `blocking` or
  `restricts`.
- Each `evidence` entry will be
  `{ class: "E3" | "E4", fixtureId, engine: { id, version, build, device }, result }`.
  The array stays empty until executed.

A **per-target outcome** is computed and never authored:

```json
{
  "feature": "value:text-wrap/pretty",
  "profile": "pandamstyle:default@1",
  "engine": "safari_ios",
  "floor": "…",
  "state": "incompatible",
  "reason": "support-after-floor",
  "basis": "compat-data-mirrored",
  "proof": null
}
```

The state is one of the five:

- `native`
- `transformed-with-proof`
- `equivalent-fallback`
- `incompatible`
- `unknown`

The reason is a finite enum:

- `full-support-at-floor`
- `support-after-floor`
- `no-support`
- `prefixed-only`
- `flagged-only`
- `alternative-name-only`
- `partial-implementation`
- `unreviewed-caveat`
- `blocking-caveat`
- `removed-before-latest`
- `no-data`
- `ranged-data`
- `preview-only`
- `engine-not-in-data`
- `unrecognized-construct`
- `obsolete-engine`
- `platform-scoped`
- `transformation-proven`
- `equivalent-proven`

The basis is one of:

- `compat-data`
- `compat-data-mirrored`
- `derived-from-electron`
- `executed`

The outcome function is total and evaluated per (feature, engine, floor), in
order:

1. If the construct was not recognized, the outcome is `unknown` with reason
   `unrecognized-construct`.
2. A `platform:*` feature in a profile that lacks the platform is
   `incompatible` with reason `platform-scoped`.
3. Statements applicable at the floor give `native` only when the support is
   full: unprefixed, unflagged, not partial and not removed between the floor
   and the latest release in the data. Every caveat on that engine must also
   be `irrelevant`.
4. Otherwise, a proven transformation gives `transformed-with-proof`, and a
   proven equivalent gives `equivalent-fallback`.
5. Otherwise, positive data showing absence (`version_added: false` or a later
   version) gives `incompatible`. Missing, ranged (`≤N` below the floor),
   `true`, `preview` or `null` data gives `unknown`.

The profile summary for a feature is the worst engine state, with the order
native < transformed < equivalent < unknown < incompatible. Per-engine rows
always stay visible.

A combination is never better than any of its components. Its own record and
caveats apply on top of them.

Partial implementations and BCD notes are **never auto-native** (§9 T2). A
caveat disposition is a committed review keyed by its note digest. When a data
refresh changes the note, the disposition reverts to `unreviewed`.

### 4.3 Extraction from emitted CSS

The extractor runs on the canonical emitted rule entries of the revision:
property, value, selector or at-rule chain, and priority. It does not read
authoring syntax, so compiler-intrinsic output (§1) is covered. Each entry
keeps its source location and its owner, which is either a definition
condition, a token, a recipe or page source.

A bounded tokenizer maps values, selectors and at-rule preludes to feature keys.
A construct the tokenizer cannot classify yields `unknown /
unrecognized-construct`; it is never assumed native. The raw-string conditions
of Alpha 1 are covered this way until the CE-07 condition parser replaces the
tokenizer.

Records exist for features that the compiler does not admit yet, such as
`text-wrap`, anchors and view transitions. They are tested at the record and
outcome level. End-to-end compile cases use only constructs the Alpha 1 compiler
can emit: conditions, layers, admitted properties and values.

## 5. Diagnostics policy

### 5.1 Rules

- Every emitted feature is **required** unless an enhancement policy (§5.2)
  covers it.
- A required feature whose profile summary is `incompatible` or `unknown`
  fails that profile with an error. A target-profile failure makes the
  revision `ok: false`. Diagnostics are ready, but no generation is published.
  This is fail-closed (Q2).
- A required feature that is `transformed-with-proof` or `equivalent-fallback`
  passes and is reported in the target facts, not as a warning.
- An optional enhancement whose state is not `native` produces a warning, and
  `ok` is unaffected. Its fallback policy is applied and named in the warning.

### 5.2 Enhancement policy (design-system author only)

A new definition field, validated in the registry phase:

```js
enhancements: [
  { feature: 'selector:has', fallback: { kind: 'degrade', note: 'static layout without parent-state styling' } },
  { feature: 'value:text-wrap/pretty', fallback: { kind: 'degrade' } },
]
```

The fallback kinds in CE-01.1:

- `degrade`. The browser ignores the construct. The author accepts the
  resulting degraded behavior, and the outcome is reported as degraded,
  **never** as equivalent.
- `alternative-value`, which names an admitted value native on every
  announced engine, is defined in the schema. Its emission is deferred to
  CE-01.2 because it changes CSS bytes and identity (Q5).

Page-role source cannot declare a policy. A policy that names an unknown
feature, a non-catalog key or an invalid fallback is an error. A policy for a
feature that is already native everywhere produces an info diagnostic: the
policy has no effect.

### 5.3 Codes

The new codes are additive under diagnostics protocol v1, phase `targets`.

| Code                                  | Severity | Rule                                                                                       | Context / expected / repair                                                                                                                                                                                                                                                  |
| ------------------------------------- | -------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PMS_INVALID_TARGET_CONFIG`           | error    | `targets.config`, `targets.query.nondeterministic`, `targets.profile.unknown`              | Context `{ term, position }`. Repair `replace-target-term`, with candidates drawn from the supported term forms or built-in profile refs                                                                                                                                      |
| `PMS_INCOMPATIBLE_TARGET_ENGINE`      | error    | `targets.engine.obsolete`, `targets.engine.unsupported-floor`                              | Context `{ engine, version }`. Repair `remove-target-engine`, not applicable when the engine is the only one                                                                                                                                                                |
| `PMS_TARGET_CAPABILITY_INCOMPATIBLE`  | error    | `targets.capability.required`                                                              | Context `{ feature, property, value, conditionPath, profile, engine, floor, state, reason }`. Expected `{ states: [native, transformed-with-proof, equivalent-fallback], profile }`. Page role: candidates are admitted values of the same property that are native on every announced profile, with repair `replace-with-value`. Design-system role: repair `declare-enhancement`, or `raise-target-floor` (not applicable automatically) |
| `PMS_TARGET_CAPABILITY_UNKNOWN`       | error    | `targets.capability.evidence`                                                              | Same context as above; the reason is one of the `unknown` reasons. Repair `unknown`, `applicable: false`, unless candidates exist                                                                                                                                           |
| `PMS_TARGET_ENHANCEMENT_DEGRADED`     | warning  | `targets.enhancement.degraded`                                                             | Context `{ feature, profile, engines[], fallback }`. No repair                                                                                                                                                                                                               |
| `PMS_INVALID_ENHANCEMENT_POLICY`      | error    | `targets.enhancement.policy`                                                               | Design-system role only. Context `{ feature, fallback }`                                                                                                                                                                                                                     |

Diagnostics follow the existing protocol:

- One diagnostic per (feature, profile, source location). Per-engine rows go
  in `context.engines`, capped, with a total.
- `source` points at the emitting declaration or condition definition.
- `role` is preserved.
- Candidate bounds and truncation follow the v1 rules.

The code tables in `diagnostics-protocol-v1.md`, `reference/compiler-api.md` and
`agent-repair.md` are updated.

## 9. Threats to correctness

| Threat                                                   | Prevention                                                                                                                                                                                                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T1. Property support substituted for keyword or subfeature support | Each catalog key has its own BCD path, and the parent link is informational only. A key with no path is `unknown / no-data`. The extractor emits keyword, function, unit and at-rule-kind keys alongside the property key. A mutation test forbids parent fallback |
| T2. Partial implementations or bugs hidden               | `partial_implementation`, `prefix`, `flags`, `alternative_name` and notes block `native`. Caveats need a committed disposition keyed by note digest, and a changed note resets it. Per-engine rows are never collapsed out of facts or diagnostics                |
| T3. Non-deterministic data                               | Bundled generated data is regenerated in CI with byte identity. There is no runtime Browserslist and no ambient configuration, environment, clock or network input. Relative and usage queries are rejected. Data versions and digests sit in every resolution record |
| T4. A Playwright engine taken as Safari/iOS proof        | Evidence records carry the exact engine id, version, build and device class. The `safari_ios` basis can only be `compat-data[-mirrored]` or `executed` with `engine.id: safari_ios`. A validator rejects `webkit` or `safari` evidence attached to `safari_ios`. Dependency ranges and host manifests are not evidence classes at all |
| T5. Mirrored data presented as independent               | `mirrored` is taken from the BCD source and surfaced as `basis: compat-data-mirrored`                                                                                                                                                                              |
| T6. Compiler-intrinsic output escaping the check         | Extraction reads emitted rule entries, not authoring syntax, so layers, the specificity ladder, custom properties and `@property` are covered                                                                                                                       |
| T7. Electron conflated with Chrome                       | The `derived-from-electron` basis keeps the Electron version. Platform keys are `incompatible` outside Electron profiles                                                                                                                                           |

## 10. Open questions for the orchestrator

- **Q1. Query input.** Recommended: restricted `>=` query subset, explicit
  floors and named profiles, with no Browserslist at compile time. The
  alternative bundles an exact-pinned `browserslist` and accepts full queries.
  It needs runtime data identity checks and still rejects relative and usage
  terms.
- **Q2. Unknown outcomes.** Recommended: a required `unknown` is an error,
  failing closed. Accepting this may fail existing projects whose conditions
  contain constructs the extractor cannot classify.
- **Q3. Default engines.** Recommended: chrome, edge, firefox, safari,
  safari_ios and chrome_android, which is mostly mirrored data. Also choose
  whether firefox_android is included.
- **Q4. Android WebView.** Recommended: opt-in profile only.
- **Q5. `alternative-value` fallback emission.** Recommended: defer to CE-01.2.
  CE-01.1 ships `degrade` only.
- **Q6. Versioning.** Recommended: additive fields with versions unchanged
  (manifest 1, artifacts 1, build report 2, ABI 1). The alternative bumps
  `manifestSchemaVersion` to 2, which core's hard-typed identity and AG-03
  would have to absorb.
- **Q7. iOS proof engines for #81.** Accept a real device only, or also an
  Apple iOS Simulator runtime recorded as `device: simulator`?
- **Q8. Closure record.** Recommended: the new `decision-closures.v1.json`,
  leaving `scope-decisions.v1.json` untouched.
- **Q9. Implicit default.** Recommended: projects without `targets` get
  `pandamstyle:default@1`, with the new diagnostics and a migration note.
  The alternative is opt-in target checking until a later epoch.
- **Gate.** After implementation starts, the measured floor table and the
  floor exceptions (§3, step 4) come back for decision before the freeze commit.
