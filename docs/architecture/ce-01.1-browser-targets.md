# CE-01.1 design note: browser targets and capability outcomes

Status: **implemented in CE-01.1** on the branch of #44, with the
orchestrator decisions of 2026-10-19 recorded in
`tests/core-evolution/decision-closures.v1.json`. Where the earlier design text
and §5, §6, §8.1 and §10 differ, those sections describe the code. Nothing here
is a browser support claim: claims attach to emitted CSS and exact target
evidence only.
Task: [#44](https://github.com/lbframe/pandam-style/issues/44), epic #39, base
`e2a864b`. Follows the [agent delivery protocol](../agent-delivery-protocol.md)
rule 2.

## Revision: lighter design

Revised on 2026-10-19 at the orchestrator's request, to cut maintenance. It
replaces §2.2–§2.5 and §4. What changed, and why:

- **Browserslist instead of our own query parser.**
  - Profiles are Browserslist queries, resolved with exact-pinned
    `browserslist`, `caniuse-lite`, `electron-to-chromium` and
    `baseline-browser-mapping`.
  - Standard queries such as `defaults`, `> 0.5%` and `last 2 versions` are
    accepted. Only clock-dependent terms, and terms that read inputs outside
    the configuration, are refused.
  - The custom grammar and the browser-name table of the query parser are
    gone. A small map from Browserslist name to BCD id remains, because
    evaluation needs it.
  - Engines outside the announced set are recorded as exclusions with a
    warning, not refused, because `defaults` contains them. This replaces the
    error proposed in the original §2.5.
- **No global feature catalog.**
  - Keys exist only for constructs in the project's emitted CSS. The bundled
    data is the CE-00.1 BCD 8.1.6 data, restricted to the emittable paths
    (0.6 MB, down from 1.5 MB).
  - The BCD source checkout and the mirrored-statement label are dropped, as
    are the Electron map and release lists (Browserslist provides them), the
    `api:*` records, and property-scoped `::marker` combinations.
  - Keyword- and subfeature-level keys stay, which is AC2.
- **Outcome states.**
  - Five states are in the schema; CE-01.1 computes `native`,
    `equivalent-fallback` (reviewed platform inapplicability only),
    `incompatible` and `unknown`. `transformed-with-proof` is CE-01.2's.
  - Prefixed and flagged statements are never native. A partial statement is
    native only under a committed review with `partial: true`, `missing` and a
    `rationale` (orchestrator decision 7, which reinstates the reviewed-partial
    path); otherwise it is `unknown`.
  - A note on a full statement still needs a committed review (§4.4).

Unchanged:

- the configuration location;
- projects without `targets` getting the default profile;
- the diagnostics codes and policy (§5);
- the surfaced fields (§6);
- the decision mapping (§7), except D-BP-09: the data pin now means the
  Browserslist packages plus CE-00.1's BCD;
- the test plan (§8).

## 1. Source facts this design starts from

Each fact below was inspected in the source at `e2a864b`; none was executed.

- The compiler has no browser-target concept. `@mdn/browser-compat-data`
  appears nowhere. `browserslist` 4.28.0, `caniuse-lite` and
  `baseline-browser-mapping` appear in `yarn.lock` only transitively, through
  Babel. The root `package.json` already overrides `baseline-browser-mapping`
  with `resolutions`, which shows that a consumer can swap data under a
  dependency.
- The project configuration is `ProjectConfig` (`types/index.d.ts:12-24`),
  normalized in `project/session/index.js` `normalizeConfig`. Unknown keys are
  dropped silently. Vite and the Next coordinator forward an explicit
  allowlist. Rsbuild spreads its input through.
- `SEMANTIC_CONFIG_KEYS` (`designSystemFile`, `engineOptions`, `useCSSLayers`)
  trigger a counted full fallback (`compiler-configuration`). The per-file
  validity key and `fresh.js` take `engineOptions` and `useCSSLayers`.
- The compiler itself emits target-sensitive CSS whatever the source:
  - `@layer` blocks when `useCSSLayers` is set;
  - otherwise a `:not(#\#)` specificity ladder (`engine/ordering/rules.js:673`);
  - custom properties for tokens;
  - `@property` for typed tokens.

  Condition definitions are raw strings (`registry/index.js:413-441`). They
  can carry `:has()`, `@container`, `@supports` and media features verbatim.
- The canonical snapshot (`registry/snapshot.js`) has `identity`,
  `capabilities`, `registry`, `vocabulary`, `compiled` and `tooling.manifest`.
  The constants are ABI 1, `pms-0.1` and manifest schema 1. `artifacts.json`
  and core's `GeneratedIdentity` hard-check these identity fields.
- Registry 1,108 entries carry BCD 8.1.6 data at **property level only**.
  - 35 entries reference D-BP-06, 10 reference D-BP-07 and 3 reference
    D-BP-03.
  - The 101 `obsolete-engine-prefix` entries belong to CE-01.
- The CE-00.2 corpus (840 declarations) exercises these contexts:
  - selectors `:focus-visible`, `:dir()`, `::file-selector-button`;
  - media features `prefers-reduced-motion`, `forced-colors`,
    `prefers-contrast`, `pointer` and `hover`.

  It does not exercise `:has()`, containers, layers, `@property`, anchors,
  scopes or view transitions.

## 2. Target configuration contract

### 2.1 Where it lives

| Concern                                             | Owner                                                         | Surface                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Which engines an application announces              | Application (project)                                         | `ProjectConfig.targets`; host plugin options forward the same plain object  |
| Which features are optional enhancements, with what fallback | Design-system author                                  | New definition field `enhancements` (§5.2)                                  |
| What a reusable package requires                    | Compiler (computed)                                           | Manifest `targetRequirements` (§6, D-BP-13); a package never declares targets |

Targets are a property of the application, not of the design system. One
design system may serve applications with different targets. Consumer (page)
source can never change targets or policies.

### 2.2 Shape

```ts
interface TargetConfig {
  // Named profiles the application announces. All must pass.
  profiles: readonly ProfileRef[];          // e.g. ['pandamstyle:default@1']
  // Project-defined profiles, referenced as 'project:<name>'.
  define?: Readonly<Record<string, ProfileDefinition>>;
}
type ProfileRef = `pandamstyle:${string}@${number}` | `project:${string}`;
interface ProfileDefinition {
  query: string;           // a Browserslist query, §2.3
  platform?: 'electron';   // platform-scoped extensions (D-BP-03, LIM-07)
}
```

Built-in, versioned profiles are Browserslist query presets:

| Profile                         | Query preset                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| `pandamstyle:default@1`         | Modern evergreen web, desktop and mobile, with floors frozen from the corpus as described in §3. Engines: `chrome`, `edge`, `firefox`, `safari`, `ios_saf`, `and_chr`, `and_ff` |
| `pandamstyle:ios-safari@1`      | `ios_saf` at the default floor, for iOS-only applications                            |
| `pandamstyle:electron@1`        | `electron 44.7` (D-BP-03), with platform `electron`                                  |
| `pandamstyle:android-webview@1` | `android` at the default Chromium floor; opt-in only                                 |

A profile id is immutable. Changing floors means `@2`; `@1` never changes
meaning. When `targets` is absent, the project gets `pandamstyle:default@1`,
and provenance records `origin: "default"`.

### 2.3 Deterministic resolution

Resolution is a pure function of four inputs:

- the `targets` value, canonicalized with `stableJson`;
- the exact-pinned `browserslist`, `caniuse-lite`, `electron-to-chromium` and
  `baseline-browser-mapping` packages, which are compiler runtime dependencies;
- the compiler-bundled compat data (§2.4);
- the built-in profile presets.

Each profile query is resolved with Browserslist:

```js
browserslist(query, {
  config: false, env: undefined, path: undefined,
  ignoreUnknownVersions: false, mobileToDesktop: true, stats: {},
})
```

- The query is always explicit, so Browserslist never loads `.browserslistrc`,
  `package.json#browserslist`, `BROWSERSLIST` or `BROWSERSLIST_CONFIG`.
- `stats: {}` stops it from reading `BROWSERSLIST_STATS` or searching parent
  directories for `browserslist-stats.json`.
- `mobileToDesktop` gives `and_chr` and `and_ff` ranges real version lists
  instead of the single current mobile release.

Standard queries are accepted, including `defaults`, `> 0.5%`,
`last 2 versions`, `not dead`, `cover`, region usage and `supports`. With
pinned data they are deterministic. Before resolution, Browserslist's own
parser classifies every term, and `QUERY_TYPES` (`targets/resolve.js`)
classifies each of the pinned Browserslist's 46 query types; a test derives
that list from Browserslist's query table. Three classes are refused with
`PMS_INVALID_TARGET_CONFIG`:

- clock-dependent terms (`rule: targets.query.clock`): `last N years`,
  `since …`, `baseline` without a year or date, and
  `maintained node versions`;
- terms that read inputs outside the configuration
  (`rule: targets.query.ambient`): `browserslist config`, `extends`,
  `… in my stats`, `… in <package> stats`, `cover … in my stats`,
  `cover … in <package> stats` and `current node`. Region usage and region
  cover (`> 1% in US`, `cover 90% in alt-as`) read pinned data and are
  accepted;
- a query type absent from the classification, as after a Browserslist
  upgrade (`rule: targets.query.unclassified`).

A resolved browser list is split by name:

- Announced engines are `chrome`, `and_chr`, `edge`, `firefox`, `and_ff`,
  `safari`, `ios_saf` and `android`. They map to BCD browser ids for
  evaluation. For each engine, the floor is the lowest resolved version and
  `upTo` the highest.
- Every other browser is recorded in the profile's `excluded` list, never
  silently dropped. Its disposition is `obsolete` (§2.5) or `unannounced`, for
  example `samsung`, `opera`, `kaios` or `and_uc`. Exclusions give a
  `PMS_INCOMPATIBLE_TARGET_ENGINE` warning.
- A profile that resolves to no announced engine is an error.

Output: one **target resolution record** (`kind:
"pandamstyle-target-resolution"`, `schemaVersion: 1`):

```json
{
  "kind": "pandamstyle-target-resolution",
  "schemaVersion": 1,
  "digest": "sha256:…",
  "provenance": {
    "origin": "project-config",
    "inputDigest": "sha256:…",
    "ambientSourcesConsulted": []
  },
  "data": {
    "browserslist": { "version": "4.28.0", "digest": "sha256:…" },
    "caniuse-lite": { "version": "1.0.30001799", "digest": "sha256:…" },
    "electron-to-chromium": { "version": "1.5.459", "digest": "sha256:…" },
    "baseline-browser-mapping": { "version": "2.11.23", "digest": "sha256:…" },
    "pinned": true,
    "browserslistOptions": { "…": "…" },
    "compatData": { "schemaVersion": 1, "digest": "sha256:…", "bcd": { "version": "8.1.6", "publishedDataDigest": "sha256:…" } },
    "caveatReviewsDigest": "sha256:…"
  },
  "profiles": [
    {
      "ref": "pandamstyle:default@1",
      "origin": "builtin",
      "query": "…",
      "platform": null,
      "definitionDigest": "sha256:…",
      "browsers": ["chrome 149", "…"],
      "engines": [
        { "engine": "safari_ios", "dataEngine": "safari_ios", "floor": "…", "upTo": "…", "basis": "declared", "versions": ["…"] }
      ],
      "excluded": []
    }
  ]
}
```

- The `data` digests cover each package's `package.json` and the files
  resolution reads. `pinned` states whether the loaded packages are the exact
  pins. A consumer override of `caniuse-lite` shows up as a different version
  and digest, so the digest changes.
- `ambientSourcesConsulted` is always empty, and a test asserts it.
- An engine's `basis` is `declared`, or `derived-from-electron` for the
  `electron` engine, which is evaluated on Chromium (`dataEngine: chrome`).

### 2.4 Pinned compat data

`tools/targets/build-compat-data.mjs` generates
`packages/compiler/src/targets/data/compat-data.v1.json`, compiler-owned data
that is never edited. Its only input is the published BCD 8.1.6 `data.json`
that CE-00.1 already pins: the generator checks the digest recorded in
`docs/research/core-evolution-evidence.json`. There is no second data
pipeline: no BCD source checkout, no Electron map and no release lists, all of
which Browserslist provides.

The data is restricted to what the compiler can emit:

- `css.properties.<p>`, with every subfeature, for:
  - the Alpha 1 admitted properties;
  - the properties the accepted corpus and both Wacando sets exercise,
    directly, unprefixed or as a BCD alternative name;
  - `custom-property`;
- `css.selectors`, `css.at-rules` and `css.types`, because condition
  definitions and token values can emit any selector, at-rule, function or
  unit.

Each statement keeps `version_added`, `version_removed`,
`partial_implementation`, `prefix`, `alternative_name`, `flags` and a digest of
`notes`. A CI check regenerates the file and requires byte identity. The file
is about 0.6 MB, emitted once next to the bundles and read on the first target
evaluation.

### 2.5 IE and obsolete engines (D-BP-05)

Old target syntax is accepted, but it promises nothing:

- Internet Explorer (`ie`, `ie_mob`), legacy EdgeHTML (`edge` < 79), Presto
  Opera (`op_mini`, and `opera`/`op_mob` < 15) and BlackBerry resolve to
  `excluded` entries with disposition `obsolete` (LIM-05). They get a warning,
  and a profile made only of them is an error.
- `-ms-`, `-o-` and `-khtml-` properties in emitted CSS are `incompatible`,
  with reason `obsolete-engine`, on every profile.

## 3. Freezing the default profile from the corpus

The numbers come from the corpus and the data, never from upstream headlines.
Panda's FAQ floor and StyleX's Lightning CSS defaults are neither inputs nor
expected values.

1. **Feature set F.** Run the catalog extractor (§4.3) over two inputs:
   - every CE-00.2 corpus declaration in the profiles `web`, `content`,
     `forms` and `data`, using `accounting.v1.json` declarations, their
     contexts and the fixture stylesheets;
   - the compiler's **intrinsic emission features** under default
     configuration: custom properties, the `:not(#\#)` ladder,
     `@layer` (statement and block, only as a separate `useCSSLayers` variant)
     and the condition/at-rule wrappers that the engine emits.
2. **Per-engine minimum.** For each feature f and announced engine e, take the
   earliest version with full support: unprefixed, unflagged, not partial and
   without an unreviewed caveat (§4.2). The data in §2.4 is the only input.
3. **Floor.** `floor(e)` is the maximum over F of that minimum. The tool
   records the binding features that set each engine's floor.
4. **Floor exceptions.** A feature with no full-support version for some e
   cannot set a floor. It is listed as an exception and needs a reviewed
   decision before the freeze. The options are:
   - an optional enhancement with an author fallback;
   - an approved equivalent with proof;
   - an engine limitation recorded in the profile.

   Examples to expect include `forced-color-adjust` in Safari and `ruby-*` in
   some engines.
5. **Freeze.** `tools/targets/measure-floor.mjs` writes
   `packages/compiler/src/targets/profiles/default.v1.json`. It contains:
   - the floors, binding features and exceptions with their decisions;
   - the corpus manifest digest;
   - the data digest.

   A check rederives the file and requires identity, so the floor cannot
   drift from its inputs. **The measured table goes to the orchestrator for
   decision before the freeze commit.** Floor-binding versus enhancement
   choices are product decisions.

Features outside F, such as `:has()`, containers, anchors, view transitions,
`@scope`, typed `@property` or `text-wrap: pretty`, never raise the default
floor. Each is evaluated against the frozen floor and is either
`native`, or must be an author-declared enhancement, or fails the profile.

## 4. Capability records

### 4.1 Feature keys of the emitted CSS (`pandamstyle-feature-catalog`, v1)

There is no global feature catalog. A key exists only for a construct found in
the project's emitted CSS:

- design-system rules (tokens, themes, recipes, conditions);
- page rules;
- the compiler's intrinsic emission: custom properties, the `:not(#\#)`
  ladder, `@layer` under `useCSSLayers`, and `@property` where emitted.

Each key is evaluated on its own BCD path, never on its parent's.

| Kind            | Key form                          | Mapping rule                                                                                                                                       |
| --------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `property`      | `property:<name>`                 | `css.properties.<name>`. A vendor-prefixed name uses the base property's statements with exactly that prefix, and a renamed one uses its `alternative_name` statements. `-ms-`/`-o-`/`-khtml-` are obsolete |
| `value`         | `value:<property>/<keyword>`      | Every keyword with a BCD subfeature of its own, compared case-insensitively (`currentColor`): `text-wrap/balance`, `width/fit-content`, `display/multi-keyword`, `color/alpha-hex`, global keywords, and the named and system colors BCD records one by one (`AccentColor`, `Mark`) in any property. A keyword without one is the property's base grammar |
| `value` (fn)    | `value:<property>/<fn>()`         | Functions recorded under the property (`grid-template-columns/repeat()`)                                                                           |
| `function`      | `function:<name>[/relative]`      | Shared type families (color, gradient, image, then `css.types`), searched case-insensitively. Transform, filter, easing and basic-shape functions only for properties whose grammar uses them, so `clip: rect()` never borrows `basic-shape/rect()`. `css.types` comes last, so `color()` is `css.types.color.color`, never the `<color>` type |
| `unit`          | `unit:<unit>`                     | Container, viewport-variant, font-relative, angle, time, resolution and flex units                                                                 |
| `selector`      | `selector::<pseudo>` / `::<pseudo>` | `css.selectors.<name>`, or its alternative name (`:-moz-focusring`)                                                                              |
| `at-rule`       | `at-rule:<name>[/<kind>]`         | `layer/statement`, `layer/block`, `container/style`, `container/scroll-state`, `supports/selector`, `scope`, `starting-style`, `position-try`, `view-transition`, `property` |
| `media-feature` | `media:<feature>`                 | `min-`/`max-` folded, `range_syntax`, `or_syntax` (D-BP-11)                                                                                        |
| `descriptor`    | `descriptor:<at-rule>/<name>`     | `@property` and `@font-face` descriptors with their own statements                                                                                 |
| `platform`      | `platform:electron/<name>`        | `-webkit-app-region`, `-webkit-user-drag`, `-webkit-font-smoothing` (D-BP-03, LIM-07)                                                               |
| `combination`   | `combination:<key>`               | `:has()` nested in `:has()` and pseudo-elements in `:has()` (invalid everywhere); `!important` in a layer block (restriction recorded for CE-01.2)   |
| form            | `<construct key>/<form>`          | A way of writing a construct that BCD records as a subfeature (§4.6): `selector::nth-child/of-syntax`, `property:overflow/multiple-keywords`, `function:rgb/space-separated-parameters`, `function:color/display-p3-linear`, `media:display-mode/standalone` |

In a `font-family` stack, every entry except the last is an author-declared
fallback written in the value. It is evaluated and recorded, and when it is not
native it gives a warning like an enhancement, not an error.

### 4.2 Record and outcome

A **per-target outcome** is computed and never authored:

```json
{
  "feature": "value:text-wrap/pretty",
  "engine": "firefox",
  "floor": "…",
  "state": "incompatible",
  "reason": "no-support",
  "basis": "compat-data",
  "path": "css.properties.text-wrap.pretty",
  "caveats": []
}
```

The five states are all in the schema. CE-01.1 computes four of them:
`native`, `equivalent-fallback`, `incompatible` and `unknown`.
`transformed-with-proof` comes only from CE-01.2 (#45). `equivalent-fallback`
comes only from a reviewed platform inapplicability
(`catalog/inapplicable.v1.json`, reason `platform-inapplicable`): `cursor`
values on `safari_ios`, `forced-color-adjust` on `safari` and `safari_ios`,
`resize` on `safari_ios` and `firefox_android`. It applies only where the data
answer is `incompatible` or `unknown`, and the outcome keeps that data answer
in `equivalent.data`. An author enhancement or a value fallback
does not change a state: the state stays honest, and the policy
decides warning versus error.

The outcome function is total and ordered per (feature, engine, target range):

1. If the construct was not recognized, the outcome is `unknown` with reason
   `unrecognized-construct`.
2. A fixed record applies next: an obsolete prefix, an invalid combination, or
   a platform feature outside its platform.
3. A **full** statement applicable at the floor gives `native`. Full means the
   emitted name, no prefix it does not use, no flag and not partial, with no
   removal up to `upTo`. Its BCD note, if any, must have a committed review
   (§4.4).
4. Otherwise the reasons are checked in this order:
   - full support only later: `incompatible`, `support-after-floor`;
   - ranged data: `unknown`, `ranged-data`;
   - **partial**: `native` with reason `reviewed-partial` only under a
     committed review carrying `partial: true`, `missing` and a `rationale`
     (a property-scoped review, such as `::marker` on Safari limited to
     `color` and `font-size`, refuses every other property as
     `blocking-caveat`); otherwise `unknown`, `partial-implementation`;
   - flagged only: `incompatible`, `flagged-only`;
   - prefixed or renamed only: `incompatible`, `prefixed-only` or
     `alternative-name-only`;
   - `preview`, `true` or `null` data: `unknown`;
   - otherwise: `incompatible`, `no-support`.
5. A `native` answer becomes `unknown`, reason `unresolved-subfeature`, when a
   reviewed `fail-closed` subfeature of the path (§4.6) is not native on that
   engine: the extractor cannot tell whether the emitted CSS uses it.

The basis is `compat-data`, or `derived-from-electron` for Electron. `executed`
and `executed-simulator` are reserved for evidence (§4.5). A profile summary is
the worst engine state, and per-engine rows always stay visible.

### 4.3 Extraction from emitted CSS

The extractor tokenizes each emitted rule (`@csstools/css-tokenizer`, already a
compiler dependency) and walks:

- selectors, recursing into `:has()`, `:is()`, `:where()` and `:not()`;
- at-rule preludes: media features, container query kinds and `@supports`
  functions;
- declarations: property, keywords, functions, units and `!important`.

Each construct keeps the owner (design system, page file with line and column,
or compiler-intrinsic) and its context: property, value, selector, at-rule
chain, and the registry conditions it came from. A construct the extractor
cannot classify is `unknown` (`unrecognized-construct`), never native.

Emitted rules are ASCII. A rule text without escapes, comments, non-ASCII
characters or unquoted `url()` is tokenized by `targets/tokens.js`, which gives
the tokens `@csstools/css-tokenizer` gives for that subset; any other text goes
to `@csstools/css-tokenizer`. A test compares both on generated inputs.

### 4.4 BCD note reviews

`packages/compiler/src/targets/catalog/caveats.v1.json` holds committed reviews
of notes on full statements. Each review is keyed by BCD path, engine and note
digest, and holds:

- a disposition: `irrelevant`, `restricts` (native, with the restriction
  recorded) or `blocking`;
- optionally `effectiveFrom`: below that floor the note counts as unreviewed,
  which is how historical "before version N" notes are handled;
- a rationale.

A note without a review makes the statement `unknown`. A changed note is
unreviewed again. A partial statement is reviewable only by a review with
`partial: true`, `missing` (the sub-behavior the engine lacks) and a
`rationale` (why the emitted use does not depend on it); a plain note review
never makes a partial statement native. The reviewed partials are
`overscroll-behavior`, `accent-color`, and `::marker` on Safari limited to
`color` and `font-size` (orchestrator decision 7). `targets-catalog-test`
requires every review to match a note of the bundled data and every partial
review to carry its three fields.

### 4.5 Evidence

Executed evidence records (`pandamstyle-target-evidence`, v1) are defined now
and produced in #81:

- They name the engine id, version, build and device, which is one of
  `real-device`, `simulator`, `desktop` or `headless`.
- `safari_ios` evidence requires `real-device` (basis `executed`) or
  `simulator` (basis `executed-simulator`, labelled separately). A real-device
  claim needs real-device evidence.
- Playwright WebKit and other WebKit ports are refused as `safari` or
  `safari_ios` evidence.

### 4.6 Syntax forms and the subfeature guard

BCD records many ways of writing a construct as subfeatures of the
construct's path: `:nth-child(2 of .y)` is `css.selectors.nth-child.of_syntax`
(Chrome 111), `overflow: hidden auto` is
`css.properties.overflow.multiple_keywords`, `rgb(1 2 3 / .5)` is
`css.types.color.rgb.space_separated_parameters`, and
`color(display-p3-linear …)` is
`css.types.color.color.colorSpace_parameter_accepts_display-p3-linear_value`
(Chrome 144). Evaluating such CSS on the parent's statement would report it
native where it is not.

The extractor reads these forms as `{ kind: 'form', …, suffix }` constructs
next to the construct they qualify, and the catalog resolves the suffix
against that construct's own BCD node (`subfeaturePath`). A form whose node has
no such subfeature adds nothing. The forms read are:

- keyword arguments of a function (`perspective(none)`, `env(…)`,
  `linear-gradient(to …)`, `steps(…, jump-end)`, `color(display-p3-linear …)`)
  and functions nested in a function (`if(style())`, `attr(type())`, `calc()`
  nested, in a color component or in a gradient stop);
- argument shapes: space-separated, alpha, float and mixed `<number>` and
  `<percentage>` color parameters, relative color from `currentcolor`,
  `color-mix()` with other than two colors, `light-dark()` images, gradient
  interpolation, hue methods, hints, double positions, a single stop and a
  unitless `0` angle, typed division in math functions;
- value shapes per property: multiple keywords, two values, elliptical and
  four-corner radii, alternative text, cursor positions, `rem` font sizes,
  negative `z-index`, 3D transforms, multiple shadows, backgrounds and masks,
  the spread radius, basic shapes, `text-decoration` shorthand parts,
  `white-space` shorthand values, `font` widths, `first`/`last baseline`, and
  a property animated by `transition` or set in `@keyframes`;
- selector forms: `of <selector>`, `:not()` selector lists, `:lang()` lists
  and wildcards, `::cue()` arguments, attribute case modifiers, nested
  pseudo-elements (`::before::marker`), keyword arguments
  (`::scroll-button(up)`), properties BCD records per pseudo-element
  (`::selection { text-decoration }`, `::marker { quotes }`), animations of
  generated content, and `::backdrop` values that rely on inheritance;
- at-rule forms: media feature values (`display-mode: standalone`) and
  computed values, container features and range syntax, name-only container
  queries, `named-feature()`, `@import` `layer` and `supports()`, page-margin
  boxes, `@page` descriptor keywords, `@keyframes` timeline ranges and
  `!important`, and `@font-face` `format()`/`tech()` hints.

`catalog/subfeatures.v1.json` reviews every other subfeature of a path an
emitted construct is evaluated on, with one of two dispositions:

- `not-css-syntax`: the subfeature is not a way of writing CSS. It states
  support for a layout context, an element type, the document's language or
  script, a referenced resource's format, or an engine behavior (matching
  boundaries, privacy, interpolation, shorthand expansion). The construct's
  own statement is evaluated;
- `fail-closed`: a syntax form the extractor does not read. Where it is not
  native and the construct is, the construct is `unknown` with reason
  `unresolved-subfeature` (§4.2, rule 5).

`targets-subfeature-test` derives the guard from the bundled data. It
generates example CSS for every construct family and executes extraction on
it, then requires every unreached subfeature of a reached path to be reviewed
and every review to name such a subfeature. A subfeature added by a data
update fails the test until it is extracted or reviewed. Parent named and
system colors (`css.types.color.named-color`) are value types, not constructs;
their keywords are read as `value` keys (§4.1).

## 5. Diagnostics policy

### 5.1 Rules: advisory and enforced modes

Every emitted feature is **required** unless an enhancement policy (§5.2) or a
fallback written in the value itself (every entry but the last of a
`font-family` stack) covers it. The enforcement mode follows the configuration's
provenance (orchestrator decision 4):

| Mode       | When                                            | Required `incompatible` / `unknown`        | Enhancement not native | Revision                                              |
| ---------- | ----------------------------------------------- | ------------------------------------------ | ---------------------- | ----------------------------------------------------- |
| `advisory` | no `targets` (provenance `origin: "default"`)   | warning, `context.enforcement: "advisory"` | warning                | `ok`, publishes; the profile is recorded as `failing` |
| `enforced` | explicit `targets` (`origin: "project-config"`) | error                                      | warning                | `ok: false`, nothing published                        |

In both modes the default profile is resolved and every outcome recorded. A
required feature that is `transformed-with-proof` or `equivalent-fallback`
passes and appears only in the facts. A policy for a feature native on every
announced profile gives an info diagnostic. A failing resolution (invalid
configuration, refused term, unknown profile, no announced engine) is an error
in both modes, because there is nothing to evaluate. Engines outside the
announced set are excluded with a warning.

A migration note for existing projects is in
[agent migration](../agent-migration.md#browser-targets-ce-011-behavior-change).

### 5.2 Enhancement policy (design-system author only)

The definition field `enhancements`, validated in the registry phase:

```js
enhancements: [
  {
    feature: 'selector::has',
    fallback: {
      kind: 'degrade',
      note: 'static layout without parent-state styling',
    },
  },
  { feature: 'value:text-wrap/pretty', fallback: { kind: 'degrade' } },
];
```

- `degrade`: the browser ignores the construct and the author accepts the
  degraded behavior. The outcome stays as computed and is reported as degraded,
  **never** as equivalent.
- `alternative-value` is in the schema and refused with
  `PMS_INVALID_ENHANCEMENT_POLICY` (`context.deferredTo: "CE-01.2"`): its
  emission changes CSS bytes and identity and belongs to CE-01.2 (#45).
- A policy naming a key that is not a catalog key, without a fallback, with an
  unknown fallback field or kind, or duplicated, is
  `PMS_INVALID_ENHANCEMENT_POLICY`. Page source cannot reach the field.
- The normalized list enters the registry payload, and so `registryDigest`, only
  when it is non-empty: a definition without it keeps its digest.
- A policy covers the construct's forms (§4.6): a form key is
  `<construct key>/<form>`, and a degraded construct degrades whichever way it
  is written. It does not cover keyword values: a policy on `property:display`
  leaves `value:display/flex` required.

### 6.2 Cost model

Target checking reads every emitted rule, so the implementation keeps a
revision's cost proportional to what changed (CE-00.3 budgets):

- Each unit (a page contribution, the design system's `injected` rules, the
  compiler-intrinsic emission) is summarized once per unit identity, and a
  recompiled page whose rules and locations are unchanged keeps its previous
  summary. The session holds one accumulator that adds and removes only changed units and
  reuses its previous evaluation when nothing changed. Facts entries are
  memoized frozen objects, so unchanged facts keep their object and digest.
  A fresh build uses the same functions without an accumulator; tests require
  incremental sums and results to equal a fresh evaluation.
- Resolution is memoized by its canonical input. Built-in profiles resolve
  from `profiles/builtin-resolutions.v1.json`, precomputed with the pinned
  Browserslist and used only when every loaded data package has the recorded
  version and digest; anything else resolves live, and Browserslist is loaded
  on first live use only.
- The compat data is indexed once and each entry parsed on first use; the
  digest is still taken over the exact bytes. The public bundles carry the
  digest of the asset they ship, computed at build time, and a test hashes
  the shipped file; the bytes are kept as a one-byte Latin-1 string and each
  entry is decoded on first use.
- Feature keys whose totals did not change keep their evaluated entry and
  diagnostics; only touched keys are evaluated again. A design-system revision
  with the same structure (a token value edit) keeps its counts and facts and
  re-evaluates only the keys whose diagnostics read the changed contexts. Each
  facts entry is serialized once and spliced into the facts digests.
- Retention is bounded by the session: page content keys live with their file
  in the accumulator and are dropped with it, summaries are never mutated
  once cached, and the process-wide extraction results and construct records
  are bounded and evicted together. `targets-incremental-test` requires a
  session evaluation to equal a fresh one after every edit kind, a targets or
  data-identity change, and file additions, renames and deletions.

### 6.3 Determinism details found during implementation

- `baseline-browser-mapping` rejects a Baseline year later than the wall
  clock's, so `baseline 2027` fails in 2026 and resolves in 2027. A dated
  Baseline term after the newest release year in the pinned data is refused as
  `targets.query.clock`; up to that year the term never depends on the clock.
- Browserslist prints an "update caniuse-lite" warning once its data is six
  months old. That advice would break the pin, so it is suppressed for the
  synchronous resolution call.

## 9. Threats to correctness

| Threat                                                   | Prevention                                                                                                                                                                                                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T1. Property support substituted for keyword or subfeature support | Each catalog key has its own BCD path, and the parent link is informational only. A key with no path is `unknown / no-data`. The extractor emits keyword, function, unit, at-rule-kind and syntax-form keys alongside the property key. A mutation test forbids parent fallback, and the subfeature guard (§4.6) fails on any subfeature neither extracted nor reviewed |

## 10. Open questions for the orchestrator

Resolved on 2026-10-19; the answers are recorded in
`tests/core-evolution/decision-closures.v1.json` (`orchestratorDecisions`). Q1
was answered with exact-pinned Browserslist (lighter design), Q2 with
fail-closed `unknown` under explicit targets and advisory warnings without them,
Q3 with the default engines including Firefox for Android, Q7 with the iOS
Simulator labelled `executed-simulator`. The questions are kept below as asked.

- **Q1. Query input.** Recommended: restricted `>=` query subset, explicit
  floors and named profiles, with no Browserslist at compile time. The
  alternative bundles an exact-pinned `browserslist` and accepts full queries.
  It needs runtime data identity checks and still rejects relative and usage
  terms.
- **Q2. Unknown outcomes.** Recommended: a required `unknown` is an error,
  failing closed. Accepting this may fail existing projects whose conditions
  contain constructs the extractor cannot classify.
- **Q3. Default engines.** Recommended: chrome, edge, firefox, safari,
  safari_ios and chrome_android, which is mostly mirrored data. Also choose
  whether firefox_android is included.
- **Q4. Android WebView.** Recommended: opt-in profile only.
- **Q5. `alternative-value` fallback emission.** Recommended: defer to CE-01.2.
  CE-01.1 ships `degrade` only.
- **Q6. Versioning.** Recommended: additive fields with versions unchanged
  (manifest 1, artifacts 1, build report 2, ABI 1). The alternative bumps
  `manifestSchemaVersion` to 2, which core's hard-typed identity and AG-03
  would have to absorb.
- **Q7. iOS proof engines for #81.** Accept a real device only, or also an
  Apple iOS Simulator runtime recorded as `device: simulator`?
- **Q8. Closure record.** Recommended: the new `decision-closures.v1.json`,
  leaving `scope-decisions.v1.json` untouched.
- **Q9. Implicit default.** Recommended: projects without `targets` get
  `pandamstyle:default@1`, with the new diagnostics and a migration note.
  The alternative is opt-in target checking until a later epoch.
- **Gate.** After implementation starts, the measured floor table and the
  floor exceptions (§3, step 4) come back for decision before the freeze commit.
