### 1.2 Observed number and value behavior

The full probe table is in Appendix C. In summary [obs]:

- `flex: 1e308` emits **`flex:Infinity`**, and `flexGrow: 2**53 + 1` is
  accepted;
- `opacity` values 0.33333, 0.3333 and 0.33334 collapse into one class;
- a spacing token `-4px` is accepted on `paddingTop`, which gives invalid CSS
  at computed-value time;
- the token value `red;}body{display:none` breaks out of its rule, and
  `red !important`, comments, `url()`, `expression()`, `var()`, `NaN` and
  `1e+308` are emitted verbatim.

The static evaluator resolves `Infinity` and `NaN` identifiers
(`frontend/babel/static-evaluator.js:526-533`) [read]. The range check's
`Number.isFinite` (`properties.js:220`) is therefore what refuses them on the
range rows. It does not bound magnitude.

## 2. Grammar enforcement

### 2.1 Source: the descriptor `grammar` field, through a closed subset

No new production dependency. **[inferred]** `css-tree` or `@webref/css` would add a large
unpinned grammar surface, a supply-chain input and load cost, against about
1.3% RSS headroom (§7). They would also only *recognize* CSS, while policy needs
*finite admission*.

- `policy/grammar.js` (new) parses each descriptor's `grammar` string, once
  per process and lazily, into a closed node set:
  - **`keyword`**: an identifier;
  - **`numeric`**: one of `<length>`, `<percentage>`, `<length-percentage>`,
    `<number>`, `<integer>` or `<time>`, with optional CSS Values 4 range
    brackets such as `<length-percentage [0,∞]>`;
  - **`opaque`**: anything else, such as juxtaposition, `&&`, `||`, `#`,
    multipliers, function productions or `<calc-sum>`.

  Alternation `|` is the only combinator it interprets.
- **What grammar drives:**
  1. which keywords and which numeric literal shapes a design author may
     approve in `propertyDomains` (§3.3);
  2. a catalog test, which checks that every compiler-owned `standard`/`default`
     member is either matched by a non-opaque branch or listed in the row's
     reviewed `opaqueValues`. `opaqueValues` holds exact strings such as
     `repeat(3, minmax(0, 1fr))`, `inset(50%)`, `grayscale(1)` and
     `translateY(1px)`;
  3. the cross-check of the explicit per-row scalar constraints that govern
     token values (§3.5). Scalars are data; they do not depend on parsing
     opaque grammar.
- **Fail-closed on unsupported grammar.** An `opaque` branch admits nothing
  beyond the row's exact `opaqueValues`. An author literal that only an opaque
  branch could match is rejected with `property-domains.grammar-unsupported`.
  That rule is distinct from `grammar-mismatch`, so the author can tell a
  compiler gap from an authoring error. A grammar string that does not parse
  fails the catalog test, which keeps it out of a build.
- **Admission evidence (round-1 decision a).** Every grammar branch that
  *grants* admission (keywords, numeric branches and the §3.5 scalar
  constraints) is qualified against independent spec evidence. A dev-only
  test (`grammar-webref-test.js`) compares it with `@webref/css`, which is
  pinned to an exact version as a root devDependency. Version 8.7.7 is the
  latest at 2026-10-22 [obs: `npm view`]; the pin is frozen in PR A.

  For each row, the test checks two things, with webref's referenced
  productions (`<'padding-top'>`, …) expanded:
  - every admitted keyword occurs in webref's value syntax;
  - every numeric branch's type exists there, with bounds at least as tight
    as webref's range notation.

  `src/` never imports `@webref/css`, and a test asserts that `lib/` contains
  none of it. Opaque branches stay exact, compiler-reviewed strings
  (`opaqueValues`). The BCD 8.1.6 `spec_url` (for example, `width` points to
  css-sizing-3 [obs]) stays as row provenance.

### 2.2 Consumers never run the grammar

Consumer and system declarations are checked by membership only (§3.2). The
grammar is compiled once per process, at the first `buildDesignSystem`, into
frozen per-row constraints; author data is checked at registry build.
**Invariant G1:** `checkValue` reads only precompiled data (effective domains,
row constraints, token `numericFacts`). It imports neither `policy/grammar.js` nor
the tokenizer. A structural test asserts that.

## 3. Finite numeric domains

### 3.1 The numeric model

Each `numeric` grammar node compiles to a constraint:

```js
{ type: 'length'|'percentage'|'length-percentage'|'number'|'integer'|'time',
  min: number|null, max: number|null,       // inclusive, finite, from range brackets
  units: readonly string[],                 // derived, see below
  fractionDigits: 4, magnitude: 1e6 }       // global caps
```

- **Units, from a single authority.** `units` comes from `targets/catalog.js`
  `UNIT_PATHS`, by the BCD path prefix: `css.types.length.*` for `<length>`
  and `css.types.time` for `<time>`. A unit that the target catalog cannot
  classify can therefore never be approved. Every approved unit reaches target
  facts through the existing `{ kind: 'unit' }` extraction
  (`targets/extract.js:1291-1293`). The units table is exported read-only; it
  is not copied.
- **Integer or real.** `<integer>` requires `Number.isSafeInteger`. `<number>`
  accepts reals with at most `fractionDigits` fraction digits.
- **Non-finite and extreme values.** `NaN`, `±Infinity` and `|v| > magnitude`
  are rejected, as are exponent notation in strings and more than 4 fraction
  digits. The 4-digit cap equals the engine's rounding (`transform-value.js:25`).
  Every admitted number therefore serializes exactly, and distinct members never
  collapse (§1.2).
- **Zero.** `-0` is `0`. For `<length>` and `<length-percentage>`, the
  canonical zero is the unitless `0`. `0%` stays a distinct percentage member,
  and `<time>` zero keeps its unit (`0s`).
- **Canonical spelling** (`policy/literals.js`, `canonicalLiteral(constraint,
  input)`):
  - no leading `+`;
  - no redundant leading or trailing zeros (`0.5px`, not `.5px` or `0.50px`);
  - a lowercase unit;
  - no whitespace, comments or escapes.

  Numbers stay JS numbers and dimensions stay strings. A number is never given a
  unit: a bare number on a length row is rejected unless it is `0`
  (deliverables 1 and 5).

### 3.2 Consumer admission is set membership

The CE-02.1 effective domain stays the only admission source (invariant 6 of
that note). In CE-02.2 it becomes `{ values, tokens, resources }` and loses
`range`. `checkValue` does exactly this:

1. Token refs follow the CE-02.1 rules, plus the §3.5 scalar check.
2. A literal matches when `domain.values` contains it under SameValueZero, or
   when it is numeric `0` and the domain contains `'0'`, as Alpha 1 does.
3. On failure only, a lazy classifier computes `context.reason`
   (Appendix A) and, when it is unambiguous and in the domain, the canonical
   spelling as the first candidate.

Membership in a finite set of canonical, validated members is safe and finite
by construction. A consumer value can never be non-finite, non-canonical or
unsafe if it is accepted (invariant N1).

### 3.3 Author literals: only inside `standard`, only into the effective domain

CE-02.1 decision D4 deferred `width: '18px'`. CE-02.2 admits it as follows:

- A descriptor's `standard` gains a member, `numeric: Constraint[] | null`,
  compiled from its grammar. It is module-private, like `standard` itself.
- A `propertyDomains` `values` member is in `standard` when it is:
  1. in `standard.values` or `opaqueValues`;
  2. a keyword branch of the grammar;
  3. a canonical literal that satisfies one of the row's `numeric` constraints;
     or
  4. one of the CSS-wide keywords `inherit`, `initial`, `unset` or `revert`
     (§4.3).
- Anything else fails registry build with `PMS_INVALID_PROPERTY_DOMAIN`, under
  the rule for its class (Appendix A). A non-canonical member, such as
  `'18.0px'`, is an error that carries the canonical spelling; it is never
  silently rewritten. The stored domain therefore has exactly one spelling, and
  `registryDigest` is unchanged for every valid CE-02.1 entry.
- The effective domain is still exactly the override. Approved literals become
  finite `values`, so types, the manifest and candidates enumerate them.
  Consumers get no grammar channel. `compileStyles` keeps no domain parameter
  (CE-02.1 invariant 2).
- Negative lengths (deliverable 7) are a property of the grammar:
  - `marginTop`, `top` and `insetInlineStart` are signed;
  - `padding*`, `width`, `minWidth`, `maxWidth` and `height` carry `[0,∞]`.

  So `paddingTop: { values: ['-4px'] }` fails with
  `property-domains.out-of-bounds`.

### 3.4 Replacing the four legacy ranges (CE-02.1 D6)

`range` disappears from the descriptor, the effective domain, the manifest,
the types and the `propertyDomains` schema. `default` becomes finite:

| Row | Grammar (`standard`) | New `default.values` | Covers |
| --- | --- | --- | --- |
| `opacity` | `<number [0,1]>` | Multiples of 0.05 in [0, 1] (21 members) | Every literal opacity in the compiler tests, the examples, the CE-00.2 corpus and the CE-00.3 workloads (`tools/baselines/workloads.mjs:216`: 0.4, 0.6, 0.8, 1) [read] |
| `flex` | `none \| <number [0,∞]>` here; the full shorthand belongs to CE-02.3 | Integers 0–12 | No workload uses `flex`. Corpus `flex: none` stays refused until CE-02.3 |
| `flexGrow`, `flexShrink` | `<number [0,∞]>` | Integers 0–12 | Workloads: `flexGrow` 0, 1, 2; `flexShrink` 0, 1 (`workloads.mjs:217-218`) |

The CE-00.3 workloads keep compiling unchanged: their values are inside the new
defaults [read; verified at PR time by digest-stable workload compilation].
An author can approve other values inside `standard`:
- `opacity: { values: [0, 0.33, 1] }` and `flexGrow: { values: [0, 1, 1.5] }`
  are in `standard` (`<number [0,∞]>`, at most 4 fraction digits);
- `opacity: { values: [1.5] }` (out of bounds) and
  `flexGrow: { values: [0.123456] }` (precision) are not. The executable migration examples are in Appendix B.

### 3.5 Numeric facts of token values at the use site (B4)

This closes the negative-spacing case in §1.2 without CE-03 category grammar.

- **A scalar constraint on every applicable row.** Each descriptor whose
  admitted token categories can carry a number gets an explicit `scalar`
  member in `descriptors.js`:
  - the §3.1 constraint, plus `count`, the number of components the row
    accepts;
  - hand-written data, not derived from grammar, so rows whose grammar is a
    property reference or a multiplier are covered too.

  Examples:

  | Rows | `scalar` |
  | --- | --- |
  | `paddingTop`…`paddingBlockEnd`, including `paddingInlineStart` | `<length-percentage [0,∞]>`, count 1 |
  | `padding`, `paddingInline`, `paddingBlock` | The `padding-top` constraint per component; count 1–4, 1–2, 1–2 |
  | `margin*`, `top`/`right`/`bottom`/`left`, `inset*` | Signed `<length-percentage>` per component; count 1 for longhands and physical offsets, 1–4 for `margin` and `inset`, 1–2 for `marginInline`, `marginBlock`, `insetInline` and `insetBlock` |
  | `gap` | `<length-percentage [0,∞]>`, count 1–2 |

  Negative margins and offsets stay valid. The round-1 review counted 4
  negative margins and 5 negative offsets in the corpus. Two catalog tests
  apply:
  - each scalar equals its longhand's numeric grammar branch and passes the
    webref check (§2.1);
  - every row that admits a numeric-capable token category (`spacing`,
    `sizes`, `radii`, `fontSizes`, `lineHeights`, `letterSpacings`, …) has a
    `scalar`, so no row is silently unchecked.
- **Numeric facts, not a sign-only summary.**
  - At registry build, one tokenization of each base value and each theme's
    resolved value yields `numericFacts`. S1 (§4.2) reuses that tokenization.
  - `numericFacts` is `null` when the value is not a whitespace-separated list
    of numeric tokens. Otherwise it is a frozen list
    `[{ value, unit, integer, fractionDigits }]`, where `value` is the decoded
    number. Magnitude, finite bounds and precision are therefore checkable.
  - The facts are derived data, held in a `WeakMap` keyed by the registry (as
    `admittedTokens` is, `styles.js:104-129`). They are never stored in the
    registry, the snapshot or a digest; their input values are already in the
    `registryDigest` payload.
- **At use**, in the base and in every theme:
  - the component count must fit `scalar.count` (CSS Box 4 and CSS Logical 1 grammars; tests cover both count boundaries of every shorthand form, e.g. `paddingInline: '1px 2px 3px'` rejects);
  - every component must satisfy the scalar: units in `scalar.units`, no
    unitless non-zero number on a length row, bounds, at most 4 fraction
    digits, and `|v| ≤ 1e6` (a `1e308px` token decodes to a huge value and
    fails).

  A violation is `PMS_FORBIDDEN_VALUE`, rule `category-strict`,
  `reason: 'token-value-out-of-domain'`, with `component`, `constraint` and
  `theme` in context. Candidates are the category's tokens that pass.
- **Non-finite values arriving through tokens:**
  - a JS-number token value that is `NaN` or `±Infinity`, or whose magnitude
    is above 1e6, is a registry error (S1 clause 5);
  - on a row with a `scalar`, a token value that is a single identifier
    `nan`, `infinity` or `-infinity` (ASCII case-insensitive) is rejected at
    use with `reason: 'non-finite'`.
- **Limitation.** Other shapes (`calc()`, colors, mixed lists) stay unchecked
  until CE-03 typed category grammar (CAP-20). This is stated as a limitation,
  not claimed as coverage.

## 4. Safe value serialization

### 4.1 Threat model

- **Adversary A, the consumer task** (page source, relays, runtime props, a
  page-role repair agent). Its goal is to emit a declaration or value that the
  definition did not approve.
- **Adversary B, an honest but mistaken definition author.** Its failure mode
  is malformed or cascade-altering CSS. The issue's AC2 states that "build
  configuration authority does not excuse malformed CSS output".
- **Out of reach:** an author who deliberately writes well-formed hostile CSS.
  The author role is trusted for vocabulary (ADR 0003); §4.2 still refuses
  out-of-model constructs.

| Channel | Closed by |
| --- | --- |
| Consumer literal | N1: membership in validated canonical members |
| Consumer key `'--x'`, vendor keys | §4.3 rules; never admitted |
| Casts and `@ts-expect-error` | The compiler re-checks every value; types are a projection (§5) |
| An object imitating a `TokenRef` | `tokenPathOf` `refKind`, unchanged |
| Author literal (`propertyDomains`) | §3.3 grammar, plus S1 |
| Token, theme override and condition text | S1 at registry build |
| Condition-block keys in style objects (consumer, recipe, pattern) | S1 in `compileStyles`, before the key reaches the engine (§4.2, entry 3) |
| Global rules | No authoring entry today (§1.1). A future entry must call S1, and a structural test lists the S1 call sites |
| Compiler-owned `standard`/`default`/`opaqueValues` | S1 as a catalog test |
| Transform stage | Runs after S1. CE-01.2 `applyTransforms` finds declaration ends by `;`/`}` (`targets/transforms.js:186` at `01a556b`), so S1 is its precondition [read] |

### 4.2 Invariant S1: one safety predicate, by construction

`policy/value-safety.js` (new) has one function,
`unsafeValueClass(text, kind)`, where `kind` is `value` or `condition`. It
**always tokenizes the whole text** with the pinned `@csstools/css-tokenizer`.
There is no precheck and no fast path (round-1 decision B2).

**Entry points (B3).** Each one is enumerated, and a structural test pins
these call sites:

1. token values and theme override values, at registry build;
2. condition definitions, at registry build;
3. **condition-block keys** (`:…`, `@…`, `[…`) that reach emission through
   `compileStyles`, for every role: consumer `create()`, recipes (base,
   variants, compounds, slots) and patterns. The check runs on the key before
   the engine sees it. Selector grammar and ownership stay with CE-07.1
   (SF-02), and that includes refusing raw keys altogether. The safe key
   `'[dir=rtl] &'` therefore still compiles, as Alpha 1 records;
4. author literals in `propertyDomains`, and the compiler-owned
   `standard`/`default`/`opaqueValues` (a catalog test).

Global rules have no entry point today (§1.1).

A text is safe only when all of the following hold:

1. **No tokenizer error.** Any parse error the tokenizer reports is a
   rejection: bad-string, bad-url, an unclosed string, url or comment, or EOF
   inside a block or function. Blocks and functions must also balance (`[bad`
   fails).
2. **Closed token types.** The allowed types are ident, function, number,
   percentage, dimension, hash, string, whitespace, comma, `(`, `)`, `[`, `]`
   and the delims `/ + - * . %`. For `condition` text, the at-keyword and colon
   tokens and the delims `& > ~ = ^ $ |` are also allowed. Comments, CDO
   (`<!--`), CDC (`-->`), semicolon, `{`, `}` and `!` are outside the list.
3. **No raw `;`, `{`, `}` or `\` anywhere in the source text, inside strings
   included.**
   - The CE-01.2 transform scans raw `;`/`}` boundaries
     (`targets/transforms.js:186` at `01a556b`), so string context is no
     defense.
   - A backslash would allow an escape that re-spells a forbidden character or
     function name (`\75 rl(`, `\3b`), or a line continuation inside a
     string.
4. **Approved functions only, at every nesting depth.** Every function
   token's name must be in a frozen `APPROVED_FUNCTIONS` list. The comparison
   is ASCII case-insensitive (`uRl(` matches `url(`, which is not listed), on
   the tokenizer's decoded name. A url-token is never allowed.
   - **Vendor aliases** (`-webkit-image-set`, `-webkit-gradient`,
     `-moz-element`) are not listed and are never folded to an unprefixed
     entry.
   - **Unicode lookalikes** (fullwidth `ｕrl`, Cyrillic `у`) do not
     ASCII-fold to a listed name, so they are rejected as unlisted.
   - **The initial proposal** covers only what compiler-owned values,
     existing tests and workloads need:
     - for `value`: `rgb`, `rgba`, `hsl`, `hsla`, `hwb`, `lab`, `lch`, `oklab`,
       `oklch`, `color`, `color-mix`, `light-dark`, `cubic-bezier`, `steps`,
       `linear`, `calc`, `min`, `max`, `clamp`, `repeat`, `minmax`, `inset`,
       `translate`, `translateX`, `translateY`, `scale`, `rotate`,
       `grayscale` and `blur`;
     - for `condition`: `is`, `not`, `where`, `has`, `nth-child`,
       `nth-last-child`, `nth-of-type`, `nth-last-of-type`, `dir`, `lang`,
       `selector` and `scroll-state`.
   - **How PR B freezes the list:** it runs S1 over every existing fixture,
     workload and CE-00.2 corpus token. An existing use outside the list is
     reported as a compatibility delta, and is never silently added.
   - **Never listed:** reference constructs such as `url`, `src`, `image`,
     `image-set`, `element`, `cross-fade`, `paint`, `attr`, `var`, `env`
     (D4), `if` and `expression`, at any depth (`calc(var(--x))` fails).
5. **Finite numbers.** A JS number is finite, with magnitude at most `1e6`.

Each failure class is a distinct `reason` (Appendix A). Grammar beyond S1 stays
with the owning lots. S1 is the minimum that makes `generate-css-rule.js:87`,
`vars-utils.js:33` and the raw-key path safe to concatenate.

**S2, the serialization round trip (a catalog and fixture test).** For every
declaration that the fixtures and the CE-00.3 workloads emit, re-tokenizing the
emitted rule must yield exactly one declaration per property, the same value
tokens as the approved member and the expected selector/at-rule prelude. This
is checked before and after `applyTransforms`.

### 4.3 Finite outcomes for deliverable 3

| Input | Outcome |
| --- | --- |
| CSS-wide `inherit`/`initial`/`unset`/`revert` | Approvable per row in `propertyDomains.values`; never in `default`. Unapproved use: `FORBIDDEN_VALUE`, `reason: 'css-wide-keyword'` |
| `revert-layer` | Not approvable: `property-domains.css-wide-unsupported`. Its meaning depends on layers (CE-07; see the CE-01.2 note on layers) |
| `null` / `undefined` value | `FORBIDDEN_VALUE`, `reason: 'null-value'`. Removal and tombstones are not part of the consumer language; CE-02.3 decides on them together with resets |
| Consumer key `--*` | `PMS_UNSUPPORTED_PROPERTY`, rule `supported-properties.custom-property`. The compiler owns every emitted custom property |
| Vendor key (`Webkit*`, `Moz*`, `ms*`, `-webkit-*`, …) with no recognized row | `supported-properties.vendor-extension`, with `replacement` when a standard row exists. Recognized platform rows keep CE-02.1 F7 |
| Unknown property | CE-02.1 `supported-properties.unrecognized`, unchanged |
| Malformed definition data | `PMS_INVALID_PROPERTY_DOMAIN` rules (Appendix A). Unsafe token, theme or condition text: `PMS_FORBIDDEN_VALUE` / `value-safety.<class>`, phase `registry`; conditions: `PMS_UNKNOWN_CONDITION` / `value-safety.<class>` |

## 5. Single authority and downstream consistency

| Fact | Derived from (CE-02.2) |
| --- | --- |
| Acceptance | `snapshot.properties` effective `domain` (finite), plus token `numericFacts` derived from `registry.resolvedValues` and the theme values (§3.5) |

## 7. Performance risk

- **Gate:** CE-00.3 budgets v3. The c10000 session peak-RSS cell has about 1.3%
  headroom. **No pass is predicted.**
- **Design bounds (unmeasured):**
  - the consumer path adds no parse; on success it is one membership test, as
    in CE-02.1;
  - the classifier runs on failures only;
  - the grammar compiles once per process (107 short strings) into frozen
    constraints;
  - S1 tokenizes each token value once per registry build (t1000: 1,000 short
    strings), and each condition once;
  - `numericFacts` is one small frozen list per numeric token, or `null`.
- **Measurement in built artifacts (each PR), after `yarn build`, fresh
  process:**
  - added `lib/` bytes;
  - the heap and RSS delta of a `buildRegistry` on the c10000 definition with
    and without S1;
  - the retained size of `numericFacts`;
  - first-use cost of the grammar for a definition with 107 overrides.

  Then the budget gate on the measurement host store copy against `alpha1`,
  reporting the RSS, generated-module and CSS cells whatever the outcome.
- **No precheck and no fast path (B2).** S1 always tokenizes. Author text is
  small, and the definition-time entries run once per registry build.
- **The one compile-path entry is raw condition-block keys** (§4.2, entry 3).
  Their S1 result is memoised per key string in a `WeakMap` keyed by the
  registry, so each distinct key is tokenized once per design-system
  revision. The c10000 workloads use named conditions only [read:
  `tools/baselines/workloads.mjs`, to be confirmed by the PR B count].
