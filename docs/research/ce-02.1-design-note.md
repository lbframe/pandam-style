## 2. Descriptor model

### 2.1 One record per recognized property

`design-system/policy/descriptors.js` is a hand-written data module and the only
property authority. It holds a frozen, null-prototype `Map` from the authoring
key (camelCase) to a descriptor:

```js
{
  key: 'width', css: 'width', aliases: [],          // CE-02.3 fills aliases
  status: 'standard',                               // | 'platform'
  platform: null,                                   // CE-01.1 platform id, e.g. 'electron'
  grammar: "auto | <length-percentage> | min-content | max-content | fit-content",
                                                    // informative here; CE-02.2 enforces it
  contexts: ['element'],                            // see note below
  standard: { values: ['auto','min-content','max-content','fit-content','100%', /* Alpha 1 literals */],
              tokens: ['sizes', 'spacing'], resources: [], range: null },  // maximum approvable domain
  default:  { values: ['100%','fit-content','1px', /* … */], tokens: [], resources: [], range: null },
                                                    // = the Alpha 1 domain; `range` is non-null
                                                    // only on the 4 legacy rows (§6.2)
  form: 'longhand',                                 // | 'shorthand' | 'rejected-composite'
  longhands: null,                                  // shorthand expansion, parity-tested
  family: 'sizing',
  conflicts: [],                                    // reset/conflict family members (CE-02.3 consumes)
  direction: null,                                  // { axis: 'inline'|'block', side } | { physical }
  targetFeature: 'property:width',                  // derived by test from targets/catalog featuresOf()
}
```

- **Mixed domains.** A domain is a union of independent finite members: `values`
  (exact literal keywords or approved literals; numeric `0` is the same as
  `'0'`, as today), `tokens` (token categories) and `resources` (resource kinds,
  empty until CE-03). Two examples:
  - "an approved size token or `auto`/`min-content`" is
    `{ tokens: ['sizes'], values: ['auto', 'min-content'] }`;
  - Alpha 1's `width` is `{ values: [...10 literals] }`.

  No `kind` discriminant exists, so lowering, types, the manifest and
  diagnostics all handle the same union. The fourth member, `range`, exists only
  for the 4 legacy Alpha 1 rows. It is a continuous interval and is never
  described as a finite domain (§6.2).
- **Immutable lookup.** The compiler-owned catalog is a private `Map` inside
  `descriptors.js`, reachable only through `descriptorOf(key)` and
  `descriptorKeys()`. The `Map` never escapes the module; a frozen `Map` would
  still allow `set` and `delete`. The snapshot's `properties.descriptors` is a
  frozen null-prototype object, deep-frozen with every row. All lookups use
  `Object.hasOwn`, so no prototype key resolves.
- **Recognition is separate from admission.** `policy/recognized.v1.json` is
  generated by a new `tools/policy/build-recognized.mjs`, which supports
  `--check`, from the CE-00.1 registry entries. It holds `{ css, disposition,
  subkind, replacement }` for 1,108 names. It is loaded lazily, on a
  diagnostic path. It authorizes nothing; it only selects the outcome in §4.
  Its load and allocation cost is measured in the built artifact (§6.4), not
  assumed.
- **Scope.** Descriptors with domains exist only for the 107 Alpha 1 names (102
  admitted and 5 composite). Other recognized properties get their descriptors
  in their owning lots (CE-04 to CE-11).
- **Platform-extension rows are recognition-only in 02.1.** These rows carry
  `status: 'platform'`, a `platform` id and no domain. Every use of one is
  rejected with `PMS_UNSUPPORTED_PROPERTY`, rule
  `supported-properties.platform-extension`. This holds even when a target
  profile announces the matching platform. Admitting them is follow-up F7.
- **`contexts`.** In 02.1, `contexts` is `['element']` for every row. Condition
  blocks, recipes and patterns are element contexts today, so 02.1 changes no
  behavior. CE-07 adds pseudo-element and other contexts against the same
  field.
- **`targetFeature`.** A test checks that `targetFeature`, `platform` and
  `PLATFORM_FEATURES` are consistent. `PLATFORM_FEATURES` becomes
  `platformExtensions()` read from the descriptors, with the same 3 entries.

### 2.2 `propertyDomains`: author data that narrows or approves

```js
defineSystem({
  systemId: 'acme',
  tokens: { sizes: { sm: { value: '8rem' } } },
  propertyDomains: {
    width:   { tokens: ['sizes'], values: ['auto', 'min-content'] },  // approve: mixed
    display: { values: ['flex', 'grid', 'none'] },                    // narrow
  },
});
```

- **Normalization.** `policy/domains.js` `normalizePropertyDomains(input,
  tokens)` runs in `buildRegistry`, next to `normalizeEnhancements`
  (`registry/index.js:452`).
  - Each key must be an own key that names a descriptor whose `form` is not
    `rejected-composite` and whose `status` is `standard`.
  - Each entry is a plain object with at least one of the keys `values`,
    `tokens` and `range`, and no other key (`resources` arrives with CE-03).
    Each array is non-empty, has no duplicates and contains only strings or
    finite numbers.
  - `range` (`{ min, max }`) is accepted only on a row whose `standard.range`
    is non-null, and only if it lies within that range. A number in `values`
    is in `standard` when it is listed in `standard.values` or lies within
    `standard.range`.
- **The entry is the whole effective domain.** It may contain only members of
  the descriptor's `standard` domain. Any excess is an error, never silently
  dropped. Every approved token category must exist in `tokens` with at least
  one token.
- **Overrides disable whatever they do not restate.** When an override
  exists, the effective domain is exactly that override. Every member it does
  not restate is empty: `values`, `tokens`, `resources` and `range`. This holds
  for acceptance, types, the manifest and repair candidates alike. No branch is
  inherited from `default`. For example, `opacity: { values: [0, 1] }` rejects
  `0.5`, generates the type `0 | 1`, and drops `range` from the manifest
  (invariant 6, §7.1).
- **No consumer callback or broad channel.** No function, RegExp, pattern
  string, `"*"` or `string`/`number` type literal is accepted. The schema is
  data with closed keys.
- **Digest.** The normalized result goes into the registry payload, and so into
  `registryDigest`, only when it is non-empty. This follows the `enhancements`
  precedent at 469–471. A definition without it keeps its digest.
- **Typing.** `types/index.d.ts` `Definition` gains
  `propertyDomains?: Readonly<Record<string, { values?: readonly (string|number)[]; tokens?: readonly string[]; range?: Readonly<{ min: number; max: number }> }>>`.
  The keys are not enumerated, so this adds no hand-written allowlist.

### 2.3 Effective table

One function, `effectiveDomain(descriptor, override)` in `policy/domains.js`,
is the only place a domain is computed:

- with an override, it returns exactly
  `{ values: o.values ?? [], tokens: o.tokens ?? [], resources: [], range: o.range ?? null }`;
- without one, it returns `default`.

`buildDesignSystem` calls it once per row to build the effective table:

- a row an author entry overrides gets a new frozen descriptor with
  `domain = effectiveDomain(...)` and `origin: 'approved' | 'narrowed'`;
- every other row reuses the module-level frozen descriptor with
  `domain = default` and `origin: 'default'`.

Acceptance, types, the manifest, diagnostics, repair candidates and target
candidates read only the effective row's `domain`. None of them reads
`standard` or `default` (§3, invariant 6).

`origin` is `narrowed` when the effective domain is a subset of `default`, and
`approved` otherwise. One table serves both roles. Only token *visibility*
differs: public tokens for consumers, private tokens allowed for the system role.
This is unchanged.

### 2.4 Pattern consistency

Pattern declarations already pass through `compileStyles`. If narrowing removes
a value that a pattern parameter can emit (for example `display: 'grid'` for the
`grid` pattern), registry build fails with `PMS_INVALID_PROPERTY_DOMAIN`, rule
`property-domains.pattern-conflict`. The pattern catalog in the manifest
therefore never advertises an unusable selection (D8).

## 6. Migration, compatibility and performance

### 6.1 Alpha 1 behavior

Without `propertyDomains`, the effective domain equals `default`, which
transcribes Alpha 1. An equivalence test loads the pinned Alpha 1 blob the way
`classify.mjs:40-56` does and probes two sets:

- **Alpha 1 names.** Every one of them, with every admitted value, one token
  per category, out-of-domain probes and prototype keys.
- **Every recognized name that Alpha 1 did not support.** These are the 1,001
  names with `alpha1.kind: unsupported` in the CE-00.1 registry, converted to
  authoring keys with the `camel` expression in `classify.mjs`. Each
  scoped-platform-extension name is also probed in a project whose target
  profile announces its platform.

For both sets, the test asserts the same accept/reject result and the same
code as Alpha 1. The expected outcome for every name in the second set is the
Alpha 1 rejection, `PMS_UNSUPPORTED_PROPERTY`. There are only two intended
deltas:

- prototype keys move to `supported-properties.unrecognized`;
- `PMS_UNSUPPORTED_PROPERTY` rules gain a suffix (§4).

The CE-00.2 corpus tooling sees these renames:

- `tests/core-evolution/validate-corpus.mjs:534-538` requires each fixture's
  `sourceInspection.rule` (`supported-properties`, `category-strict`, …) to
  appear in its recorded `site`, `engine/lowering/styles.js`. PR A emits the
  rules from that file, so the check still passes: every new rule starts with
  `supported-properties`, and `category-strict` and `structural-domain` are
  kept (§4).
- `run-negatives.mjs:196-201` compares observed rules exactly with
  `observedAlpha1`. Against a CE-02.1 build, it reports the suffixed rules as
  deltas from the frozen alpha1 record. That record stays unedited.

The Alpha 1 module stays at its path, byte-identical, so that these keep
passing: `tests/core-evolution/validate.mjs` (its digest check), the corpus
validator and `tools/coverage`. Rollup only bundles what is imported, so the
module does not ship [inferred from `packages/compiler/package.json` `files: lib`
and the rollup build; to verify with `npm pack --dry-run`].

### 6.2 Ranges

The 4 Alpha 1 ranges stay as they are, as an explicit `range` member marked
`legacy` in the manifest and the types, until CE-02.2. CE-02.2 replaces them
and owns their source migration (decision D6). Two limits apply:

- a legacy range never bypasses an explicit override (§2.2);
- a range is never described as finite, whether in the manifest, the types,
  the diagnostics or the documentation.

### 6.3 Generated artifacts

CSS bytes are expected to be unchanged for workloads without `propertyDomains`
[inferred]. The design module, `.d.ts` and `manifest.json` change (manifest v2).
This is a new epoch, `ce-02.1-<sha>`, and the `alpha1` store is never modified.

**Epoch identity manifest (produced by PR B).** `ce-02.1-<sha>` gets a
committed identity manifest with the same shape as alpha1's, so that an AG
qualification (AG-12.2) can bind a candidate to the epoch:

- **Location:** `benchmarks/core-evolution/epochs/ce-02.1-<sha>/manifest.v1.json`,
  next to its closure `package.json` and lockfile.
- **Content, modeled on `benchmarks/core-evolution/epochs/alpha1/manifest.v1.json`:**
  the source commit and tree; each packed `@pandamstyle` tarball's file, bytes,
  SHA-256 and integrity; the closure install command; and the
  installed-tree and installed-`@pandamstyle` digests.
- **`<sha>`** is the PR B source commit that is packed.

The current tooling does not yet produce such a manifest for a candidate:

- `tools/baselines/archive.mjs` writes only the frozen alpha1 manifest, at a
  fixed path (`MANIFEST`, line 70; it refuses to overwrite at 992–997);
- `tools/baselines/measure.mjs` `epochIdentity` (88–125) records only a
  candidate closure's lockfile digest, package integrity and tree digest, and
  only inside raw results.

PR B therefore parameterizes the `archive.mjs` manifest command by epoch name
and closure. The command still refuses to overwrite any committed manifest,
including alpha1's.

### 6.4 Performance

- **Risk: budgets v3 on c10000.** Peak RSS headroom on the session cell is
  under 2% after CE-01.1. This note makes no prediction that either PR passes.
- **Design choices that bound the cost** (none of them is measured yet):
  - one own-key lookup per declaration, instead of up to four;
  - no per-declaration allocation;
  - module-level frozen rows are shared, and only author-overridden rows are
    allocated;
  - `properties` is pre-frozen, so the snapshot freeze skips it;
  - the recognized catalog loads lazily, on diagnostic paths;
  - one coarse semantic unit, not per-property arrays on 10,000 files;
  - a stable `domainOf` identity per snapshot.
- **Measurement in the built artifact (each PR).** After `yarn build`, a
  fresh-process script reports these figures for `lib/`:
  - added bundle bytes;
  - `heapUsed` and RSS deltas of loading the descriptor module, and of first
    loading `recognized.v1.json` (forced by one unrecognized-property
    diagnostic);
  - the retained size of `snapshot.properties`, from a heap snapshot of one
    `buildDesignSystem` on the c10000 design system.

  The figures are reported as measured, with no zero-cost claim.
- **Gate (both PRs).** Each PR runs the CE-00.3 budget gate before merge, on a
  copy of the store on the perf measurement host, against `alpha1`. The report
  states the RSS, generated-module (+10%) and CSS (+5%) cells explicitly,
  whatever the outcome.

  signals this break.
- Release notes are owned by CE-15.

## 7. Invariants, threat model and verification

### 7.1 Invariants by construction

1. Policy resolves a property only through `descriptorOf` (a private `Map`)
   or the frozen null-prototype `properties.descriptors`, using `Object.hasOwn`.
   No plain-object lookup remains, and no mutable catalog escapes its module.
2. `propertyDomains` is read only from the definition, in `buildRegistry`.
   `compileStyles` takes no domain parameter, and neither does any consumer API.
3. Effective ⊆ `standard`. Any violation is a registry error, which throws at
   `build-system.js:47`; nothing is partially applied.
4. Every domain member is a finite enumeration or a reference to a declared
   token. The only exception is the legacy `range` (4 rows, removed by CE-02.2),
   which is labeled as a continuous range and never as finite.
5. Types, manifest, candidates, repair domains and target candidates are all
   functions of `snapshot.properties`.
6. **No inherited admission branch.** `effectiveDomain` (§2.3) is the only
   function that computes a domain. With an override, it returns exactly the
   override, and every member the override does not restate is empty. Every
   consumer reads only the effective row's `domain`: acceptance, types,
   manifest, diagnostics, repair and target candidates. A structural test
   asserts that no module outside `policy/` reads `standard` or `default`.

### 7.2 Threat model

The adversary is a consumer task (page source, relay modules, runtime props, a
repair agent acting in the page role). Its goal is to authorize vocabulary or a
raw value. It has these channels:

| Channel | Why it cannot authorize |
| --- | --- |
| Style keys and values | Checked against the effective domain |
| A `propertyDomains` key inside `create()` | It is an unrecognized property |
| Prototype keys | Invariant 1 |
| An object that imitates a `TokenRef` | `tokenPathOf` with `refKind`, unchanged |
| Private tokens in a mixed domain | The visibility check is unchanged |
| A mutated generated manifest | The compiler reads the snapshot, never the module |
| Repair suggestions | Never offer author edits as applicable |

Out of compiler reach: who edits the design-system file. That file is the author
role (ADR 0003), exactly as for tokens today. `propertyDomains` adds no channel
beyond it.

## 9. AG compatibility

AG-03.1 (#12) and AG-03.2 (#13) are not started. The commitments below answer
AG's four original requests (descriptive fields, fingerprint split,
compilation identity, epochs) and its two round-1 requests (`meta` presence,
epoch identity manifest).

1. **Room for descriptive fields.** Each entity record, including a property
   descriptor and a `propertyDomains` entry, reserves one key, `meta`, for
   descriptive data. 02.1 creates no `meta` key.
   - The `propertyDomains` entry schema is closed in 02.1. AG-03.1 extends it
     with `meta` only.
   - Enforced fields are exactly those listed in a frozen `ENFORCED_FIELDS`
     constant beside the descriptors. Policy, types and diagnostics read only
     those fields, and a test asserts that no policy or engine module reads
     `meta`.
2. **`meta` presence semantics.** There are two distinct states,
   and every CE-owned normalization, flattening and projection preserves them:
   - **`meta` absent** (no own key): nothing is declared. Normalization never
     synthesizes a `meta` key or a default value such as `meta ?? {}`.
     Projections omit the key.
   - **`meta: {}` present and empty:** the author explicitly declares that
     there is no descriptive metadata. It is kept as an own key holding a
     frozen empty object. It is never collapsed into "absent", and "absent" is
     never expanded into it.

   The copy rule is `Object.hasOwn(entry, 'meta')`. It defines presence
   semantics, not a storage location: wherever metadata is stored or
   projected, the two states stay distinct. Storage is owned by AG-03.1 (#12,
   design note `docs/architecture/ag-03.1-vocabulary-metadata.md` §3.1): all
   validated `meta` lives in one side table, `registry.semantics`, and never
   in compiled records. The normalized `propertyDomains` entries, the
   effective table and the shared `snapshot.properties` rows therefore never
   carry `meta`, so the effective table stays shared and pre-frozen and no
   compilation digest can see metadata. AG-03.1 applies the same rule to
   fields inside `meta`, so "explicitly absent" never needs an invented
   sentinel value. Neither state enters a compilation digest (item 4). A test
   round-trips both states through normalization and the snapshot. That test
   lands with AG-03.1, because 02.1 still rejects `meta`. It round-trips
   both states through `registry.semantics` and asserts that `registryDigest`
   and `properties.digest` are byte-identical with and without `meta`.
3. **Fingerprint split without a format change.**
   - `properties.digest` and the `registryDigest` payload hash only enforced
     fields. They never include `meta`.
   - AG-03.2 can add a sibling `discoveryDigest` next to them without moving a
     field.
   - Caveat: the design module embeds `tooling.manifest` (`snapshot.js:313-314`).
     Metadata projected into the manifest would therefore change module bytes on
     a metadata-only edit. AG should project discovery metadata into a separate
     projection, or accept regenerating the module (not the CSS).
4. **Compilation identity: an explicit list, not wildcards.** These fields
   count, and only these:
   - **`documentKind`, `capabilities`.**
   - **`identity`:** `systemId`, `registryDigest`, `abiVersion`,
     `compilerContractVersion`, `manifestSchemaVersion`.
   - **`registry`:** `systemId`, `tokens`, `resolvedValues`, `themes`,
     `themeParents`, `themeOverrides`, `themeMetadata`, `conditions`,
     `conditionOrder`, `recipes`, `enhancements`, `propertyDomains` (minus
     `meta`), `vocabularyDomains`, `diagnostics`, `registryDigest`.
   - **`properties`:** `kind`, `schemaVersion`, `catalogVersion`,
     `catalogDigest`, `digest`, and for each descriptor the `ENFORCED_FIELDS`:
     `key`, `css`, `aliases`, `status`, `platform`, `grammar`, `contexts`,
     `domain`, `origin`, `form`, `longhands`, `family`, `conflicts`,
     `direction`, `targetFeature`.
   - **`targets`, `targetFacts`:** whole records, each with its own digest;
     they drive diagnostics.
   - **`vocabulary`:** `tokens`, `publicTokenPaths`, `tokenCategories`,
     `tokenPathsByCategory`, `semanticTokens`, `conditions`, `conditionNames`,
     `themes`, `themeDetails`, `publicRecipeIds`, `recipes`, `patterns`.
   - **`compiled`:** `varsByToken`, `themeClasses`, `themes`, `recipes`,
     `cssRules`.
   - **`tooling.manifest`:** `schemaVersion`, `systemId`, `registryDigest`,
     `abiVersion`, `compilerContractVersion`, `manifestSchemaVersion`,
     `capabilities`, `tokens`, `semanticTokens`, `tokenCategories`,
     `conditions`, `themes`, `themeDetails`, `recipes`, `patterns`,
     `properties`. These affect the design module bytes.
   - **`tooling.candidateDomains`:** `tokens`, `recipes`, `themes`,
     `conditions`, `patterns`, `properties`. These affect diagnostic
     candidates only.
   - **`tooling.repairDomains`:** `tokensByCategory`, `recipeAxes`, `themes`,
     `conditions`, `patterns`, `properties`. These also affect diagnostic
     candidates only.

   Excluded: every `meta` subtree, and every discovery-only digest. This
   includes a future `discoveryDigest`, even one placed next to
   `identity.registryDigest`: identity counts by the named fields above, not by
   `identity.*`. A field added later counts as compilation identity unless
   AG-03.2 lists it as discovery-only.
5. **Epochs.** Manifest v2 ships as epoch `ce-02.1-<sha>`.
   PR B commits that epoch's identity manifest, with tarball digests and its
   closure, modeled on the alpha1 manifest (§6.3), so that AG-12.2 can bind a
   candidate to it. The AG-00 corpus reads only the compiled Alpha 1 artifacts.
   The `alpha1` store and manifest are never edited.

## 10. Decisions

All ten recommendations of round 0 are accepted as decisions.

| # | Question | Decision |
| --- | --- | --- |
| D1 | A new `PMS_UNKNOWN_PROPERTY` code, or new rules on `PMS_UNSUPPORTED_PROPERTY`? | **Rules.** The code stays stable for the semantic oracle, the CE-00.2 corpus and agents |
| D2 | Bump the manifest to v2, or keep a lossy `supportedProperties`? | **Bump.** A category-xor-set view cannot represent mixed domains truthfully (migration in §6.5) |
| D3 | Bump `compilerContractVersion`? | **No.** The runtime ABI and refs are unchanged; manifest v2 marks the format and the break (§6.5) |
| D4 | Author literals outside `standard` (`width: '18px'`) in 02.1? | **No.** Use tokens. CE-02.2 adds grammar-validated literals |
| D5 | Approvable token categories: a closed list per descriptor, or any author category? | **Closed list** (adds `sizes`). CE-03 brings typed category grammar |
| D6 | Keep the 4 legacy ranges in 02.1? | **Yes, as they are, until CE-02.2.** A range never bypasses an explicit override (§2.2, invariant 6), and it is never described as finite (§6.2) |
| D7 | Relocate the pinned Alpha 1 policy file now? | **No.** Keep it byte-identical and unimported. Relocate at the next CE-00.1 registry regeneration (F1) |
| D8 | Narrowing that conflicts with a pattern: error, or drop the pattern? | **Error.** No silent catalog mutation |
| D9 | Incremental unit: one `property-domains` unit, or one per property? | **One,** given the RSS headroom. Domain edits already rebuild the design system. Finer units can come with CE-12.2 |
| D10 | Does narrowing apply to recipes (system role)? | **Yes.** One effective domain for every role; only token visibility differs |
